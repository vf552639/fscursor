# План: Автопривязка домена к Cloudflare-аккаунту по имени зоны

**Дата:** 2026-08-11
**Источник:** `task7.md`, план №3 роадмапа; долг из `task5.md`, оставшийся вне
объёма `2026-08-10-cloudflare-сворачивание-и-счётчик.md`.
**Связь с бизнесом:** пользователь заводит домены пачками, а зоны в Cloudflare у
него уже созданы. Сегодня связь между ними он проставляет руками по одной —
на сотне доменов это сотня одинаковых кликов, и любой пропущенный превращается
в домен, которому нечем прописать NS.

## Контекст (проверено кодом)

- Зоны в БД **не хранятся** — тянутся вживую командой `cf_list_zones`
  (`desktop/src-tauri/src/commands/cloudflare.rs:123`, зарегистрирована в
  `lib.rs:56`). Значит матчинг возможен только в десктопе.
- Тип `Zone` (`frontend/src/api/cloudflare.ts:53`) даёт `id`, `name`,
  `name_servers`, `status` — этого достаточно и для аккаунта, и для zone_id.
- Один запрос на аккаунт покрывает всё (см. JSDoc `zonesQuery`), `staleTime`
  60с; запрашивать зоны отдельно на каждый домен не нужно и нельзя.
- Запись результата: `PUT /domains/{id}` (`useUpdateDomain`) принимает и
  `cloudflare_account_id`, и `cloudflare_zone_id`. Роут `bulk-assign-cloudflare`
  проставляет ТОЛЬКО account_id, zone_id ему неизвестен, — для нашей задачи
  он не годится.
- Создание домена идёт по HTTP: `useCreateDomain` (`POST /domains`),
  `useBulkCreateDomains` (`/domains/bulk`), `useBulkCreateStructuredDomains`
  (`/domains/bulk-structured`), плюс `bulkImportDomains` (файловый импорт).
  Все возвращают созданные строки (`created: Domain[]`), кроме файлового
  импорта, который отдаёт только счётчики.

**Решение по UX (пользователь, 2026-08-11):** молча при создании + кнопка
«Match Cloudflare zones» для уже существующих доменов.

## Acceptance criteria

- [x] После добавления домена (Add Domain / Bulk Add) в **десктопе**, если имя
      домена точно совпадает с именем зоны в одном из подключённых активных
      CF-аккаунтов, домену проставляются `cloudflare_account_id` и
      `cloudflare_zone_id`; пользователь видит тост «Cloudflare: привязано N».
      **Отклонение (сознательное, см. Итог):** сообщение — не тост воркспейса, а
      баннер страницы, и текст английский («Cloudflare: 1 of 1 linked.») по
      языку соседних сообщений этого экрана.
- [x] Перезаписи не происходит: трогаем только домены, у которых
      `cloudflare_account_id` пуст.
- [x] Совпадение в ДВУХ аккаунтах — не привязываем ни к одному, домен попадает
      в отчёт как неоднозначный. Угадывать за пользователя, в каком аккаунте
      живёт его зона, нельзя.
- [x] В вебе (не Tauri) создание домена работает ровно как раньше: зон нет,
      автопривязки нет, ошибок и лишних запросов тоже нет.
- [x] Есть массовое действие «Match Cloudflare zones» по выделенным доменам
      (десктоп): показывает итог — сколько привязано, сколько без совпадения,
      сколько неоднозначно, сколько не удалось записать.
- [x] Логика матчинга — чистая функция с юнит-тестом; в ней нет ни сети, ни
      React.
- [x] `npx tsc --noEmit` и `npm test` во `frontend` зелёные.

## Edge cases

- **CF-аккаунтов нет / нет активных** — ничего не делаем, тост не показываем.
  **Уточнено при реализации:** правило оставлено как есть для автопривязки
  (после каждого заведённого домена «Cloudflare: аккаунтов нет» — это шум тому,
  кто Cloudflare не пользуется), но по кнопке «Match Cloudflare zones»
  сообщение показывается: кнопку нажали руками, и молчащая кнопка неотличима
  от сломанной. Разводит эти два случая `mode` в `summarizeCfBind`, у обоих
  есть тест.
- **`cf_list_zones` упал на одном из аккаунтов** — это НЕ «совпадений нет».
  Аккаунт, зоны которого прочитать не удалось, исключается из решения об
  однозначности, а пользователю сообщается, что часть аккаунтов не опрошена.
  Иначе «не нашли» врёт про домен, зона которого лежит в непрочитанном аккаунте.
- **Регистр** — сравнение регистронезависимое; в Cloudflare имена зон в нижнем
  регистре, ввод пользователя — какой угодно.
- **Точка в конце** (`example.com.`) и пробелы — нормализовать перед сравнением.
- **Поддомен** (`shop.example.com` при зоне `example.com`) — в этом плане
  **не привязываем**: осознанное сужение. Зона родительская, а `zone_id` в
  строке домена сегодня читается как «зона этого домена» (см. `useZoneNameservers`
  и вкладку NS, которая пушит NS этой зоны регистратору). Привязка поддомена к
  родительской зоне заставила бы NS-путь врать. Отдельная задача, если понадобится.
- **Сотни доменов** — зоны читаются ОДИН раз на аккаунт на весь прогон;
  сопоставление локальное. Запись — `PUT` на каждый привязанный домен, с
  ограниченной конкурентностью (не `Promise.all` на 200 запросов сразу).
- **Провал записи по части доменов** — прогон не останавливается, отчёт
  различает «нет совпадения», «неоднозначно» и «не удалось записать».
- **Гонка с инвалидацией** — по завершении один `invalidateQueries` на
  `domainsKeys.all`, а не по одному на домен.
- Zero-knowledge: имена зон и id — не секреты; API-токен CF в этом пути не
  покидает десктоп (его читает сама команда `cf_list_zones`).

## Фазы

### Фаза 1 — Чистая функция матчинга + тест  `[x]`

Новый модуль `frontend/src/lib/cfZoneMatch.ts`:

- Нормализация имени (trim, нижний регистр, срез завершающей точки).
- `matchDomainsToZones(domains, zonesByAccount)` → для каждого домена один из
  исходов: `matched {accountId, zoneId}` / `none` / `ambiguous {accountIds}` /
  `skipped` (у домена уже есть `cloudflare_account_id`).
- Никакой сети, никакого React — только данные.
- Тест `frontend/src/lib/cfZoneMatch.test.ts`: точное совпадение, разный
  регистр, точка в конце, совпадение в двух аккаунтах, домен уже привязан,
  поддомен (ожидаем `none` — это зафиксированное решение, а не недосмотр),
  пустой список зон.

### Фаза 2 — Исполнитель привязки (десктоп)  `[x]`

Новый модуль `frontend/src/api/cfAutoBind.ts` (или функция в `api/cloudflare.ts`
— на усмотрение исполнителя, но вне React-компонента):

- `autoBindDomainsToCloudflare(domains, opts)`:
  1. `isTauri()` — иначе сразу пустой отчёт, без походов.
  2. Список активных CF-аккаунтов (из кэша запросов, если он свеж; иначе
     обычный запрос).
  3. `cf_list_zones` на каждый аккаунт, ошибки не роняют прогон, а помечают
     аккаунт как непрочитанный.
  4. `matchDomainsToZones` из фазы 1.
  5. `PUT /domains/{id}` на каждый `matched` — с ограниченной конкурентностью.
  6. Один `invalidateQueries({ queryKey: domainsKeys.all })` в конце.
- Возвращает отчёт: `bound[]`, `none[]`, `ambiguous[]`, `writeFailed[]`,
  `unreadAccounts[]`.
- Функция построения текста итога — отдельная чистая функция с тестом
  (по образцу `summarizeBulkProvision` в `api/domains.ts`): текст уезжает
  пользователю, и его надо проверять без DOM.

### Фаза 3 — Автопривязка при создании  `[x]`

Файл: `frontend/src/pages/Domains.tsx` (`AddDomainModal` и `handleBulkAdd`).

- После успешного создания (`useCreateDomain`) и после успешного bulk-создания
  (обе ветки `handleBulkAdd` — text и csv) вызвать `autoBindDomainsToCloudflare`
  на созданных строках (`result.created`).
- Молча — значит без диалога, но НЕ без следа: короткий тост
  «Cloudflare: привязано N из M» (и упоминание неоднозначных, если они есть).
  Действие, изменившее данные без спроса, обязано о себе сказать.
- Провал автопривязки не должен рушить создание домена: домен уже создан, это
  главный результат; ошибка привязки — отдельная строка сообщения.
- В вебе шаг не выполняется вовсе (гейт `isTauri()` внутри исполнителя).
- Файловый импорт (`DomainBulkImportDialog`) не подключаем: его ответ не
  содержит созданных строк, только счётчики. Для него работает кнопка из фазы 4.

## Итог

**Реализован целиком (фазы 1–5).** `npx tsc --noEmit` чист; `npm test` — 72
файла / 723 теста, зелено и в дефолтной зоне, и под `TZ=America/New_York`
(база ветки была 69 / 685).

Что появилось:

- `frontend/src/lib/cfZoneMatch.ts` (+ тест, 10 кейсов) — правило «какая зона
  принадлежит домену»: нормализация имени и четыре исхода
  (`matched`/`none`/`ambiguous`/`skipped`). Ни сети, ни React.
- `frontend/src/api/cfAutoBind.ts` (+ тест, 15 кейсов) — прогон:
  `isTauri()` → активные аккаунты (`fetchQuery`, кэш) → `cf_list_zones` на
  аккаунт → матчинг → `PUT /domains/{id}` с конкурентностью 4 → одна
  `invalidateQueries`. Плюс чистая `summarizeCfBind` (текст итога + тон).
- Автопривязка в `AddDomainModal` (через новый проп `onCreated`) и в обеих
  ветках `handleBulkAdd`; кнопка «Match Cloudflare zones» в
  `BulkActionToolbar` (только десктоп) — `frontend/src/pages/Domains.cfbind.test.tsx`,
  13 кейсов.

Решения, которые стоит помнить:

- **Основная поверхность отчёта — баннер страницы, запасная — тост
  воркспейса.** Пропы у provision существуют потому, что тот несёт пароли,
  которых нет больше нигде. У привязки секретов в отчёте нет, повтор
  идемпотентен (уже привязанные домены пропускаются), а итог называет домены
  ЭТОГО списка — показывать его поверх страницы серверов не о чем. Плюс тост
  живёт 2200 мс (`DesktopWorkspace.tsx`), а в итоге до пяти чисел и оговорка
  про непрочитанные аккаунты — та часть, которую пропустить нельзя. Баннер
  стоит там же, где страница уже показывает исход массового действия
  (`bulkProvisionError`), и тон у него тот же, что у тостов: `role="status"`
  на чистом успехе, `role="alert"` + «⚠» на полууспехе.
  **Исправлено по ревью:** первая версия на этом и останавливалась, и отчёт
  размонтированной страницы пропадал совсем. Довод «прогон секундный» верен
  для одного домена и неверен для пачки: на двухстах доменах это
  последовательная вычитка зон каждого аккаунта (пагинация, `retry: 1`) плюс
  двести `PUT` по четыре за раз — десятки секунд, за которые уйти со страницы
  обычное дело. Теперь работает та же развилка, что у `onBulkProvisionError`:
  жива страница — баннер, нет её — тост (`showToast` / `showWarning` по тону,
  четвёртого вида тоста не заведено). Проп `onCloudflareBindNotice`
  обязательный — забытый означал бы бесследную правку данных, которой никто не
  просил. Есть тест.
- **Прежний итог гасится в начале прогона, а не по приходу нового.** У нового
  итога его может не быть вовсе (в `auto` прогон без аккаунтов и прогон, где
  привязывать нечего, молчат), и старая строка оставалась стоять, читаясь как
  отчёт о последнем действии. Есть тест.
- **Язык сообщения — английский.** Критерий выше цитировал русский текст, но
  всё, рядом с чем эта строка встаёт, по-английски: `summarizeBulkProvision`,
  баннер отказа массового прогона, тосты воркспейса — то есть обе поверхности,
  на которые итог приходит. Экран при этом двуязычен, и это не аргумент «за»:
  русские строки на нём есть (ошибки Bulk Add, подписи модалок массового
  назначения) — они наследство, а не образец, и все новые строки этой ветки
  английские.
- **Гейт «один прогон за раз» — только у кнопки.** Автопривязка не гейтится:
  домен, заведённый во время прогона по кнопке, иначе молча остался бы без
  зоны — то есть стал бы ровно тем «доменом, которому нечем прописать NS»,
  ради которого функция и сделана. Параллельные прогоны безопасны (зоны делят
  одну запись кэша, `PUT` идемпотентен). Есть тест.
- **`useZoneDetails` потребителя так и не получил, долг остаётся открытым.**
  Планы №1 и №2 записывали его естественным потребителем именно эту задачу —
  не сошлось по существу: привязка ищет зону по ИМЕНИ по всему списку сразу и
  работает вне React, а `useZoneDetails` — хук, выбирающий ОДНУ зону по уже
  известному `zoneId`. Ей нужен ровно тот список, поверх которого он сделан,
  поэтому она берёт `zonesQuery` напрямую (тот для этого экспортирован).
  Комментарий в `api/cloudflare.ts`, обещавший этот план потребителем,
  исправлен.

Долг и осознанные сужения:

- **Поддомен не привязывается к родительской зоне** (`shop.example.com` при
  зоне `example.com` → `none`). Зафиксировано планом: `cloudflare_zone_id`
  читается фронтом как «зона ЭТОГО домена», и вкладка NS пушит регистратору её
  nameservers. Отдельная задача, если понадобится.
- **Домен с аккаунтом, но без `zone_id`, не трогается вовсе.** Признак
  «пропустить» — именно аккаунт. Дописать такому домену зону — другое правило
  (аккаунт задан, неоднозначности нет, искать надо только в нём), и его никто
  не заказывал. Отдельная задача.
- **Файловый импорт (`DomainBulkImportDialog`) не подключён** — его ответ
  содержит только счётчики, созданных строк в нём нет. Для него работает
  кнопка тулбара; это ровно тот сценарий, ради которого она и сделана.
- **`cloudflare_enabled` привязка не трогает.** Она проставляет аккаунт и зону
  — то, чего не хватало NS-пути; смысл флага «включён ли Cloudflare для
  домена» — отдельное решение продукта.
- **`Domains.tsx` вырос до 1210 строк** (было 1077). Новая логика вынесена в
  модули (`lib/cfZoneMatch`, `api/cfAutoBind`), в странице остались вызов,
  баннер и стейт, но разбор God-компонента (план №4) от этого не легче.
