# План: стабильная подпись release-бандла — связка ключей перестаёт спрашивать пароль

**Дата:** 2026-08-06
**Связь с бизнесом:** каждая операция с секретом читает мастер-ключ из связки ключей.
Пока личность приложения нестабильна, macOS спрашивает пароль на каждое чтение — на
рабочем экране это десятки окон подряд. Продукт, который продаётся как «пульт управления
инфраструктурой», в таком виде непригоден к работе, хотя технически исправен.

## Зачем

Пользователь получает поток системных запросов «связка ключей хочет использовать
конфиденциальную информацию». Причина сверена по коду:

1. Собранный `.app` подписан ad-hoc:
   `CodeDirectory ... flags=0x20002(adhoc,linker-signed)`, `Signature=adhoc`,
   `TeamIdentifier=not set`. В ACL элемента связки программа опознаётся по подписи,
   а у ad-hoc подписи роль личности играет CDHash — хеш кода. Пересборка меняет хеш →
   для macOS это другая программа → вопрос возвращается, а «Always Allow» бесполезен.
2. `keychain::load_master_key` зовётся из 13 мест (`commands/vault.rs:15`,
   `commands/cloudflare.rs:44`, `commands/registrars.rs:26`, трижды в
   `commands/provision.rs`, `sync/client.rs:19` и др.) — ключ не кэшируется в памяти,
   каждая команда идёт в связку заново. Пока личность не внесена в ACL, это отдельный
   диалог на каждую операцию.

Механизм лечения в проекте уже описан и реализован — `desktop/dev-signing.sh` заводит
самоподписанный сертификат «SDMP Dev Signing» и подписывает им бинарник, чтобы личностью
стал сертификат, а не хеш кода. Но скрипт подписывает только `target/debug/sdmp-desktop`;
release-бандл, который отдаёт `build-dmg.sh`, остаётся ad-hoc. Сертификата на машине
сейчас нет вовсе: `security find-identity -v -p codesigning` → `0 valid identities found`.

**Объём этой работы (по решению пользователя): только подпись.** Кэш мастер-ключа в
памяти — отдельная задача (см. «Отложено»).

## Что делаем

Tauri CLI умеет брать личность из окружения — в бинаре CLI есть и
`APPLE_SIGNING_IDENTITY`, и конфиг `bundle.macOS.signingIdentity`. Значит подписывать
бандл руками после сборки не нужно (и нельзя: `.dmg` собирается из `.app` в том же
прогоне, подпись «после» не попала бы внутрь образа).

`build-dmg.sh` перед сборкой проверяет, есть ли в связке личность «SDMP Dev Signing»:

- есть → экспортирует `APPLE_SIGNING_IDENTITY` — Tauri подписывает `.app` до упаковки
  `.dmg`, личность стабильна между пересборками;
- нет → собирает как раньше (ad-hoc, сборка не ломается) и печатает подсказку про
  разовый `./desktop/dev-signing.sh setup`;
- если `APPLE_SIGNING_IDENTITY` уже задана снаружи — не перетирать.

`setup` требует подтверждения в системном окне, поэтому запускает его пользователь сам,
один раз. После первого запуска подписанного приложения связка спросит последний раз —
«Always Allow».

## Acceptance criteria

- [x] Без сертификата: `./desktop/scripts/build-dmg.sh` собирает как прежде, exit 0,
      печатает понятную подсказку про `dev-signing.sh setup`.
- [x] С сертификатом: в `tauri build` уходит `APPLE_SIGNING_IDENTITY="SDMP Dev Signing"`
      (проверено заглушками `security`/`npm` — сертификата на машине ещё нет).
- [x] Уже заданная снаружи `APPLE_SIGNING_IDENTITY` не перетирается.
- [ ] `codesign -dv` на собранном `.app` показывает `Authority=SDMP Dev Signing`
      вместо `Signature=adhoc` — ждёт `dev-signing.sh setup` от пользователя.
- [ ] Две пересборки подряд дают одну и ту же личность — там же.
- [x] `docs/BUILD.md` объясняет разовый шаг и почему связка спрашивала.

## Edge cases

- Сертификата нет / удалён → сборка не падает, только подсказка.
- Личность есть, но `codesign` не может добраться до приватного ключа → падает
  `tauri build`; сообщение должно указывать на `./desktop/dev-signing.sh status`.
- Идентификатор бандла обязан совпадать с тем, что в ACL: `com.sdmp.desktop`
  и в `tauri.conf.json:5`, и в `dev-signing.sh:46`. Разойдутся — вопрос вернётся.
- Zero-knowledge: `security -A` (открыть элемент всем программам) применять нельзя —
  это отменяет обещание продукта; запрет уже зафиксирован в шапке `dev-signing.sh`.

## Фазы

### Фаза 1 — `build-dmg.sh` передаёт личность  `[x]`

- Определение личности, экспорт `APPLE_SIGNING_IDENTITY`, подсказка при отсутствии.
- Файлы: `desktop/scripts/build-dmg.sh` (коммит `f824099`).

### Фаза 2 — документация  `[x]`

- Раздел в `docs/BUILD.md`: почему связка спрашивала, разовый `dev-signing.sh setup`,
  что дальше сборки подписываются сами.
- Файлы: `docs/BUILD.md` (коммит `f824099`).

### Фаза 3 — проверка на этой машине  `[ ]` — ждёт действия пользователя

- Пользователь выполняет `./desktop/dev-signing.sh setup` (нужен ввод в системном окне).
- Пересборка → `codesign -dv` показывает `Authority=SDMP Dev Signing`.
- Запуск, один раз «Always Allow», пересборка → окно больше не появляется.

**Проверено 2026-08-06 14:02** (пересборка после правки фронта): `security find-identity -v
-p codesigning` → `0 valid identities found`, `codesign -dv` на собранном `.app` →
`Signature=adhoc`, `TeamIdentifier=not set`. То есть фолбэк фазы 1 отработал ровно как
задумано (сборка не упала, exit 0), а сама фаза 3 по-прежнему упирается в `setup`,
которого никто не выполнял. Пока он не выполнен, каждая сборка получает **новую** adhoc-личность
— то есть ровно та проблема с повторными вопросами связки, ради которой план и заводился,
воспроизводится при каждой пересборке.

## Итог

- **Реализован частично — код готов, ждёт одного действия человека.** Фазы 1–2 сделаны
  и проверены (без сертификата сборка не ломается и подсказывает; с сертификатом
  переменная уходит в `tauri build` — проверено заглушками; внешняя личность не
  перетирается). Фаза 3 не закрыта: `dev-signing.sh setup` требует подтверждения в
  системном окне, автоматикой его не выполнить.
- **Отложено:** кэш мастер-ключа в памяти на сессию (Tauri managed state + zeroize при
  блокировке и выходе) — снимает диалоги ещё до выдачи ACL и убирает 13 чтений связки
  на каждый экран. Нужен отдельный план.
- **Отложено (Stage 5):** настоящая подпись Developer ID + нотаризация — это про
  скачанный `.dmg` и Gatekeeper, а не про связку ключей.
