# Бэкапы домена: вкладка Backup + чтение и создание через FastPanel/SSH


## Контекст

В карточке домена (`DomainDetailModal`) сегодня пять вкладок, и бэкапов среди них нет
вовсе. Есть статичная заглушка `SectionCard "Backups"` + `Badge COMING SOON` внутри
вкладки **Server** — [DomainServerTab.tsx:157-173](frontend/src/components/domains/tabs/DomainServerTab.tsx#L157).
Ноль пропсов, ноль запросов, ноль Tauri-команд. За ней в продукте не стоит ничего: ни
модели на бэкенде, ни колонки у домена, ни поля в снимке `fp_facts`, ни единого вызова
чего-либо связанного с бэкапами в Rust (`mysqldump`/`tar`/`restore` не встречаются нигде;
`.bak` есть только у nginx-сниппета в `apply_nginx_override`).

План 18.08 поставил эту заглушку осознанно (отступление №1: «селекты Frequency/Destination,
которые ничего не сохраняют, — это обещание настройки, которой нет»), но условий её снятия
не записал. Настоящий план их выполняет.

**Что решено с пользователем:**
- Отдельная вкладка **Backup**: показывать существующие копии + кнопка «сделать бэкап сейчас».
- Разведка FastPanel CLI на живом сервере под root — **можно**.
- Куда девать архив: в первой версии — **скачивание на машину пользователя**. Внешнее
  хранилище (S3/FTP) нужно позже — архитектура обязана оставить для него место, но не
  реализовывать его сейчас.

**Что известно про источник данных (проверено по `docs/FASTPANEL_CLI.md`, снят живым
прогоном 2026-08-16):**
- `sites list --json` — команда, которую мы **уже гоняем** при `domain_read_facts`, —
  содержит поле `"backups":[]` ([FASTPANEL_CLI.md:69](docs/FASTPANEL_CLI.md#L69)). На живом
  сервере массив был **пуст**, поэтому форма непустого элемента неизвестна.
- Команда `backup:plan` существует и доступна даже непривилегированному пользователю панели
  ([FASTPANEL_CLI.md:23](docs/FASTPANEL_CLI.md#L23)) — но её **ни разу не звали**: ни
  `--help`, ни `list`, ни `--json`. Форма вывода и коды возврата неизвестны.
- Каталог, куда панель кладёт архивы, не разведан.

Отсюда главный принцип фазировки: **разведка блокирует ЧТЕНИЕ чужих бэкапов, но не блокирует
создание своих.** `tar` и `mysqldump` — инструменты с известной формой, их разведывать не надо.

---

## Ключевые решения

### 1. Собственный архив, а не `backup:plan`

Создание бэкапа делаем сами: `tar` каталога сайта + `mysqldump` каждой БД домена + манифест,
всё это одним `.tar`. Причина: у `backup:plan` неизвестны форма вывода, коды возврата и место
складирования — мы не сможем ни проверить целостность, ни забрать файл, ни убрать за собой.
`backup:plan` остаётся источником **чтения** и кандидатом на будущую фазу.

Следствие, которое обязано быть видно на экране: **наш архив не появится в списке копий
панели**. Это два разных предмета с разным происхождением, и смешивать их в одном списке
нельзя.

### 2. Транспорт: новый `exec_to_writer`, а не `russh-sftp`

`SshSession::exec` для бинарного гигабайта непригоден трижды
([client.rs:204-235](desktop/src-tauri/src/ssh/client.rs#L204)):
- копит всё в `Vec<u8>` и делает `String::from_utf8_lossy` — каждый невалидный UTF-8 стал бы
  U+FFFD, то есть архив был бы испорчен целиком;
- **сливает stdout и stderr в один буфер** — одно предупреждение `tar` вклеилось бы в середину файла;
- дедлайн **суммарный** (`deadline = now + timeout`), а не по бездействию — здоровая
  многоминутная выгрузка обрывалась бы на середине.

Берём вариант A (`exec_to_writer`), а не SFTP-крейт, потому что:
- SFTP закрывает один шаг из тринадцати — `tar`, `mysqldump`, `sha256sum`, замок, `rm -rf`
  всё равно идут через `exec`;
- исторический баг с `Eof`/`exit-status` уже оплачен именно в exec-цикле
  ([client.rs:214-228](desktop/src-tauri/src/ssh/client.rs#L214), план 2026-08-06) — новый
  цикл наследует это знание, SFTP-путь заводил бы свой набор граблей, не покрытый нашими тестами;
- ноль новых зависимостей.

### 3. Keepalive — сквозная правка, которую надо назвать вслух

`russh::client::Config` создаётся сегодня только с `inactivity_timeout`; keepalive выключен.
Молчащий получасовой `tar` не шлёт ни байта, и единственный способ его пережить без keepalive
— раздуть inactivity до часов, то есть перестать замечать оборванную связь вовсе.
Включаем `keepalive_interval: Some(30s)`, `keepalive_max: 3`.

**Это меняет поведение ВСЕХ SSH-операций продукта.** В лучшую сторону (мёртвый сервер
опознаётся за ~2 минуты вместо 600 секунд, а 300-секундный молчаливый `certificates create-le`
перестаёт жить на честном слове), но это изменение, и оно должно приниматься сознательно.

### 4. Незнание называется словом (принцип №6)

`backups` в `DomainFacts` — **не** `Vec<BackupEntry>`. Пустой список означал бы «бэкапов нет»
— утверждение, которого мы сделать не можем. Структура несёт явное состояние:

```rust
pub struct BackupsFacts {
    pub state: BackupsState,          // Known | Unknown
    pub entries: Vec<BackupEntry>,
    pub probed: Vec<&'static str>,    // где смотрели — иначе «не знаем» ≡ «не пробовали»
}
```

На фронте это даёт **четыре** различимых состояния, а не два:

| На проводе                      | Что значит                          | Что на экране                                     |
| ------------------------------- | ----------------------------------- | ------------------------------------------------- |
| поля `backups` нет вовсе        | снимок снят сборкой до этой функции | «снимок старый, пересними» + кнопка               |
| `state: "unknown"`              | панель ответила, разобрать не вышло | «не смогли прочитать список» — **не** «копий нет» |
| `state: "known"`, `entries: []` | панель ответила, копий нет          | «FastPanel копий не показывает»                   |
| `state: "known"`, есть записи   | список                              | список                                            |

Пока разведка не показала непустой `sites[].backups[]`, пустой массив трактуется как
`Unknown`. Это зашито константой `SITE_BACKUPS_FIELD_TRUSTED: bool = false` с расписанным
смыслом — переключать только вместе со ссылкой на раздел `docs/FASTPANEL_CLI.md`, где форма
зафиксирована.

### 5. Диалог — панель сохранения, не выбор папки

`dialog:allow-save` (а не `allow-open` с `directory:true`): человек должен видеть и править
имя файла, а `allow-open` открыл бы вебвью ещё и чтение произвольных путей, которого задача не
требует. Команда принимает **полный путь файла** (`destPath`), не каталог.

## Фазы

### Фаза 0 — разведка `[ ]` · БЛОКИРУЕТ фазы 3 и 8

**Предусловие P0:** на разведываемом сервере должен быть **хотя бы один сделанный бэкап**
(через веб-морду FastPanel, руками). Без него форма непустого `sites[].backups[]` не снимется
— скрипт этого добыть не может по построению.

Новые read-only секции в [scripts/fastpanel-discovery.sh](scripts/fastpanel-discovery.sh),
в стиле существующих (`run`/`run_sh`/`fp`/`skip_section`, маркеры `#sdmp:*`):

- **CLI**: `backup:plan --help`, `backup:plan list --json`, `backup:plan list`, плюс
  `backup --help` и `backups --help` — прецедент `database` vs `databases`
  ([FASTPANEL_CLI.md:203](docs/FASTPANEL_CLI.md#L203)) уже стоил бага в провижининге; две
  лишние строки дешевле повторного захода на продакшн.
- **Раскладка на диске**: `find` по `/var/www/<owner>/data`, `/var/backups`,
  `/var/lib/fastpanel2`, `/mnt`, `/backup` — каждое место своей секцией («каталога нет» и
  «каталог пуст» — разные ответы). Файлы через `find -printf '%p\t%s\t%TY-…'` (машинный
  формат вместо зависящего от локали `ls -l`).
- **Расписание**: `systemctl list-timers`, `ls /etc/cron.d`. **`crontab -l` НЕ зовём** — в
  cron-строке панели может стоять `mysqldump -p<пароль>`, а шапка скрипта обещает, что
  паролей мы не собираем.
- **Внутренняя БД панели**: `SHOW TABLES | grep -i backup`, `DESCRIBE`, `SELECT COUNT(*)`.
  ⚠️ **`SELECT *` запрещён**: в строках таблицы бэкапов лежат учётки внешних хранилищ.
  Побочный и важный результат секции — работает ли `mysql` под root **без пароля через
  сокет** (от этого зависит вся схема `mysqldump` в фазе 2).
- **Инструменты**: `command -v` для `tar gzip mysqldump sha256sum du df nice ionice install`,
  `tar --version` (GNU vs busybox меняет схему кодов возврата), `df -Pk /var/tmp`.

**Итог фазы:** новый раздел «9. Бэкапы» в `docs/FASTPANEL_CLI.md` с формами вывода и кодами
возврата, обезличенный по правилам файла.

### Фаза 1 — `exec_to_writer` + keepalive `[x]` · не блокируется разведкой

[desktop/src-tauri/src/ssh/client.rs](desktop/src-tauri/src/ssh/client.rs):

```rust
pub struct ExecStream { pub exit: i32, pub bytes: u64, pub stderr: String, pub signal: Option<String> }

pub async fn exec_to_writer<W, F>(&mut self, cmd: &str, idle_timeout: Duration,
                                  out: &mut W, on_progress: F) -> Result<ExecStream, SshError>
where W: tokio::io::AsyncWrite + Unpin + Send,
      F: FnMut(u64) -> std::ops::ControlFlow<()> + Send;
```

- stdout → writer как есть (никакого `from_utf8_lossy`), stderr → отдельный буфер с потолком
  `STREAM_STDERR_CAP = 8 KiB`;
- дедлайн сдвигается на **каждом** принятом сообщении — ловит замолчавший канал, а не
  длительность команды;
- `pty` не параметр: всегда false и не может быть иначе — псевдотерминал переводит `\n` в
  `\r\n`, то есть тихо портит каждый байт 0x0A;
- разбор `Eof`/`ExitStatus`/`Close` наследуется построчно вместе с комментарием из `exec`;
- `ChannelMsg::ExitSignal` → `signal` (OOM-killer на гигабайтном `tar` выглядит именно так, и
  без этого поля такой конец неотличим от «код не доехал»);
- новый вариант `SshError::Cancelled` — отмена не сбой, и в аудите/UI обязана выглядеть иначе,
  чем оборванная связь;
- `KEEPALIVE_INTERVAL = 30s`, `KEEPALIVE_MAX = 3` в `connect()` (решение 3).

**Сделано.** Всё перечисленное — в `ssh/client.rs`: `ExecStream`, `exec_to_writer` (дедлайн
пересчитывается на каждом витке цикла), `CappedStderr` с потолком 8 KiB, `SshError::Cancelled`,
`ExitSignal → signal`, keepalive в `connect`. Юниты: потолок stderr (сохраняется начало, потеря
названа), тексты `Cancelled` и `Disconnected`, связь `KEEPALIVE_BUDGET` с интервалом и квотой.
Шесть интеграционных тестов из раздела «Проверка» написаны и **прогнаны на живом докере**
(`lscr.io/linuxserver/openssh-server`, 8 passed вместе с двумя старыми).

**Правка сверх спеки, найденная ревью (обязательная).** Исходов у выгрузки не два, а **три**, и
третий чуть не остался невидимым. Смерть сессии — по `inactivity_timeout` или по keepalive —
приходит в `exec_to_writer` тем же концом потока сообщений, что и нормальное завершение:
`Session::run` падает, отправитель канала исчезает, `Channel::wait()` отдаёт `None`. Первая
редакция выходила по нему из цикла молча и возвращала `Ok(ExecStream { exit: -1 })` — то есть
оборванный на середине гигабайтный архив приезжал как штатно закрытый поток. Теперь нормальным
концом считается только тот, при котором доехал ИТОГ команды (`exit-status` или сигнал), а
`None` без итога — `SshError::Disconnected { bytes }`, где число байт значит «размер потери», а
не «сколько сделано». Заодно выяснилось, что ветка `ChannelMsg::Close` на russh 0.45 мертва:
приняв `CHANNEL_CLOSE`, russh выкидывает канал из карты, не переслав `Close` наружу, — ветка
оставлена страховкой и названа таковой в комментарии.

**Отступления, принятые в фазе 1:**

1. *Инвариант таймаутов оказался не универсальным.* Проверка «`KEEPALIVE_INTERVAL ×
   (KEEPALIVE_MAX+1)` (= 120 с) < каждый session timeout» проходит для `FACTS_SESSION_TIMEOUT`
   (600), `PROVISION_SESSION_TIMEOUT` (420) и `FP_SESSION_TIMEOUT` (300), но НЕ для
   `LIST_SITES_SESSION_TIMEOUT` (60) и таймаута кнопки «SSH Test» (45). Поднимать их не стали:
   обоим нужна быстрая реакция на мёртвый сервер, а полный бюджет удлинил бы её вдвое-втрое.
   Разбор кода russh 0.45 (`client/mod.rs:885-970`) показывает, что для корректности хватает
   более слабого условия: inactivity сбрасывается ЛЮБЫМИ принятыми данными, в том числе ответом
   на keepalive, — значит живая молчаливая сессия не умирает при любом `session_timeout >
   KEEPALIVE_INTERVAL`, а полный бюджет даёт лишь запас на пропущенные ответы. Поэтому тестов
   два вида: полный бюджет — у трёх долгих сессий, «успеть спросить и получить ответ хотя бы
   раз» — у двух коротких, с комментарием почему.
2. *Литерал `Duration::from_secs(45)` в `ssh_exec` получил имя* `SSH_TEST_SESSION_TIMEOUT` —
   иначе самый короткий session timeout продукта нечем было закрепить тестом.
3. *Ради теста keepalive добавлена `connect_with_keepalive_override`* (продуктовый путь —
   по-прежнему `connect`). Плановые «inactivity 5 s + sleep 12 s» с продуктовым интервалом 30 с
   недостижимы: keepalive не успел бы прозвучать ни разу. Функция позволяет тесту взять
   интервал 2 с и получить честную пару «без keepalive умирает / с ним доходит», а сами
   продуктовые 30 с закреплены юнит-тестами соотношений.

### Фаза 2 — создание бэкапа, ядро `[x]` · не блокируется разведкой

Новый `desktop/src-tauri/src/ssh/backup_run.rs` (зеркалит существующее разделение:
`fastpanel.rs` создаёт, `fastpanel_facts.rs` читает).

Шаги, все через `q()` из `fastpanel.rs`, `pty:false`:

| Шаг                   | Команда                                                                                                                          | Таймаут |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------- |
| `resolve`             | `sites list --json` → `index_dir`; `databases list --json` → БД по `site.domain`                                                 | 60s     |
| `preflight`           | `command -v tar gzip mysqldump sha256sum du df`                                                                                  | 60s     |
| `space`               | `du -sk <site_path>`, `df -Pk /var/tmp` — нужно ≥ 1.2× оценки                                                                    | 60s     |
| `lock`                | `mkdir -m 700 /var/tmp/sdmp-backup/<domain>`                                                                                     | 60s     |
| `archive_files`       | `set -o pipefail; nice -n 19 ionice -c3 tar --warning=no-file-changed -cf - -C <parent> <base> \| gzip -1 > <work>/site.tar.gz`  | 3600s   |
| `dump_db` (на каждую) | `set -o pipefail; mysqldump --single-transaction --quick --routines --triggers --events <db> \| gzip -1 > <work>/db-<db>.sql.gz` | 3600s   |
| `manifest` + `pack`   | манифест JSON, затем `tar -cf <archive> -C <work> manifest.json site.tar.gz db-*.sql.gz` (имена перечислены явно, без glob)      | 3600s   |
| `checksum`            | `sha256sum <archive>`, `stat -c %s`                                                                                              | 60s     |
| `cleanup`             | `rm -rf <work>`                                                                                                                  | 60s     |

Решения, которые обязаны быть защищены комментарием в коде:

- **Рабочий каталог `/var/tmp/sdmp-backup/`, не под `site_path`.** Архив под document root
  скачивается по HTTP кем угодно, пока лежит там, и попадает внутрь следующего `tar` самого
  себя. Это дыра, а не стилистика.
- **Замок — каталог.** `mkdir` на POSIX атомарен, `test -f && touch` — нет. Просроченный
  замок **не сносим автоматически**: отдельная действенная ошибка с путём. Автоснос убил бы
  чужой идущий бэкап.
- **Пароль БД в argv не ставим никогда.** `mysqldump -p<пароль>` виден в `ps` всем
  пользователям сервера на всё время дампа — это хуже, чем разовое эхо argv у FastPanel
  ([FASTPANEL_CLI.md §7](docs/FASTPANEL_CLI.md#L388)), потому что длится минуты. Идём через
  root-сокет, тем же способом, каким уже работает `list_site_databases`. Не сработало —
  **честный отказ**, а не тихий фоллбэк на пароль в argv. `db_password_blob_id` в первой
  версии не расшифровываем вовсе.
- **`gzip -1`, `nice`, `ionice`** — продакшн обслуживает живой сайт.
- **Код `tar` 1 = «файлы менялись при чтении» → предупреждение, не отказ; ≥ 2 → отказ.**
- Идемпотентность трёхслойная: замок-каталог на сервере (переживает перезапуск десктопа,
  ловит второй десктоп) + `BackupRuns` в managed state Tauri + `runExclusive` во фронте.

Манифест `{"format":"sdmp-backup/1","domain":…,"created_at":…,"site_path":…,"databases":[…],
"parts":[{name,kind,sha256}],"tool":…}` — чтобы человек, открывший архив через полгода, понял,
что это и куда разворачивать, не заглядывая в SDMP.

**Сделано.** `desktop/src-tauri/src/ssh/backup_run.rs` (~2100 строк: ~1250 кода с
комментариями и ~850 тестов) —
чистое SSH-ядро без Tauri, keychain и событий: `create_backup(s, fp_path, domain, now)
-> Result<BackupArtifact, BackupError>`. Все девять шагов на месте и в порядке плана,
каждая интерполяция через `q()`, `pty: false` у всех (идут через `Exec::run`). Пять решений
из списка выше защищены комментариями в коде поимённо. `BackupArtifact` описывает архив
**на сервере** (`path`, `file_name`, `bytes`, `sha256`, `parts`, `databases`, `site_path`,
`created_at`, `warnings`) — место под второго адресата (S3/FTP) осталось ровно там, где
задумано: после `checksum`.

Тесты: **35 юнитов** в модуле (322 → 357 в `cargo test`, 0 failed) + **2 интеграционных**
на живом докере (8 → 10 passed). Покрыто: `q()` на всех интерполяциях (прогон целиком с
доменом `a b'c`), `pipefail` и `PIPESTATUS` в обоих конвейерах, коды `tar` 0/1/≥2 и 137,
граница 1.2× (ровно/чуть меньше/чуть больше), фильтр по домену не ловит `example.com.old`,
форма манифеста и попадание всех частей, замок (повторный `mkdir` отказывает; просроченный
даёт действенную ошибку с путём и `rm -rf`, и НИ ОДНОЙ команды удаления от нас), уборка на
всех путях выхода включая отказ на середине, отсутствие пароля в argv.

**Как решена неоднозначность `list_site_databases`** (главный вопрос фазы). Эта функция
схлопывает «баз нет» и «обе команды упали» в `Ok(vec![])`; для бэкапа это дало бы архив без
единой базы, который выглядит полным. Поэтому бэкап её **не зовёт**, а разбирает
`databases list --json` сам (`databases_for_backup`) по правилу `ftp_accounts_from_json`:
`Some(vec![])` только когда форма понята (массив пуст ИЛИ есть узнаваемые строки со
`site.domain`); ни одной узнаваемой строки, либо наша строка без `name`, либо не-JSON, либо
ненулевой код — `None` → отказ `BackupError::DatabasesUnknown`. mysql-фолбэка нет вовсе:
он фильтрует по префиксу имени, а на этой сборке имена БД захешированы (`skonloedb`), то есть
почти наверняка вернул бы пусто — «не знаем», выданное за «нет».

**Отступления фазы 2:**

1. *`command -v tar gzip mysqldump …` одной строкой не работает* — у bash `command -v` с
   несколькими именами печатает найденные и возвращает 0, даже если часть отсутствует
   (проверено), то есть плановая форма не умеет ответить «чего нет». Заменено циклом,
   печатающим `имя<TAB>OK|MISSING` (образец `build_log_stat_cmd`). Заодно `nice`/`ionice`
   объявлены НЕобязательными: их отсутствие — предупреждение и команда без префикса, а не
   отказ; `mysqldump` требуется, только если у домена есть базы.
2. *Кроме `pipefail` конвейеры печатают `${PIPESTATUS[*]}`.* Одного pipefail мало: он отдаёт
   код последнего упавшего звена, и «`tar` вернул 1» неотличимо от «`gzip` упал» — а это
   предупреждение против отказа с обрезанным архивом. Маркер `SDMP_RC` не доехал → отказ
   («не поняли исход»), а не молчаливый успех; это же честно закрывает случай не-bash логин-шелла.
3. *Замок и рабочий каталог — один каталог* (`/var/tmp/sdmp-backup/<домен>`), архив лежит
   рядом (`/var/tmp/sdmp-backup/<домен>-<штамп>.tar`). Снятие замка и уборка мусора обязаны
   быть одним действием; уборка на успехе архив не трогает, на отказе — сносит вместе с
   недоделанным архивом.
4. *Домен санируется в имя каталога* (`safe_component`): `q()` спасает от шелла, но не от
   смысла пути, а `..`/`/` в домене увели бы `mkdir`/`rm -rf` наружу. Есть и проверка пути
   сайта (`site_path_is_sane`): `/` или `/var/www` в `index_dir` означали бы «заархивируй
   пол-сервера».
5. *Свой тип ошибки `BackupError`,* а не `SshError::Session(String)`: половина исходов
   действенная («замок занят», «нет места», «не знаем баз»), и различать их по подстроке
   фазе 4 не придётся. `warnings` — `Vec<String>`, а не `Vec<&'static str>` из плана: текст
   предупреждения несёт цифры (какой код вернул `tar`, какого инструмента нет).
6. *Учтён факт из ревью фазы 1:* убитая команда через обычный `exec` (в отличие от
   `exec_to_writer`) приезжает не сигналом, а отсутствием `exit-status`, то есть кодом `-1`.
   Там, где код сверяется с нулём, `-1` попадает в отказ сам; там, где код игнорируется
   (`du` ненулевой на любом нечитаемом подкаталоге), `-1` проверяется отдельно
   (`ensure_exit_status_arrived`). OOM-killer на самом `tar` виден в `PIPESTATUS` как 137 и
   ловится общим правилом «≥ 2 — отказ». Оба случая под тестами.
7. *Расширена видимость шести элементов модуля* (`PIPE_STATUS_TAIL`, `parse_pipeline_status`,
   `build_lock_cmd`, `build_lock_probe_cmd`, `parse_lock_probe`, `build_cleanup_cmd`) с
   `pub(crate)` до `pub` — ради интеграционных тестов: они отдельный крейт. Чужие модули не
   тронуты вовсе.

**Интеграционных тестов ровно два, и это осознанно:** на голом openssh без FastPanel и mysql
доказуемы только две вещи, и обе — ключевые. `a_backup_lock_directory_cannot_be_taken_twice`
(второй `mkdir` действительно падает, `stat -c %Y`/`date +%s` разбираются, после уборки замок
берётся снова) и `the_pipeline_marker_survives_a_real_login_shell` (коды обоих звеньев
доезжают через настоящий exec-канал). Сам `tar --warning=no-file-changed` в докере не
гоняется намеренно: у busybox такого флага нет, и тест падал бы по причине, которой на
целевых серверах с GNU tar не существует.

**Правки по ревью (второй коммит фазы).** Ревью нашло восемь вещей; закрыты все, кроме
прогона clippy (правки внесены, проверить не успел — дерево пошло на слияние с master):

1. *Контрольные суммы получили часовой бюджет.* `sha256sum` частей и архива стояли под
   60-секундным `BACKUP_STEP_TIMEOUT`, хотя читают ровно те же гигабайты, что писал `tar`:
   сайт, ради которого выставлен час, гарантированно падал бы на последнем шаге — после часа
   работы и с уборкой, уносящей готовый архив. Соответствие «шаг → бюджет» теперь под тестом
   `every_step_gets_the_budget_its_work_needs` (раньше `FakeServer` таймаут выбрасывал, и
   мутация «все длинные шаги по 60 с» проходила зелёной).
2. *Оценка места названа тем, что она есть.* Комментарий обещал, что 1.2× «закрывает дампы
   баз»; для сайта «100 МБ файлов и база на 20 ГБ» это ложь на два порядка. Теперь сказано
   прямо: оценка — только `du` каталога сайта, размер баз в неё не входит, а настоящая защита
   от кончившегося диска — код возврата `gzip` в `PIPESTATUS`, делающий нехватку отказом на
   том шаге, где она случилась. Оценка осталась дешёвой ранней остановкой.
3. *Обязанность снести серверный архив названа вслух* — в доках `BackupArtifact` и `cleanup`:
   файл остаётся в `/var/tmp/sdmp-backup/` намеренно, удалить его обязан вызывающий после
   подтверждённой выгрузки (сошлись sha256 и размер). Сам модуль этого сделать не может — он
   не знает ни адресата, ни того, довезли ли файл. **Фазе 4 это делать обязательно:** иначе
   `/var/tmp` продакшна набивается тарболлами и роняет живые сайты.
4. *Сырой вывод сервера больше не уезжает в `warnings`.* Ошибка уборки — единственная, чей
   текст попадает в `Serialize`-структуру на УСПЕШНОМ пути, и она несла до 300 символов
   stderr. Теперь только шаг, код возврата и наш собственный путь.
5. *Базы связываются с сайтом по `site.id`, домен — фолбэк.* `find_site_row` матчит сайт по
   любому из `domain|domain_name|server_name|name`, а фильтр сравнивал со ЗАПРОШЕННОЙ строкой:
   разойдись они — `recognized > 0`, `names == []`, то есть уверенное «баз нет». Это была
   последняя дорога к «пустому архиву, который выглядит полным».
6. *Закрыты три дырки, через которые проходили мутации:* квотирование имени БД, квотирование
   обоих путей в `rm -rf` (самая опасная строка модуля — держалась только на `safe_component`)
   и бюджет каждого шага.
7. *Клиппи:* пояснение к шести `pub` было написано `///` с пустой строкой (приклеивалось
   документацией к `PIPE_STATUS_TAIL`) — стало `//`; убран `trim()` перед `split_whitespace`.
   **Прогон clippy не выполнен** — остановлен на слияние.
8. *`--` перед именами* у `tar` и `mysqldump` плюс запрет ведущего дефиса в `db_name_is_safe`:
   `q()` не кавычит токен из безобидных символов, и база с именем `--all-databases` формально
   утащила бы в архив весь сервер.

Мелочи оттуда же: `lock_state_text` говорит «last touched», а не «created» (мерится mtime,
который обновляет запись каждой части); `parse_df_avail_kb` ищет колонку по проценту, а не
считает с конца (с конца ломается точка монтирования с пробелом — прежнее «почему» было
неверным); `df` смотрит на родителя корня, и связь «корень на уровень ниже точки
монтирования» закреплена тестом.

**Ещё два незаявленных решения** (были в коде с первого коммита, в списке отступлений их не
было): `umask 077` в обоих конвейерах — внутри рабочего каталога лежат дампы баз, и создаваться
они обязаны нечитаемыми для прочих пользователей сервера; `chmod 700` корня отдельной командой —
`mkdir -m` действует только на создаваемый каталог, а корень от прошлых прогонов мог остаться
с правами пошире.

**Третий коммит фазы — правки по второму ревью (три пункта, все закрыты):**

1. *Первая редакция правки №5 занесла НОВУЮ дорогу к «баз нет».* Строка считалась узнаваемой,
   если у неё есть `site.id` **или** `site.domain`, а сравнение по id шло, только когда id есть
   с обеих сторон. Форма «строки БД несут один `site.id`» при нечитаемом `id` строки сайта
   давала `recognized > 0`, ни одного совпадения и уверенное `Some([])` — то есть «баз нет»
   вместо отказа (до правки №5 та же форма честно отказывала). Теперь узнаваема только та
   строка, по которой можно СРАВНИТЬ: `row_domain.is_none() && !(row_id.is_some() &&
   site_id.is_some())` → пропуск. Ключ, которым мы не умеем воспользоваться, узнаванием не
   считается. Тест `a_link_we_cannot_compare_is_not_recognition` проверен мутацией: со снятой
   починкой краснеет.
2. *Флак интеграционного теста вылечен, а не узаконен.* `printf x | (exit 5)` — гонка: читатель
   выходит не читая, и `printf` то успевает в буфер трубы, то ловит SIGPIPE (2000 прогонов в
   контейнере: 1993 раза `0 5`, 7 раз `141 5`, ≈0,35 %). Читатель теперь дочитывает
   (`cat >/dev/null`) — 2000 прогонов дали `2000 0 5`, гонки нет по построению. Ожидание «0
   либо 141» отвергнуто: оно превратило бы доказательство в допущение. Разбор `PIPESTATUS` в
   продукте при этом верен и не менялся — `tar` ловит SIGPIPE, только если умер `gzip`, а у
   того свой код ≠ 0, и он проверяется первым.
3. *Фолбэк `df` больше не врёт вместо отказа.* `build_space_cmd` возвращает `Option<String>`:
   нет пригодного родителя у `BACKUP_WORK_ROOT` — нет команды, шаг отказывает. Подстановка
   литерала `/var/tmp` увела бы проверку мерить чужую ФС, просто в другую сторону. Заодно в
   таблицу бюджетов добавлена проба замка: счастливый путь её не проходит, поэтому тест гоняет
   второй сценарий с занятым замком.

**Осталось только живому прогону:** работает ли `mysqldump` под root через сокет на
реальном сервере; реальные времена гигабайтного сайта против `BACKUP_ARCHIVE_TIMEOUT`;
поведение `tar` на сайте, куда пишет PHP (ожидаем код 1 → предупреждение).

### Фаза 4 — Tauri-команды, события, аудит `[x]`

`desktop/src-tauri/src/commands/domain_backup.rs` — форма списана с
[domain_facts.rs](desktop/src-tauri/src/commands/domain_facts.rs) дословно (keychain →
`cache::open` → `get_row_fields` → `blob_plaintext` → `key.zeroize()` → `drop(conn)` →
`ssh_connect_session_with_timeout` → `password.zeroize()` → работа → `disconnect`).

```rust
domain_backup_create(app, user_id, domain_id, dest_path, …) -> BackupResult   // создать + скачать
domain_backup_fetch (app, user_id, domain_id, backup_id, dest_path, …)        // ← фаза 8, нужен путь из разведки
domain_backup_cancel(domain_id, runs)
```

- `BackupResult { file_name, bytes, sha256, parts, warnings: Vec<&'static str>, duration_ms }`
  — **без поля `output`**, по правилу `CreateSiteResult`: нет поля — нет пути утечки.
- Целостность: `sha256sum` на сервере до выгрузки, локально — `HashingWriter<W>`, обновляющий
  хеш в `poll_write` (второго прохода по гигабайтам нет). Пишем в `<dest>.part`, переименовываем
  только при совпадении и хеша, и размера. Иначе оборванная выгрузка оставила бы на диске файл
  с правильным именем, который выглядит рабочим архивом и им не является.
- **После успеха команда пересъёмывает факты и делает write-back** — иначе успех не виден:
  список приезжает из `fp_facts`, и экран после удачного бэкапа выглядел бы как до него.
- События `backup:progress {domain_id, step, done_bytes, total_bytes}`, свой канал (не
  `provision:progress`: у того свой словарь шагов, чужие шаги дали бы пустые тосты).
  **Троттлинг обязателен** — чанк ≤ 32 KiB, то есть ~32 тысячи событий на гигабайт; эмитим не
  чаще 250 мс / 4 МиБ, последнее событие шага — всегда.
- Отмена: `Arc<AtomicBool>`, читается в `on_progress` (реакция мгновенная) и между шагами;
  `.part` удаляется, `rm -rf <work>` выполняется.
- Валидация `dest_path` в Rust — путь приезжает из вебвью: абсолютный, родитель существует и
  это каталог. Защита не от пользователя, а от бага фронта, который однажды пришлёт пустую строку.
- Аудит `domain.backup_created` с `{bytes, parts, duration_ms, databases}`. **Путь назначения
  на машине пользователя не отправляем** — это его локальная ФС, и `~/Documents/клиент-X/` сам
  по себе разглашение.

**Сделано.** Два новых файла: `desktop/src-tauri/src/commands/domain_backup.rs`
(команды `domain_backup_create` и `domain_backup_cancel`, форма списана с `domain_facts.rs`
дословно) и `desktop/src-tauri/src/ssh/backup_download.rs` (`HashingWriter`, валидация
`dest_path`, `.part` → сверка → `rename`). Зарегистрированы в `lib.rs` вместе с managed
state `BackupRuns`. **38 новых юнитов** (357 → 395 в `cargo test`, 0 failed) и **2
интеграционных** на живом докере (10 → 12 passed).

Что закрыто по пунктам плана: sha256 сервера сверяется с посчитанным по ходу записи
(`HashingWriter` обновляет хеш в `poll_write` и хеширует ТОЛЬКО принятый writer'ом префикс —
под отдельным тестом с «жадным» writer'ом); переименование только при совпадении И хеша, И
размера; троттлинг событий 250 мс / 4 МиБ с обязательным последним событием шага; отмена
читается в `on_progress` и между шагами ядра; `dest_path` проверяется до keychain и SSH;
аудит `domain.backup_created` без пути назначения; `BackupRuns` — второй слой
идемпотентности; пересъёмка фактов с write-back'ом после успеха.

**Отступления и решения фазы 4:**

1. *`warnings` остались `Vec<String>`, а не `Vec<&'static str>` из плана.* Ядро (отступление
   5 фазы 2) собирает предупреждения с цифрами — каким кодом кончился `tar`, какого
   инструмента нет, — и статическая строка этого не выражает. Правило «нет поля — нет пути
   утечки» при этом соблюдено, потому что оно про СЫРОЙ вывод команд (там эхо argv с
   паролями): поля `output` нет, строки собраны из классифицированных исходов, наружу идут
   только в вебвью на той же машине, **а в аудит на сервер уходят числа, а не они**.
2. *Появился отдельный модуль `ssh/backup_download.rs`,* которого план не называл. Причина
   практическая: доказать честность `HashingWriter` и `.part`→`rename` можно только на живом
   потоке, а интеграционные тесты — отдельный крейт и видят лишь публичные элементы
   библиотеки; внутри приватного `mod commands` эта проверка невозможна. Заодно место под
   S3/FTP остаётся ровно там, где задумано: второй адресат — такой же модуль РЯДОМ.
3. *`CancellableExec`* — обёртка над `Exec`, вставляющая проверку флага отмены между шагами
   ядра (`create_backup` — один вызов на девять шагов, и без неё отмена на пятнадцатой минуте
   `tar` не была бы видна ядру вовсе). Отказ **одноразовый**: иначе вместе с работой
   отменилась бы и уборка, и замок остался бы на сервере. Оба свойства под тестами.
4. *У `BackupResult` два поля сверх плана:* `path` (локальный путь — фазе 7 велено печатать
   путь, который вернула команда, а не тот, что выбрал человек; на сервер он не уходит) и
   `facts_refreshed` (провал пересъёмки не делает бэкап неудачным, но и молчать о старом
   снимке нельзя).
5. *Уборка архива на сервере — здесь, и она условная.* Ядро на успехе сносит рабочий каталог,
   но сам `<домен>-<штамп>.tar` оставляет; не убери его никто, `/var/tmp` продакшна забьётся
   тарболлами. Правило: сносим, когда файл больше не нужен (успех — копия проверена и уже
   переименована; отмена — человек передумал), и **оставляем при провале выгрузки** — тогда на
   сервере единственная целая копия (локальный `.part` уже снесён), и путь к ней называется в
   тексте ошибки. Команда — `rm -f` через `q()`, только для файла непосредственно в
   `BACKUP_WORK_ROOT`, без глобов и без `-r`; чужой путь не удаляется вовсе. Под тестами:
   решение по каждому исходу, отказ на `/`, `/etc/passwd`, вложенном пути и относительном,
   квотирование имени с апострофом.
6. *Порог тишины сессии (300 с) НЕ выводится из суммы exec-бюджетов,* как у
   `FACTS_SESSION_TIMEOUT`: сумма здесь — часы, а inactivity в часы означает «не замечать
   обрыва вовсе». Требование к порогу одно — пережить keepalive-бюджет (тест на месте, приём
   из отступления 1 фазы 1).
7. *Провал пересъёмки фактов НЕ пишется на сервер телом `{error}`* (в отличие от
   `domain_read_facts`): `fp_check_error` — сигнал здоровья самого домена, а здесь чтение было
   попутной услугой. Запись объявила бы домен непрочитанным по итогам действия, которое
   удалось. Наружу это едет `facts_refreshed: false` и событием `facts_failed`.
8. *`domain_backup_fetch` не написан* — это фаза 8, и она заблокирована разведкой. Причина, по

**Отступление фазы 6: у `not-in-snapshot` нет кнопки «Проверить на сервере», и у вкладки нет

домена устроена наоборот — факт важнее записи (`lib/domainDrift`).

  (события прогресса не выставляют его никогда, даже при `done === total` — сервер мог доложить
  последний чанк и упасть на `rename`); отмена диалога не оставляет следа вообще; путь печатается
  тот, что **вернула команда**, а не тот, что выбрал человек.

**Сделано.** Четыре новых файла — `frontend/src/api/domainBackups.ts` (прогон, ключ гейта
`["domain-backup", id]`, разбор маркера отмены), `frontend/src/store/backupRuns.ts` (стор
прогона и единственная в приложении подписка на `backup:progress`),
`frontend/src/components/domains/tabs/BackupRunLine.tsx` (инлайн-строка шага, полосы и исхода),
`frontend/src/lib/chooseSavePath.ts` (нативная панель «сохранить как» + имя-предложение той же
формы, что у сервера). Вкладка `DomainBackupTab` лишилась временной строки «создать копию
отсюда пока нельзя» и получила кнопку `Create backup` в слоте `right` у `SnapshotLine`.
Тестов **+63** (`47 → 50` файлов, `644 → 707` тестов в проверочной выборке, `tsc` чист):
`store/backupRuns.test.ts`, `api/domainBackups.test.ts`, `lib/chooseSavePath.test.ts` и
переработанный `DomainBackupTab.test.tsx` (сторож «кнопок нет» стал сторожем «в вебе ноль, в
десктопе ровно одна»).

Три правила «не соврать» проверены **мутациями**, каждая дала красный: успех из события
прогресса при `done === total` (2 теста), снятый `runExclusive` (5 тестов), полоса при
неизвестном знаменателе (1 тест), путь из `dest` вместо ответа команды (2 теста), след в сторе
после отказа от панели сохранения (2 теста). Отмена — тремя своими: снятый гейт отмены
(2 теста), исход `cancelled`, подменённый на `failed` (4 теста), невидимое нажатие отмены
(2 теста). Правки по ревью — ещё пятью: `aria-live`, перенесённый на счётчик байтов;
подписка, привязанная к жизни компонента; потерянный ответ `domain_backup_cancel`; разбор
маркера через «содержит»; `role="status"` на одной зелёной строке вместо всего исхода.

**Правки по итогам ревью** (все под тестами, каждая проверена мутацией):

1. *Ответ `domain_backup_cancel` больше не выбрасывается.* Между нашим `start()` и
   `runs.start()` в Rust лежит `syncLocalCache()` — поход в сеть, — и всё это время на экране
   уже стоит живая кнопка отмены. Нажатие в это окно Rust отменять нечем, и `false` —
   единственное, чем он может это сказать; промолчав, мы держали бы «Cancelling…» десятки
   минут, чтобы в конце показать «Saved». Теперь `false` снимает признак, и кнопка снова
   нажимаема.
2. *`role="status"` поднят на весь блок исхода.* Оговорка «список копий не обновился» и
   предупреждения меняют смысл зелёной строки — успех с ними полу-, — а стояли вне живой
   области: зрячий видел три строки, скринридер объявлял одну и притом полный успех.
3. *Сторож `aria-live` на оба конца:* он есть на строке шага и его НЕТ на счётчике байтов
   (счётчик меняется четыре раза в секунду — живая область вокруг него сделала бы чтение с
   экрана потоком цифр). Раньше перенос не ронял ни одного теста.
4. *Тест «прогон переживает закрытие карточки» шлёт событие ПОСЛЕ размонтирования* и до
   повторного показа, а мок отписки гасит хендлер. Прежняя схема (событие до `cleanup`,
   пустышка вместо отписки) проходила зелёной и с подпиской, живущей в эффекте компонента, —
   то есть осознанное решение «слушатель живёт столько же, сколько приложение» не было
   закреплено ничем.
5. *Кнопка отмены появляется только когда прогон существует* (`run !== null &&
   outcome === null`), а не по одному `pending`: тот встаёт раньше — на время нативной панели
   сохранения, — и клик по отмене в это окно не оставлял вообще ничего.
6. *Разбор маркера отмены строгий* — «текст кончается маркером», а не «содержит»: в тексте
   сбоя выгрузки едет путь на сервере, и файл с таким именем превратил бы аварию в тихое
   «отменено».

Не сделано осознанно: чистка `runs` в сторе (запись крошечная, растёт по числу доменов, за
сессию это единицы) и страховка от сломанного троттлинга Rust на стороне стора — обе
проверить нечем, кроме как выдумав отказ, которого сегодня нет.

**Отступления и решения фазы 7:**

1. *Кнопка отмены — сверх буквы фазы 7, и она закрыта здесь же.* Буква фазы 7 её не
   называет, но фаза 4 называет команду `domain_backup_cancel`, а фаза 2 расписывает
   поведение отмены до деталей (`Arc<AtomicBool>` в `on_progress` и между шагами, снос
   `.part`, `rm -rf <work>`, уборка серверного архива) — всё построено, покрыто тестами и до
   этой кнопки было недостижимо. Команда без вызывающего — то же, что проп без потребителя.
   Практическая сторона весомее формальной: выгрузка идёт десятками минут, и без отмены
   единственным выходом остаётся убийство приложения, после которого на сервере висит
   замок-каталог — следующая попытка упрётся в него и потребует рук на продакшне.
   Как сделано: **кнопка отмены СМЕНЯЕТ кнопку создания** на её месте в слоте `right` (двух
   кнопок, зовущих в разные стороны, на экране не бывает), появляется только в десктопе и
   только пока прогон идёт, имеет свой ключ гейта `["domain-backup-cancel", id]` (общий с
   созданием не годится: он занят на всё время бэкапа, и отмена в той же очереди не
   выполнилась бы никогда) и идёт через `invokeIfTauri`, а не `invokeSynced` — резолвить ей
   нечего, а круг в сеть стоял бы там, где нужна быстрота. Между нажатием и остановкой
   кнопка гаснет и подписывается «Cancelling…»: команда отвечает мгновенно, а прогон
   останавливается на следующем чанке, и без видимого отклика человек жал бы её снова.
   Отбитая просьба признак снимает и прогон не хоронит — провал ПРОСЬБЫ не есть провал
   бэкапа.
2. *Кнопка стоит в слоте `right` у `SnapshotLine`* — там же, где кнопка чтения на Server и
   Logs. Место не косметическое: удачный бэкап пересъёмывает снимок, то есть меняет ровно ту
   строку, рядом с которой нажат.
3. *При `server_id === null` кнопка выключена и объясняет причину `title`,* а не спрятана.
   Это не «выключенная кнопка с подсказкой» из фазы 6: там серым обещали функцию, которой в
   продукте нет вовсе, здесь функция есть — не хватает шага, который человек делает сам.
4. *Событие `facts_failed` стор выбрасывает как незнакомый шаг.* Правду о пересъёмке несёт
   поле `facts_refreshed` ответа: событию нельзя верить в этом вопросе по той же причине, что и
   в вопросе «сохранено», — после него команда ещё может упасть. На экране полууспех — своя
   строка под «Saved», приглушённо-янтарная, не ошибка.
5. *Подписка ставится лениво первым прогоном и не снимается никогда.* Эффект компонента её бы
   унёс ровно тогда, когда события и идут (карточку закрывают посреди выгрузки); осмысленного
   срока короче жизни приложения у неё нет. Единственность — под тестом.
6. *Стор не забывает исход при размонтировании:* строка результата (и путь к файлу!) живёт до
   следующего прогона по тому же домену. Исчезающий путь — это путь, который придётся искать
   заново.
7. *Добавлен `lib/chooseSavePath.test.ts`,* которого план не требовал: имя-предложение
   санитайзится (`/`, ведущая точка, не-ASCII), и это код, а не константа.

## Проверка

**Юнит, Rust** (основная масса, на зафиксированных сэмплах из фазы 0 — по образцу
`SITES_JSON`/`FTP_JSON` в `fastpanel_facts.rs`):
- парсеры бэкапов: непонятная форма → `None`, а не «пусто»; `error: expected command…` не должен
  пройти в положительный ответ; фильтр по домену не ловит `example.com.old`; неразобранная дата
  → отсутствует, а не «сегодня»; размер не число → отсутствует, а не 0;
- сборщики команд: `q()` применён ко ВСЕМ интерполяциям (тест с доменом `a b'c`), `pipefail`
  присутствует в конвейерах;
- классификация кода `tar` (0/1/≥2), решение по свободному месту на границе;
- соотношения таймаутов: существующий `session_timeout_exceeds_the_read_exec_budget` должен
  пройти после подъёма констант; про keepalive — **два** теста, а не один (фаза 1 показала, что
  единый порог неверен): `KEEPALIVE_INTERVAL × (KEEPALIVE_MAX+1) <` session timeout у трёх
  долгих сессий (facts, provision, установка FastPanel) и более слабое «успеть спросить и
  получить ответ хотя бы раз» — у двух коротких (листинг сайтов, «SSH Test»), которым нужна
  быстрая реакция на мёртвый сервер; константы при этом НЕ поднимались (см. отступление 1 фазы 1);
- `BackupRuns`: повторная регистрация отказывает, снятие происходит на **всех** путях выхода;
- валидация `dest_path`: относительный, несуществующий родитель, пустая строка.

**Интеграционные** (`tests/ssh_integration.rs`, docker `linuxserver/openssh-server`, `#[ignore]`,
рядом с `tofu_then_exec_uname`):
- `head -c 3000000 /dev/urandom` через `exec_to_writer` → длина и sha256 совпали (ловит и
  `from_utf8_lossy`, и pty-подмену `\n`);
- `sh -c 'echo noise >&2; printf "\x00\x01\x02"'` → в writer ровно 3 байта, `noise` в stderr —
  прямая защита от слияния потоков, которым болен `exec`;
- `sh -c 'printf x; exit 7'` → `exit == 7`, `bytes == 1` — прямой наследник бага `Eof`;
- медленный поток (`printf x; sleep 1` × 5) при `idle_timeout = 1.5s` **проходит**, а `sleep 5`
  при том же — падает: тест на само отличие простоя от длительности;
- отмена: `Break` после первого чанка → `Cancelled`, сессия остаётся живой;
- keepalive: `inactivity 5s` + `sleep 12` — без keepalive умирает, с ним доходит. Единственное
  доказательство фазы 1.

**Фронт (vitest)**: четыре пустых состояния печатают четыре разные фразы и «копий нет» не
появляется ни в одном из трёх остальных; два клика по кнопке → одна команда; отмена диалога →
`invokeSynced` не вызван и на экране ни «Saved», ни ошибки; успех печатает путь **из ответа
команды**; `total_bytes` неизвестен → нет `role="progressbar"`; веб → ноль кнопок; шесть вкладок
в `getAllByRole("tab")`; `dialog:allow-save` в capabilities (сторож).

**Только живой прогон** (записать в план явно, не притворяться, что покрыто): форма
`backup:plan`; работает ли `mysqldump` под root через сокет; реальные времена гигабайтного
сайта против `BACKUP_ARCHIVE_TIMEOUT`; что делает панель, если её собственное расписание
сработает параллельно нашему `tar`; нативная панель сохранения на macOS в подписанной сборке.
