# Бэкапы домена: вкладка Backup + чтение и создание через FastPanel/SSH


## Контекст

В карточке домена (`DomainDetailModal`) сегодня пять вкладок, и бэкапов среди них нет
вовсе. Есть статичная заглушка `SectionCard "Backups"` + `Badge COMING SOON` внутри
вкладки **Server** — [DomainServerTab.tsx:157-173](frontend/src/components/domains/tabs/DomainServerTab.tsx#L157).
Ноль пропсов, ноль запросов, ноль Tauri-команд. За ней в продукте не стоит ничего: ни
модели на бэкенде, ни колонки у домена, ни поля в снимке `fp_facts`, ни единого вызова
чего-либо связанного с бэкапами в Rust (`mysqldump`/`tar`/`restore` не встречаются нигде;
`.bak` есть только у nginx-сниппета в `apply_nginx_override`).

План 18.08 поставил эту заглушку осознанно (отступление №1: «селекты Frequency/Destination,
которые ничего не сохраняют, — это обещание настройки, которой нет»), но условий её снятия
не записал. Настоящий план их выполняет.

**Что решено с пользователем:**
- Отдельная вкладка **Backup**: показывать существующие копии + кнопка «сделать бэкап сейчас».
- Разведка FastPanel CLI на живом сервере под root — **можно**.
- Куда девать архив: в первой версии — **скачивание на машину пользователя**. Внешнее
  хранилище (S3/FTP) нужно позже — архитектура обязана оставить для него место, но не
  реализовывать его сейчас.

**Что известно про источник данных (проверено по `docs/FASTPANEL_CLI.md`, снят живым
прогоном 2026-08-16):**
- `sites list --json` — команда, которую мы **уже гоняем** при `domain_read_facts`, —
  содержит поле `"backups":[]` ([FASTPANEL_CLI.md:69](docs/FASTPANEL_CLI.md#L69)). На живом
  сервере массив был **пуст**, поэтому форма непустого элемента неизвестна.
- Команда `backup:plan` существует и доступна даже непривилегированному пользователю панели
  ([FASTPANEL_CLI.md:23](docs/FASTPANEL_CLI.md#L23)) — но её **ни разу не звали**: ни
  `--help`, ни `list`, ни `--json`. Форма вывода и коды возврата неизвестны.
- Каталог, куда панель кладёт архивы, не разведан.

Отсюда главный принцип фазировки: **разведка блокирует ЧТЕНИЕ чужих бэкапов, но не блокирует
создание своих.** `tar` и `mysqldump` — инструменты с известной формой, их разведывать не надо.

---

## Ключевые решения

### 1. Собственный архив, а не `backup:plan`

Создание бэкапа делаем сами: `tar` каталога сайта + `mysqldump` каждой БД домена + манифест,
всё это одним `.tar`. Причина: у `backup:plan` неизвестны форма вывода, коды возврата и место
складирования — мы не сможем ни проверить целостность, ни забрать файл, ни убрать за собой.
`backup:plan` остаётся источником **чтения** и кандидатом на будущую фазу.

Следствие, которое обязано быть видно на экране: **наш архив не появится в списке копий
панели**. Это два разных предмета с разным происхождением, и смешивать их в одном списке
нельзя.

### 2. Транспорт: новый `exec_to_writer`, а не `russh-sftp`

`SshSession::exec` для бинарного гигабайта непригоден трижды
([client.rs:204-235](desktop/src-tauri/src/ssh/client.rs#L204)):
- копит всё в `Vec<u8>` и делает `String::from_utf8_lossy` — каждый невалидный UTF-8 стал бы
  U+FFFD, то есть архив был бы испорчен целиком;
- **сливает stdout и stderr в один буфер** — одно предупреждение `tar` вклеилось бы в середину файла;
- дедлайн **суммарный** (`deadline = now + timeout`), а не по бездействию — здоровая
  многоминутная выгрузка обрывалась бы на середине.

Берём вариант A (`exec_to_writer`), а не SFTP-крейт, потому что:
- SFTP закрывает один шаг из тринадцати — `tar`, `mysqldump`, `sha256sum`, замок, `rm -rf`
  всё равно идут через `exec`;
- исторический баг с `Eof`/`exit-status` уже оплачен именно в exec-цикле
  ([client.rs:214-228](desktop/src-tauri/src/ssh/client.rs#L214), план 2026-08-06) — новый
  цикл наследует это знание, SFTP-путь заводил бы свой набор граблей, не покрытый нашими тестами;
- ноль новых зависимостей.

### 3. Keepalive — сквозная правка, которую надо назвать вслух

`russh::client::Config` создаётся сегодня только с `inactivity_timeout`; keepalive выключен.
Молчащий получасовой `tar` не шлёт ни байта, и единственный способ его пережить без keepalive
— раздуть inactivity до часов, то есть перестать замечать оборванную связь вовсе.
Включаем `keepalive_interval: Some(30s)`, `keepalive_max: 3`.

**Это меняет поведение ВСЕХ SSH-операций продукта.** В лучшую сторону (мёртвый сервер
опознаётся за ~2 минуты вместо 600 секунд, а 300-секундный молчаливый `certificates create-le`
перестаёт жить на честном слове), но это изменение, и оно должно приниматься сознательно.

### 4. Незнание называется словом (принцип №6)

`backups` в `DomainFacts` — **не** `Vec<BackupEntry>`. Пустой список означал бы «бэкапов нет»
— утверждение, которого мы сделать не можем. Структура несёт явное состояние:

```rust
pub struct BackupsFacts {
    pub state: BackupsState,          // Known | Unknown
    pub entries: Vec<BackupEntry>,
    pub probed: Vec<&'static str>,    // где смотрели — иначе «не знаем» ≡ «не пробовали»
}
```

На фронте это даёт **четыре** различимых состояния, а не два:

| На проводе                      | Что значит                          | Что на экране                                     |
| ------------------------------- | ----------------------------------- | ------------------------------------------------- |
| поля `backups` нет вовсе        | снимок снят сборкой до этой функции | «снимок старый, пересними» + кнопка               |
| `state: "unknown"`              | панель ответила, разобрать не вышло | «не смогли прочитать список» — **не** «копий нет» |
| `state: "known"`, `entries: []` | панель ответила, копий нет          | «FastPanel копий не показывает»                   |
| `state: "known"`, есть записи   | список                              | список                                            |

Пока разведка не показала непустой `sites[].backups[]`, пустой массив трактуется как
`Unknown`. Это зашито константой `SITE_BACKUPS_FIELD_TRUSTED: bool = false` с расписанным
смыслом — переключать только вместе со ссылкой на раздел `docs/FASTPANEL_CLI.md`, где форма
зафиксирована.

### 5. Диалог — панель сохранения, не выбор папки

`dialog:allow-save` (а не `allow-open` с `directory:true`): человек должен видеть и править
имя файла, а `allow-open` открыл бы вебвью ещё и чтение произвольных путей, которого задача не
требует. Команда принимает **полный путь файла** (`destPath`), не каталог.

## Фазы

### Фаза 0 — разведка `[ ]` · БЛОКИРУЕТ фазы 3 и 8

**Предусловие P0:** на разведываемом сервере должен быть **хотя бы один сделанный бэкап**
(через веб-морду FastPanel, руками). Без него форма непустого `sites[].backups[]` не снимется
— скрипт этого добыть не может по построению.

Новые read-only секции в [scripts/fastpanel-discovery.sh](scripts/fastpanel-discovery.sh),
в стиле существующих (`run`/`run_sh`/`fp`/`skip_section`, маркеры `#sdmp:*`):

- **CLI**: `backup:plan --help`, `backup:plan list --json`, `backup:plan list`, плюс
  `backup --help` и `backups --help` — прецедент `database` vs `databases`
  ([FASTPANEL_CLI.md:203](docs/FASTPANEL_CLI.md#L203)) уже стоил бага в провижининге; две
  лишние строки дешевле повторного захода на продакшн.
- **Раскладка на диске**: `find` по `/var/www/<owner>/data`, `/var/backups`,
  `/var/lib/fastpanel2`, `/mnt`, `/backup` — каждое место своей секцией («каталога нет» и
  «каталог пуст» — разные ответы). Файлы через `find -printf '%p\t%s\t%TY-…'` (машинный
  формат вместо зависящего от локали `ls -l`).
- **Расписание**: `systemctl list-timers`, `ls /etc/cron.d`. **`crontab -l` НЕ зовём** — в
  cron-строке панели может стоять `mysqldump -p<пароль>`, а шапка скрипта обещает, что
  паролей мы не собираем.
- **Внутренняя БД панели**: `SHOW TABLES | grep -i backup`, `DESCRIBE`, `SELECT COUNT(*)`.
  ⚠️ **`SELECT *` запрещён**: в строках таблицы бэкапов лежат учётки внешних хранилищ.
  Побочный и важный результат секции — работает ли `mysql` под root **без пароля через
  сокет** (от этого зависит вся схема `mysqldump` в фазе 2).
- **Инструменты**: `command -v` для `tar gzip mysqldump sha256sum du df nice ionice install`,
  `tar --version` (GNU vs busybox меняет схему кодов возврата), `df -Pk /var/tmp`.

**Итог фазы:** новый раздел «9. Бэкапы» в `docs/FASTPANEL_CLI.md` с формами вывода и кодами
возврата, обезличенный по правилам файла.

### Фаза 1 — `exec_to_writer` + keepalive `[x]` · не блокируется разведкой

[desktop/src-tauri/src/ssh/client.rs](desktop/src-tauri/src/ssh/client.rs):

```rust
pub struct ExecStream { pub exit: i32, pub bytes: u64, pub stderr: String, pub signal: Option<String> }

pub async fn exec_to_writer<W, F>(&mut self, cmd: &str, idle_timeout: Duration,
                                  out: &mut W, on_progress: F) -> Result<ExecStream, SshError>
where W: tokio::io::AsyncWrite + Unpin + Send,
      F: FnMut(u64) -> std::ops::ControlFlow<()> + Send;
```

- stdout → writer как есть (никакого `from_utf8_lossy`), stderr → отдельный буфер с потолком
  `STREAM_STDERR_CAP = 8 KiB`;
- дедлайн сдвигается на **каждом** принятом сообщении — ловит замолчавший канал, а не
  длительность команды;
- `pty` не параметр: всегда false и не может быть иначе — псевдотерминал переводит `\n` в
  `\r\n`, то есть тихо портит каждый байт 0x0A;
- разбор `Eof`/`ExitStatus`/`Close` наследуется построчно вместе с комментарием из `exec`;
- `ChannelMsg::ExitSignal` → `signal` (OOM-killer на гигабайтном `tar` выглядит именно так, и
  без этого поля такой конец неотличим от «код не доехал»);
- новый вариант `SshError::Cancelled` — отмена не сбой, и в аудите/UI обязана выглядеть иначе,
  чем оборванная связь;
- `KEEPALIVE_INTERVAL = 30s`, `KEEPALIVE_MAX = 3` в `connect()` (решение 3).

**Сделано.** Всё перечисленное — в `ssh/client.rs`: `ExecStream`, `exec_to_writer` (дедлайн
пересчитывается на каждом витке цикла), `CappedStderr` с потолком 8 KiB, `SshError::Cancelled`,
`ExitSignal → signal`, keepalive в `connect`. Юниты: потолок stderr (сохраняется начало, потеря
названа), текст `Cancelled`, связь `KEEPALIVE_BUDGET` с интервалом и квотой. Шесть
интеграционных тестов из раздела «Проверка» написаны под `#[ignore]` (докера у автора не было —
проверены только сборкой `cargo test --features ssh_integration --no-run`).

**Отступления, принятые в фазе 1:**

1. *Инвариант таймаутов оказался не универсальным.* Проверка «`KEEPALIVE_INTERVAL ×
   (KEEPALIVE_MAX+1)` (= 120 с) < каждый session timeout» проходит для `FACTS_SESSION_TIMEOUT`
   (600), `PROVISION_SESSION_TIMEOUT` (420) и `FP_SESSION_TIMEOUT` (300), но НЕ для
   `LIST_SITES_SESSION_TIMEOUT` (60) и таймаута кнопки «SSH Test» (45). Поднимать их не стали:
   обоим нужна быстрая реакция на мёртвый сервер, а полный бюджет удлинил бы её вдвое-втрое.
   Разбор кода russh 0.45 (`client/mod.rs:885-970`) показывает, что для корректности хватает
   более слабого условия: inactivity сбрасывается ЛЮБЫМИ принятыми данными, в том числе ответом
   на keepalive, — значит живая молчаливая сессия не умирает при любом `session_timeout >
   KEEPALIVE_INTERVAL`, а полный бюджет даёт лишь запас на пропущенные ответы. Поэтому тестов
   два вида: полный бюджет — у трёх долгих сессий, «успеть спросить и получить ответ хотя бы
   раз» — у двух коротких, с комментарием почему.
2. *Литерал `Duration::from_secs(45)` в `ssh_exec` получил имя* `SSH_TEST_SESSION_TIMEOUT` —
   иначе самый короткий session timeout продукта нечем было закрепить тестом.
3. *Ради теста keepalive добавлена `connect_with_keepalive_override`* (продуктовый путь —
   по-прежнему `connect`). Плановые «inactivity 5 s + sleep 12 s» с продуктовым интервалом 30 с
   недостижимы: keepalive не успел бы прозвучать ни разу. Функция позволяет тесту взять
   интервал 2 с и получить честную пару «без keepalive умирает / с ним доходит», а сами
   продуктовые 30 с закреплены юнит-тестами соотношений.

### Фаза 2 — создание бэкапа, ядро `[ ]` · не блокируется разведкой

Новый `desktop/src-tauri/src/ssh/backup_run.rs` (зеркалит существующее разделение:
`fastpanel.rs` создаёт, `fastpanel_facts.rs` читает).

Шаги, все через `q()` из `fastpanel.rs`, `pty:false`:

| Шаг                   | Команда                                                                                                                          | Таймаут |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------- | ------- |
| `resolve`             | `sites list --json` → `index_dir`; `databases list --json` → БД по `site.domain`                                                 | 60s     |
| `preflight`           | `command -v tar gzip mysqldump sha256sum du df`                                                                                  | 60s     |
| `space`               | `du -sk <site_path>`, `df -Pk /var/tmp` — нужно ≥ 1.2× оценки                                                                    | 60s     |
| `lock`                | `mkdir -m 700 /var/tmp/sdmp-backup/<domain>`                                                                                     | 60s     |
| `archive_files`       | `set -o pipefail; nice -n 19 ionice -c3 tar --warning=no-file-changed -cf - -C <parent> <base> \| gzip -1 > <work>/site.tar.gz`  | 3600s   |
| `dump_db` (на каждую) | `set -o pipefail; mysqldump --single-transaction --quick --routines --triggers --events <db> \| gzip -1 > <work>/db-<db>.sql.gz` | 3600s   |
| `manifest` + `pack`   | манифест JSON, затем `tar -cf <archive> -C <work> manifest.json site.tar.gz db-*.sql.gz` (имена перечислены явно, без glob)      | 3600s   |
| `checksum`            | `sha256sum <archive>`, `stat -c %s`                                                                                              | 60s     |
| `cleanup`             | `rm -rf <work>`                                                                                                                  | 60s     |

Решения, которые обязаны быть защищены комментарием в коде:

- **Рабочий каталог `/var/tmp/sdmp-backup/`, не под `site_path`.** Архив под document root
  скачивается по HTTP кем угодно, пока лежит там, и попадает внутрь следующего `tar` самого
  себя. Это дыра, а не стилистика.
- **Замок — каталог.** `mkdir` на POSIX атомарен, `test -f && touch` — нет. Просроченный
  замок **не сносим автоматически**: отдельная действенная ошибка с путём. Автоснос убил бы
  чужой идущий бэкап.
- **Пароль БД в argv не ставим никогда.** `mysqldump -p<пароль>` виден в `ps` всем
  пользователям сервера на всё время дампа — это хуже, чем разовое эхо argv у FastPanel
  ([FASTPANEL_CLI.md §7](docs/FASTPANEL_CLI.md#L388)), потому что длится минуты. Идём через
  root-сокет, тем же способом, каким уже работает `list_site_databases`. Не сработало —
  **честный отказ**, а не тихий фоллбэк на пароль в argv. `db_password_blob_id` в первой
  версии не расшифровываем вовсе.
- **`gzip -1`, `nice`, `ionice`** — продакшн обслуживает живой сайт.
- **Код `tar` 1 = «файлы менялись при чтении» → предупреждение, не отказ; ≥ 2 → отказ.**
- Идемпотентность трёхслойная: замок-каталог на сервере (переживает перезапуск десктопа,
  ловит второй десктоп) + `BackupRuns` в managed state Tauri + `runExclusive` во фронте.

Манифест `{"format":"sdmp-backup/1","domain":…,"created_at":…,"site_path":…,"databases":[…],
"parts":[{name,kind,sha256}],"tool":…}` — чтобы человек, открывший архив через полгода, понял,
что это и куда разворачивать, не заглядывая в SDMP.

### Фаза 4 — Tauri-команды, события, аудит `[ ]`

`desktop/src-tauri/src/commands/domain_backup.rs` — форма списана с
[domain_facts.rs](desktop/src-tauri/src/commands/domain_facts.rs) дословно (keychain →
`cache::open` → `get_row_fields` → `blob_plaintext` → `key.zeroize()` → `drop(conn)` →
`ssh_connect_session_with_timeout` → `password.zeroize()` → работа → `disconnect`).

```rust
domain_backup_create(app, user_id, domain_id, dest_path, …) -> BackupResult   // создать + скачать
domain_backup_fetch (app, user_id, domain_id, backup_id, dest_path, …)        // ← фаза 8, нужен путь из разведки
domain_backup_cancel(domain_id, runs)
```

- `BackupResult { file_name, bytes, sha256, parts, warnings: Vec<&'static str>, duration_ms }`
  — **без поля `output`**, по правилу `CreateSiteResult`: нет поля — нет пути утечки.
- Целостность: `sha256sum` на сервере до выгрузки, локально — `HashingWriter<W>`, обновляющий
  хеш в `poll_write` (второго прохода по гигабайтам нет). Пишем в `<dest>.part`, переименовываем
  только при совпадении и хеша, и размера. Иначе оборванная выгрузка оставила бы на диске файл
  с правильным именем, который выглядит рабочим архивом и им не является.
- **После успеха команда пересъёмывает факты и делает write-back** — иначе успех не виден:
  список приезжает из `fp_facts`, и экран после удачного бэкапа выглядел бы как до него.
- События `backup:progress {domain_id, step, done_bytes, total_bytes}`, свой канал (не
  `provision:progress`: у того свой словарь шагов, чужие шаги дали бы пустые тосты).
  **Троттлинг обязателен** — чанк ≤ 32 KiB, то есть ~32 тысячи событий на гигабайт; эмитим не
  чаще 250 мс / 4 МиБ, последнее событие шага — всегда.
- Отмена: `Arc<AtomicBool>`, читается в `on_progress` (реакция мгновенная) и между шагами;
  `.part` удаляется, `rm -rf <work>` выполняется.
- Валидация `dest_path` в Rust — путь приезжает из вебвью: абсолютный, родитель существует и
  это каталог. Защита не от пользователя, а от бага фронта, который однажды пришлёт пустую строку.
- Аудит `domain.backup_created` с `{bytes, parts, duration_ms, databases}`. **Путь назначения
  на машине пользователя не отправляем** — это его локальная ФС, и `~/Documents/клиент-X/` сам
  по себе разглашение.

## Проверка

**Юнит, Rust** (основная масса, на зафиксированных сэмплах из фазы 0 — по образцу
`SITES_JSON`/`FTP_JSON` в `fastpanel_facts.rs`):
- парсеры бэкапов: непонятная форма → `None`, а не «пусто»; `error: expected command…` не должен
  пройти в положительный ответ; фильтр по домену не ловит `example.com.old`; неразобранная дата
  → отсутствует, а не «сегодня»; размер не число → отсутствует, а не 0;
- сборщики команд: `q()` применён ко ВСЕМ интерполяциям (тест с доменом `a b'c`), `pipefail`
  присутствует в конвейерах;
- классификация кода `tar` (0/1/≥2), решение по свободному месту на границе;
- соотношения таймаутов: существующий `session_timeout_exceeds_the_read_exec_budget` должен
  пройти после подъёма констант; новый — `KEEPALIVE_INTERVAL × (KEEPALIVE_MAX+1) <` каждый
  session timeout, иначе keepalive не успеет ничего доказать;
- `BackupRuns`: повторная регистрация отказывает, снятие происходит на **всех** путях выхода;
- валидация `dest_path`: относительный, несуществующий родитель, пустая строка.

**Интеграционные** (`tests/ssh_integration.rs`, docker `linuxserver/openssh-server`, `#[ignore]`,
рядом с `tofu_then_exec_uname`):
- `head -c 3000000 /dev/urandom` через `exec_to_writer` → длина и sha256 совпали (ловит и
  `from_utf8_lossy`, и pty-подмену `\n`);
- `sh -c 'echo noise >&2; printf "\x00\x01\x02"'` → в writer ровно 3 байта, `noise` в stderr —
  прямая защита от слияния потоков, которым болен `exec`;
- `sh -c 'printf x; exit 7'` → `exit == 7`, `bytes == 1` — прямой наследник бага `Eof`;
- медленный поток (`printf x; sleep 1` × 5) при `idle_timeout = 1.5s` **проходит**, а `sleep 5`
  при том же — падает: тест на само отличие простоя от длительности;
- отмена: `Break` после первого чанка → `Cancelled`, сессия остаётся живой;
- keepalive: `inactivity 5s` + `sleep 12` — без keepalive умирает, с ним доходит. Единственное
  доказательство фазы 1.

**Фронт (vitest)**: четыре пустых состояния печатают четыре разные фразы и «копий нет» не
появляется ни в одном из трёх остальных; два клика по кнопке → одна команда; отмена диалога →
`invokeSynced` не вызван и на экране ни «Saved», ни ошибки; успех печатает путь **из ответа
команды**; `total_bytes` неизвестен → нет `role="progressbar"`; веб → ноль кнопок; шесть вкладок
в `getAllByRole("tab")`; `dialog:allow-save` в capabilities (сторож).

**Только живой прогон** (записать в план явно, не притворяться, что покрыто): форма
`backup:plan`; работает ли `mysqldump` под root через сокет; реальные времена гигабайтного
сайта против `BACKUP_ARCHIVE_TIMEOUT`; что делает панель, если её собственное расписание
сработает параллельно нашему `tar`; нативная панель сохранения на macOS в подписанной сборке.
