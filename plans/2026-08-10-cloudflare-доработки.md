**3.1 Поиск по аккаунтам.** Поле над списком; фильтр по `name`/`account_id`.  `[x]`

**3.2 Поиск/сортировка зон внутри аккаунта.** Поле в развёрнутой `AccountCard`;
фильтр по имени + сортировка (имя / статус).  `[x]`
- Сделано: поиск (`filterZones`) и `<Sel>` сортировки в шапке блока «Zones» —
  то есть видны только у развёрнутой карточки. Пороги РАЗНЫЕ: поиск от 8 зон
  (`ZONE_SEARCH_MIN`) — семь имён проглядывают глазами быстрее, чем набирают
  запрос; сортировка от 2 (`ZONE_SORT_MIN`) — селектор стоит один тег в уже
  существующем ряду и полезен с двух строк, а единственная зона — единственный
  случай, когда сортировать нечего в принципе. Считаются пороги по ПОЛНОМУ

  не применяется. Пункт «Sort: status» гейтнут на `zones.some(z => z.status)`:

  действия человека, а незнание внизу — поднять его в начало «важного» значило

  доопределяются именем: без этого порядок зависел бы от источника списка.

  число найденного стоит у поля («4 of 8»). «Ни одна не подошла» — отдельная

- Тесты: `frontend/src/pages/Cloudflare.search.test.tsx` (13 штук). Проверены

## Долг, выявленный по ходу

**Д1. `api_token_masked` больше не читает никто на фронте.** После 1.2 остались
только объявление типа (`frontend/src/api/cloudflare.ts:19`) и фикстуры четырёх
тестов. Вычистить поле из `CloudflareAccountResponse` и `build_account_response`
(`backend/app/services/cloudflare_service.py:16-24`) и из TS-типа. Сцеплено с 4.1
(чистка схем) — делать одним заходом. Адрес поля в схеме —
`backend/app/schemas/cloudflare.py:50`. Правка уронит
`backend/tests/test_cloudflare_account_response.py` (точный набор ключей ответа
и `assert response.api_token_masked == "••••eeee"`) — это не «я что-то сломал», а
часть работы Д1: гард держит «ответ не обещает того, чего сервер не делает».

**Д2. Протухшая строка allowlist**
`backend/tests/test_no_plaintext_secret_schemas.py:94` разрешает
`CloudflareAccountResponse.api_token_masked` с обоснованием «Токен, уже
замаскированный сервером (`****abcd`) для списка в UI». Оба утверждения ложны:
это хвост blob_id, а никакого списка в UI после 1.2 нет. Файл сам настаивает, что
каждая строка списка — «видимый в диффе акт», так что снять её надо вместе с Д1,
а не «когда-нибудь».

**Д3. Смена типа A → MX в форме правки уходит без `priority`.**
Поле приоритета появляется пустым (у исходной A-записи приоритета нет), пустое
поле значит «не трогать», и PATCH уезжает как `{type: "MX", …}` без приоритета.
Опасность низкая и молчаливой порчи нет: Cloudflare мержит PATCH с текущей
записью, у которой приоритета нет вовсе, и либо отвергнет запрос с внятной
ошибкой (она доедет до баннера `actionError`, `Cloudflare.tsx:678-683`), либо
заведёт MX с приоритетом 0. Сейчас не чиним осознанно: лечится это валидацией,
а ТЗ фазы 1.3 её запрещало, и чинить пришлось бы симметрично в обеих формах
(создание записи тоже не проверяет приоритет). Браться — вместе с фазой 2.

**Д4 (кандидат в фазу 2). `priority` есть в данных, но не показан в таблице.**
После 1.3 запись приезжает с приоритетом, а колонки в списке прежние —
`Type/Name/Content/TTL/Proxied` (`Cloudflare.tsx:701`). У MX приоритет — половина
смысла записи: без него две MX-строки в списке неразличимы по важности. Дёшево:
колонка (или суффикс к Content) с `—` для типов без приоритета.

**Д5. Поля форм Cloudflare не связаны с подписями.** `<label>` во всех модалках
страницы — это просто текст: ни `htmlFor`, ни `id` у `Inp`/`Sel` нет, поэтому
скринридер читает поле безымянным, а тестам приходится искать по плейсхолдеру.
Работа по доступности отдельная и сквозная (не только Cloudflare) — фиксируем,
не делаем внутри фаз этого плана.

**Д6. Вторая лестница статуса Cloudflare-зоны — в `EditDomainModal`.**
`frontend/src/pages/Domains.tsx:141-157` держит свой инлайновый маппинг, уже
разошедшийся с `ZONE_STATUS_VARIANT` (фаза 2.1): `initializing` там серый, здесь
жёлтый; отсутствие статуса там даёт серый бейдж «Unknown», здесь бейджа нет
вовсе; текст там «Active»/«Pending (NS не делегированы на CF)», здесь сырое
слово Cloudflare. `CLAUDE.md`, принцип 6, требует держать лестницу в одном месте.
Сейчас это долг, а не блокер: модалка НЕДОСТИЖИМА (`setEditingDomain` нигде не
зовётся со значением — зафиксировано комментарием в `Domains.tsx:89-99`), то есть

ПЕРВЫМ шагом вынести лестницу в `frontend/src/lib/` (как `serverStatus.ts`), и
оба места импортируют оттуда. Класть таблицу в `pages/Cloudflare.tsx` и
импортировать её из `pages/Domains.tsx` нельзя: межстраничный импорт из
page-модуля хуже дубля. Отдельной строкой: у жёлтой ступени потерялось
пояснение — в мёртвой модалке было «Pending (NS не делегированы на CF)», а сырое
`pending` в списке зон не говорит, что делать; кандидат — `title` на бейдже.
