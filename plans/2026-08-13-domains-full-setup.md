# План: Domains — full setup нового домена (Кейс 2)

**Дата:** 2026-08-13
**Источник:** `task8.md` (корень), Кейс 2. Первой половине — Кейсу 1 — отведён отдельный
план `2026-08-13-domains-cloudflare-zhivoy-match.md`.
**Ветка:** `feat/domains-cloudflare-match`

## Context (зачем)

Цель: из мастера завести домен и одним потоком связать хостинг + Cloudflare (+регистратор),
завести зону и (по тумблеру) прописать NS. Схемы `BulkFullSetupRequest/Response`
(`backend/app/schemas/domain.py`) уже есть, но **эндпоинт и десктоп-команда не реализованы**.

### Граница из-за zero-knowledge (важно)

- **Бэкенд** атомарно делает то, что не требует токена: создаёт строку домена и проставляет
  `server_id` + `cloudflare_account_id` + `registrar_id`; возвращает домен и `task_log_id`.
  Идемпотентность — через idempotency key (как у provision).
- **Десктоп** выполняет то, что требует токена: `cf_create_zone` → write-back
  `cloudflare_zone_id`; по тумблеру `registrar_set_nameservers` (write-back `ns_status`).
  Всё пишет audit best-effort, как остальные команды.

## Acceptance criteria

- [ ] `POST /domains/full-setup` принимает `BulkFullSetupRequest` и проставляет связки пачке
      существующих доменов одной транзакцией, возвращая `BulkFullSetupResponse`.
- [ ] Повтор с тем же idempotency key не делает работу дважды.
- [ ] Tauri-команда `domain_full_setup` на ОДИН домен: заводит зону (или переиспользует
      существующую), пишет `cloudflare_zone_id` обратно, по флагу пушит NS.
- [ ] Наружу команда отдаёт структуру со статусами шагов — частичный успех не крашится.
- [ ] Мастер «Add Domain» умеет полный поток: домен → связки → зона → (по тумблеру) NS,
      с отчётом по шагам.
- [ ] Массовое действие «Full setup» по выделенным: диалог → бэкенд → прогон по пачке с
      конкуренцией → сводный отчёт, гейт «один прогон за раз».
- [ ] Тумблер «Прописать NS» дизейблится для регистратора без API; кнопка «Создать и
      настроить» при этом остаётся активной.
- [ ] Бэкенд не ходит в Cloudflare и к регистратору — ни строчкой.

## Edge cases

- Зона уже существует в аккаунте → не дублировать (fallback на поиск по имени).
- Регистратор не выбран или его провайдер без NS-API → NS-шаг пропускается, остальное идёт.
- Частичный провал в пачке: отчёт строками, а не исключением.
- Веб (`!isTauri()`): шаги выполнения (зона/NS) недоступны — только связки, либо действие
  скрыто.
- Двойной клик по массовому действию — гейт, как у привязки/provision.

## Фазы

### Фаза 1 — Бэкенд: эндпоинт `[ ]`

Поддержать **оба входа**:
- **Новый домен (одиночный).** Мастер сперва создаёт домен существующим `POST ""`
  (реюз `create_domain`), получая `id`, затем идёт в full-setup по этому id.
- **Массовый по существующим.** `POST /domains/full-setup` на базе готовой
  `BulkFullSetupRequest` (`domain_ids`, `server_id`, `cloudflare_account_id`,
  `registrar_id?`) — реализовать роут (сейчас только схема). Сервис `domain_service.py`:
  транзакция «проставить связки пачке» (реюз `bulk_assign_server`/`bulk_assign_cloudflare`),
  вернуть `BulkFullSetupResponse` (id для последующего write-back зоны из десктопа).

Бэкенд только персистит связки; зону/NS он не трогает (zero-knowledge).

### Фаза 2 — Десктоп: команда исполнения `[ ]`

Новый `commands/full_setup.rs` — Tauri-команда `domain_full_setup` (на ОДИН домен): по
`domain_id`+`cloudflare_account_id` зовёт `cf_create_zone` (если зоны нет), пишет
`cloudflare_zone_id` обратно (`domain_write_back`), по флагу `push_ns` —
`registrar_set_nameservers`. Реюз `cloudflare::client::create_zone` (+ поиск зоны по имени
через `list_zones`, отдельной `get_zone_by_name` в клиенте сегодня нет) и трейта
регистратора; наружу — структура со статусами шагов (зона / NS / что не удалось).
Массовость — на фронте: пачка гоняет ту же команду с конкуренцией (паттерн `mapWithLimit`
из `cfAutoBind.ts` / гейт как у `provision_bulk`). Зарегистрировать в `lib.rs`.

### Фаза 3 — Фронт: мастер + массовое действие `[ ]`

**Одиночный** (мастер из «Add Domain»): расширить `AddDomainModal.tsx` (или новый
`FullSetupModal.tsx`): поля Домен, Регистратор, Хостинг(сервер), Cloudflare-аккаунт +
тумблеры «Создать зону в Cloudflare», «Прописать NS у регистратора». Поток: `POST ""`
(создать домен) → (desktop) `domain_full_setup` → отчёт по шагам (зона создана / NS
прописаны / что не удалось), тон как у привязки.

**Массовый** (по выделенным): кнопка «Full setup» в `BulkActionToolbar.tsx` → диалог
(сервер + CF-аккаунт + регистратор + те же тумблеры) → `POST /domains/full-setup` →
(desktop) прогон `domain_full_setup` по пачке с конкуренцией → сводный отчёт (как
`CloudflareBindBanner`). Гейт «один прогон за раз», как у привязки/provision.

Desktop-only для шагов выполнения (зона/NS).

Уточнения UX (решения пользователя):
- **Счётчик доменов в выпадашках.** Сервер и CF-аккаунт показывать как «имя — N доменов»,
  наименее загруженные сверху (сортировка по возрастанию N). N — из локального списка
  `useDomains()` группировкой по `server_id` / `cloudflare_account_id` (считаем домены в
  SDMP, не живые зоны — быстро, работает и в вебе).
- **«Создать зону».** = `cf_create_zone` (POST /zones) — завести домен как зону в выбранном
  аккаунте, получить `zone_id` + NS; если зона уже есть, не дублировать. Инлайн-пояснение
  под тумблером.
- **Регистратор без API.** NS-API умеют только `hostiq` и `namecheap` (десктоп
  `make_service`, `registrars/mod.rs`). Хелпер `registrarSupportsNsApi(provider)` —
  общий с Кейсом 1 (`lib/registrarCaps.ts`, единственный источник правды, зеркалит
  десктоп): если провайдер не из этих двух или регистратор не выбран → **дизейблить только
  тумблер** «Прописать NS» + подсказка «нет API — пропишите NS вручную». Кнопка «Создать и
  настроить» остаётся активной.

## Переиспользуем (не плодим нового)

- Бэкенд: `create_domain`, `bulk_assign_server`, `bulk_assign_cloudflare` — `domain_service.py`
- Десктоп: `cloudflare::client::create_zone` / `list_zones`, `registrar_set_nameservers`,
  `domain_write_back`
- Фронт: `useCreateDomain` — `api/domains.ts`; `mapWithLimit` — `api/cfAutoBind.ts`;
  `registrarSupportsNsApi` — `lib/registrarCaps.ts` (из Кейса 1)

## Гарды корректности

- Zero-knowledge: бэкенд не ходит в Cloudflare/регистратор; зоны/NS — только десктоп.
- Full-setup идемпотентен (idempotency key); частичный успех — строки отчёта, не краш.
- Существующая зона не дублируется.
- Гейт «один прогон за раз» на массовом действии.

## Верификация

1. Мастер нового домена → `full-setup` создаёт домен+связки → десктоп заводит зону,
   (по тумблеру) NS → отчёт по шагам; повтор идемпотентен.
2. Регистратор без NS-API → тумблер NS дизейблен, домен и зона всё равно созданы.
3. Массовое действие по выделенным → сводный отчёт, частичные провалы строками.
4. Тесты точечно: бэкенд-тест эндпоинта full-setup; фронт — диалог и сборка отчёта.
