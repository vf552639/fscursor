# План: Шесть правок вкладки Domains и карточки домена

**Дата:** 2026-08-21
**Источник:** `task20.md` (корень репозитория) — претензии, собранные на живых данных после
редизайна вкладки (`2026-08-20-redizayn-vkladki-domains.md`, выполнен целиком).
**Связь с бизнесом:** принцип №6 CLAUDE.md — «не рисуй незнание здоровьем», и принцип №2 —
«плотность без тесноты». Вкладка Domains — главный экран продукта; сегодня она в трёх местах
говорит не то, что есть, а в трёх других — говорит невнятно.

Три из шести правок — настоящие дефекты (список спорит с карточкой про SSL; колонка Status
называет не то, что человек читает; правка срока не сохраняется), три — доводка вида и словаря
(лишняя строка NS на карточке, разнокалиберный ряд фильтров, двуязычные подписи).

Работа только фронтенд. Ни один запрос к API, Tauri-команда, миграция или правило подсчёта
не меняются: всё, что нужно фазе 1, **уже приезжает** в ответе `GET /domains`
(`backend/app/schemas/domain.py:123-124` → `frontend/src/api/domains.ts:49-50`).

### Решения, принятые с пользователем

| Вопрос | Решение |
|---|---|
| Язык вкладки (долг №6 плана редизайна — «решает пользователь») | Вкладка Domains **целиком на английский**, включая модалки, которые с неё открываются. |
| Перевод достаёт общие модули (`describeServerBinding`, `domainWord`), которые читает и карточка сервера | Принято: переводим и там. Русский вопрос из английской панели выделенных — хуже, чем перевод соседнего экрана. |
| Порядок исполнения | Все шесть фаз одной сессией, коммит на фазу, `tsc` + `vitest` после каждой. |
| Доказательство фикса срока (фаза 4) | **Отдельный коммит с красными тестами**, затем коммит с фиксом. Красное должно остаться в истории. |
| Живая приёмка в десктопе | За пользователем: агент её выполнить не может. |

## Acceptance criteria (что значит «готово»)

- [ ] Состояние SSL в строке списка и в карточке домена считается **одной функцией из одного
      источника** (`sslState` по снимку `fp_facts`); домен, ни разу не проверенный по SSH,
      читается `Not checked`, а не `No SSL`.
- [ ] Сортировка колонки SSL сортирует по тому же, что колонка показывает.
- [ ] Колонка называется `Setup`, подписи человеческие (`Deployed`, `Not set up`, …),
      наведение объясняет, что это ступень настройки внутри SDMP, а не здоровье сайта.
- [ ] Чипы среза подписаны теми же словами, что колонка.
- [ ] На карточке домена ровно один ответ про NS — живая карточка `NAMESERVERS`.
- [ ] `Expires: set date` сохраняется по уходу из поля и по `Enter`; `Escape` отменяет.
      Двойной записи нет, автоматического ретрая отвергнутой даты нет.
- [ ] Четыре контрола ряда фильтров — одной высоты, одной рамки, одного шрифта, со своей
      стрелкой у селектов.
- [ ] Ни одной русской подписи на вкладке Domains и в открывающихся с неё модалках.
- [ ] `npx tsc --noEmit` чисто; `npx vitest run --testTimeout=30000` — вся сюита зелёная.

## Edge cases (продумать заранее)

- **Домен без снимка вовсе** (`fp_facts === null`) и **домен со снимком, но без отметки времени** —
  оба уходят в `unchecked`; гейт на пару «факты есть, отметки нет» уже стоит в `snapshotOf`.
- **Протухший снимок**: `valid`/`missing` протухают в `unchecked`, `expired`/`expiring`
  переживают протухание (асимметрия свежести — уже в `sslState`, менять её нельзя).
- **Сортировка по SSL**: `unchecked` уходит в конец при ЛЮБОМ направлении (`null` из ранга),
  ровно как незнакомый статус в `domainStatusRank`.
- **Незнакомый статус домена** (пришёл с бэкенда новый) — подпись `Unknown`, не падение.
- **`last_provision_error`** остаётся сильнее подсказки в `title` бейджа статуса.
- **Пустой инпут срока** по-прежнему означает «снять срок» и записывается `null`, а не `""`.
- **Провал записи срока**: уход из поля НЕ повторяет только что отвергнутую дату; ретрай —
  только явным действием.
- **Ширина колонки SSL** должна вмещать `No certificate` — самую длинную из новых подписей.
- **Тесты, цепляющиеся за русские подписи**, — их девять файлов; перевод обязан их починить,
  а не обойти.

### Фаза 1 — SSL в списке читает то же измерение, что карточка `[x]`

**Дефект.** Домен, у которого карточка показывает `SSL: Valid`, в таблице стоит с `No SSL`.
Источника два: строка читает `domain.ssl_status` — НАШУ запись момента provision
(`desktop/src-tauri/src/domains/provision.rs:894` — единственный писатель; `domain_service.py:85,121`
гасит её в NULL при переезде домена на другой сервер), карточка считает
`sslState(domain.fp_facts?.ssl, domain.fp_facts_at)` (`DomainDetailModal.tsx:146`) — живое
измерение сертификата по SSH. Домен, настроенный мимо SDMP, имеет пустой `ssl_status` навсегда,
и `No SSL` про него — неправда.

**Решение:** строка показывает `sslState` из снимка, теми же подписями, что карточка
(`SSL_BADGE`, `lib/domainFacts.ts:242-249`): `Valid / Expiring soon / Expired / No certificate /
Read error / Not checked`.

- `components/domains/types.ts` — `DomainUI` получает `ssl: DomainFacts["ssl"] | null` и
  `facts_at: string | null`; `toDomainUI` (:47) их пробрасывает. Это единственное место
  переименования полей, второго заводить нельзя.
- `components/domains/DomainRow.tsx:201-202, 286-299` — вместо `d.ssl_status === "active"`
  считается `sslState(d.ssl, d.facts_at, now)` (`now` в строке уже есть, :196); подпись и цвет —
  из `SSL_BADGE` + `STATUS_PILL[variant]`. `title` называет возраст снимка, а не `ssl_status`.
- `components/domains/DomainTable.tsx` — ширина колонки SSL в `<colgroup>` под `No certificate`.
- `lib/domainFacts.ts` — новый `sslStateRank(state): number | null` рядом с `sslState`
  (`unchecked → null`).
- `components/domains/sortDomains.ts:113` — сортировка колонки переезжает на `sslStateRank`;
  второй ключ — `ssl.expires_at` из снимка вместо `ssl_expires_at`.
- `sslStatusRank` / `SSL_STATUSES` в `lib/domainStatus.ts` остаются без потребителя —
  **удалить** вместе с их тестами, а не оставлять мёртвыми.
- **НЕ трогаем:** `lib/domainCounts.ts:88` («Failed at SSL» по `ssl_status === "error"`) и строку
  `SSL at provision` в `DomainOverviewTab.tsx:125-130` — обе про исход provision, а не про
  сертификат на сервере. После фазы они остаются единственными поверхностями `ssl_status`.

**Долг плана редизайна, который закрывается сам:** №1 (расхождение `text.faint` у `No SSL`)
и №3 («колонка сортирует по частично невидимому»).

### Фаза 2 — колонка Status объясняет себя `[x]`

**Дефект.** Колонка называет не здоровье сайта, а ступень настройки внутри SDMP:
`new → ns_pending → ns_ok → provisioning → site_created → ssl_pending → active → failed`
(`lib/domainStatus.ts:39-48`, канон — `backend/app/core/constants.py:23-31`). `ACTIVE` стоит
только у доменов, прошедших provision **из приложения**; заведённые вручную остаются `NEW`
навсегда. Подпись сегодня — просто `status.toUpperCase()`, и объяснить себя ей нечем.

- `lib/domainStatus.ts` — записи `DOMAIN_STATUSES` получают `label` и `hint`; `domainStatusLabel`
  берёт подпись оттуда вместо `status.toUpperCase()` (комментарий модуля «подпись здесь НЕ
  хранится» переписать — он станет неправдой). Новый `domainStatusHint(status)`.
  Подписи: `new → Not set up`, `ns_pending → Waiting NS`, `ns_ok → NS set`,
  `provisioning → Deploying`, `site_created → Site created`, `ssl_pending → Issuing SSL`,
  `active → Deployed`, `failed → Failed`, незнакомый → `Unknown`.
- `components/domains/DomainStatusBadge.tsx:59` — подпись меняется сама; `title` собирается из
  `domainStatusHint`, а `last_provision_error`, когда он есть, по-прежнему сильнее. Бейдж рисуют
  ДВА места — строка и шапка карточки (`DomainModalHeader.tsx:87`), — правка приезжает в оба.
- `components/domains/DomainTable.tsx:77` — заголовок `Status` → `Setup`, ключ сортировки
  `status` не меняется; у заголовка `title` «Setup stage inside SDMP, not site health».
  Заодно снимается путаница с колонкой `Status` вкладки Servers, где смысл другой.
- `components/domains/DomainStatChips.tsx` — подписи чипов к тем же словам
  (`Deployed` / `Not set up` / `Failed`), иначе чип `Active` фильтровал бы то, что в колонке
  подписано `Deployed`.

### Фаза 4 — правка срока сохраняется по Enter и по уходу из поля `[x]`

**Дефект.** Единственный вход в запись — событие `change` нативного `<input type="date">`
(`DomainExpiryField.tsx:175-178`); `onBlur` пишет РОВНО ОДИН случай — пустое поле (:196-199),
обработчика `Enter` нет вовсе (комментарий :186-188 объясняет это тем, что «дата уже записана
на change»). Симптом подтверждён пользователем: **поле схлопывается и снова показывает
`set date`, красной ошибки нет** — то есть `commit` не вызывался ни разу. Тесты этого не ловят
по построению: все 12 сценариев дёргают `fireEvent.change` напрямую
(`DomainExpiryField.test.tsx:198-309`), то есть проверяют путь, который в WebKit и не срабатывает.
Бэкенд ни при чём: `PUT /domains/{id}` принимает `expiry_date` (`schemas/domain.py:63`),
`model_dump(exclude_unset=True)` различает «не прислали» и «null».

Причина — не бэкенд и не мутация, а отсутствие запасного входа в `commit`.

**Шаг 4а — красные тесты (отдельный коммит).** `components/domains/DomainExpiryField.test.tsx`:
(а) `fireEvent.blur(input, { target: { value: PICKED } })` **без** `change` пишет дату один раз —
точная модель отказа в WebKit; (б) `Enter` пишет и закрывает поле; (в) `Escape` закрывает без
записи; (г) `blur` после провала той же даты не шлёт второй `PUT`. Прогон обязан быть КРАСНЫМ,
и это надо показать выводом.

**Шаг 4б — фикс.** `components/domains/DomainExpiryField.tsx`:
- `onBlur` (:196-199) коммитит ЛЮБОЕ значение, а не только пустое: `commit(e.target.value)`.
  Двойной записи не будет — гард `if (next === (shown ?? null)) return` в `commit` (:148) уже
  гасит повтор после удачного `change`, и тест «выбор в пикере пишется один раз» (:273) это
  сторожит.
- Новый `onKeyDown`: `Enter` → `commit(draft ?? "")` + закрыть поле; `Escape` → закрыть без записи.
- Единственный новый гард: на `blur` НЕ повторять запись, которая только что провалилась
  (`update.isError && draft === edit?.value`) — иначе уход из поля с отвергнутой датой дёргал бы
  ретрай, которого не просили. Ретрай остаётся доступен явным действием (новый выбор / `Enter`).
- Комментарии :186-188 и :196-199 переписать: они утверждают ровно то, что оказалось неверным.

Все 12 существующих сценариев обязаны остаться зелёными **без правок**.

### Фаза 5 — ряд фильтров одним набором `[x]`

**Доводка.** `CONTROL_STYLE` (`DomainFilters.tsx:50-54`) задаёт селектам только рамку, радиус и
кегль; всё остальное остаётся дефолтом примитива `Sel` (`Primitives.tsx:277-282`):
`padding 8px 12px` против `8px 14px` у поля, `box-sizing` не задан, `font-family` системный,
`color: #111` вместо токена — плюс нативная стрелка WebKit.

- `components/domains/DomainFilters.tsx` — `CONTROL_STYLE` дорастает до полной геометрии
  контрола: `padding: "8px 14px"`, `boxSizing: "border-box"`, `fontFamily: "inherit"`,
  `color: tokens.text.body`, `background: tokens.surface.base`, `outline: "none"`.
  Селекты дополнительно получают `appearance: "none"` и свою стрелку — `backgroundImage`
  с inline SVG в `data:`-URI (CSP десктопа это разрешает: `img-src 'self' data:`,
  `desktop/src-tauri/tauri.conf.json:24`), `backgroundRepeat/Position` и правый `paddingRight`
  под неё. Одинаковая высота получается из общего `padding` + `border-box`.
- Примитив `Sel` (`Primitives.tsx:277`) **не трогаем** — его рисуют Servers, Activity и Settings,
  и правка там протащила бы редизайн одной вкладки на всё приложение (та же причина, по которой
  `CONTROL_STYLE` вообще заведён).
