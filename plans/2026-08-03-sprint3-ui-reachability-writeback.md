**Дата:** 2026-08-03
**Связь с бизнесом:** приложение должно стать реально юзабельным «для себя» end-to-end
(`.business/goals/` — фаза A «продукт работает для владельца»). Ядро исполнения написано,
но до него не дотянуты кнопки, а результаты исполнения не сохраняются.

Источник: `sprint3.md` в корне репозитория.

## Acceptance criteria (что значит «готово»)

- [ ] Каждая из 4 команд Группы A вызывается кликом в UI в десктопе (не deep link) и
      имеет web-fallback через `OpenInDesktop`/`sdmp://`.
- [ ] После успешного provision/install несекретные поля результата доезжают до сервера
      (проверяется повторным запуском: срабатывают гарды `ssl_exists` / «уже установлен»).
- [ ] Ни один пароль (`db_password`, `ftp_password`, пароль панели) не уходит на сервер.
- [ ] `pytest`, `cargo test`, `vitest` зелёные; `tsc` не хуже преэкзистующего долга.

## Edge cases (продумать заранее)

- Web-режим: любая мутация недоступна → `OpenInDesktop` с корректным `sdmp://`-действием;
  deep-link парсер (`parseDeepLinkAction`) знает только 3 хоста — новые действия либо добавляем,
  либо не выдаём как ссылку.
- Двойной клик по provision/install → кнопка disabled на время `isPending`; на стороне Rust —
  идемпотентность уже есть.
- Write-back упал (сеть/401) → операция на сервере уже выполнена; write-back best-effort,
  не роняет команду, но пишет предупреждение и событие прогресса.
- Zero-knowledge: write-back шлёт только метаданные. Пароли остаются в возвращаемом в UI
  результате и показываются один раз.
- Обратная совместимость: `with_db: Option<bool>` в Rust — старый фронт продолжает работать.
