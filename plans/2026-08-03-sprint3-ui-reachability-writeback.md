**Дата:** 2026-08-03
**Связь с бизнесом:** приложение должно стать реально юзабельным «для себя» end-to-end
(`.business/goals/` — фаза A «продукт работает для владельца»). Ядро исполнения написано,
но до него не дотянуты кнопки, а результаты исполнения не сохраняются.

Источник: `sprint3.md` в корне репозитория.

## Acceptance criteria (что значит «готово»)

- [ ] Каждая из 4 команд Группы A вызывается кликом в UI в десктопе (не deep link) и
      имеет web-fallback через `OpenInDesktop`/`sdmp://`.
- [ ] После успешного provision/install несекретные поля результата доезжают до сервера
      (проверяется повторным запуском: срабатывают гарды `ssl_exists` / «уже установлен»).
- [ ] Ни один пароль (`db_password`, `ftp_password`, пароль панели) не уходит на сервер.
- [ ] `pytest`, `cargo test`, `vitest` зелёные; `tsc` не хуже преэкзистующего долга.

## Edge cases (продумать заранее)

- Web-режим: любая мутация недоступна → `OpenInDesktop` с корректным `sdmp://`-действием;
  deep-link парсер (`parseDeepLinkAction`) знает только 3 хоста — новые действия либо добавляем,
  либо не выдаём как ссылку.
- Двойной клик по provision/install → кнопка disabled на время `isPending`; на стороне Rust —
  идемпотентность уже есть.
- Write-back упал (сеть/401) → операция на сервере уже выполнена; write-back best-effort,
  не роняет команду, но пишет предупреждение и событие прогресса.
- Zero-knowledge: write-back шлёт только метаданные. Пароли остаются в возвращаемом в UI
  результате и показываются один раз.
- Обратная совместимость: `with_db: Option<bool>` в Rust — старый фронт продолжает работать.

> в argv схлопывается в `opaque_exit`, `Debug` снят или замаскирован на всех структурах с
> секретами, 12 точек `tracing::` не несут пароль.

## Вне объёма

- **Группа C (сбор метрик серверов)** — по рекомендации самого `sprint3.md` не тянем в спринт:
  на юзабельность provisioning не влияет. Отдельным планом.
- Создание отсутствующих бэкенд-эндпоинтов исполнения (`install-fastpanel`, `set-ns` и т.п.) —
  архитектурно неверно (исполнение живёт в десктопе); вместо этого мёртвые вызовы переводятся
  на Tauri-команды.
- **Шесть кнопок того же мёртвого класса в `DomainDetailModal`** — `Create Site`, `Create DB`,
  `Request SSL`, `Refresh SSL`, `Cancel SSL`, `Save nginx override` — бьют в
  `POST /domains/{id}/{create-site,create-db,ssl-request,ssl-cancel,nginx-override}`, которых
  на бэкенде нет. Требуют разбора «что переводится на существующие Tauri-команды, а что
  удаляется» — это объём отдельной фазы, а не хвост фазы 5. Отдельным планом. Вместе с ними
  идут: мёртвые схемы `backend/app/schemas/domain.py` (`BulkSetNSRequest`, `BulkSetNSResponse`,
  `SetNSResponse`, `CreateSiteRequest`, `NginxOverrideRequest`, `RefreshSslResponse` — NB:
  фронтовый тип `SetNSResponse` в `api/domains.ts` живой, его придётся переименовать) и
  правка `docs/CURRENT_STATUS.md` / `docs/PROJECT_OVERVIEW.md`, где в одной строке с
  вычеркнутым `mark-ns-set` остались `create-db`, `ssl-*`, `nginx-override`, `bulk-full-setup`
  и Celery-таски (`check_ns` и др.), которых тоже нет — в `backend/app/tasks/` лежит только
  `renewal_task.py`. Править их надо разом, иначе документ уверенно врёт про остаток.
- **Обход гейта у `sdmp://install-fastpanel`** (найдено ревью фазы 6, дефект старше спринта):
  `lib/deepLink.ts` зовёт `invokeSynced("install_fastpanel", …)` напрямую, мимо
  `installFastPanelKey(id)`, а кнопка в `ServerDetail` блокируется чтением того же
  `MutationCache`. Значит после запуска по ссылке кнопка «Install» остаётся активной →
  второй инсталлятор поверх первого на живом сервере (30+ минут, `apt upgrade`). Rust не
  страхует: проверка «FastPanel already installed» читает состояние **до** того, как первый
  прогон что-то поставил. Лечится одной строкой по образцу `runProvisionDomain` из фазы 6 —
  рецепт готов, задача парная к уже сделанной.
- **Ошибка одиночного provision нигде не отображается** — `singleProvision.error` не
  отрендерен ни разу; провал виден только по тостам прогресса. Дефект старше спринта, но
  после появления `PROVISION_DOMAIN_KEY` поверхность стоит ~10 строк.

## ГЛАВНОЕ, что вскрыло финальное ревью: секрет невозможно ввести в принципе

Каждая фаза проверяла «кнопка → команда → write-back» и ни одна не проверила, что команда
вообще может отработать. **Пути записи блоба секрета не существует нигде.** Проверено
независимо по четырём точкам:

1. `backend/alembic/versions/011_zero_knowledge_v1.py:229-235` дропает `ftp_password_encrypted`,
   `db_password_encrypted`, `fastpanel_password_encrypted`, `api_token_encrypted`,
   `api_key_encrypted`, `api_secret_encrypted` — **без единого `op.execute`**, конвертирующего
   их в `blob_storage`. Все `*_blob_id` у всех строк `NULL`.
2. `frontend/src/lib/crypto.ts:115` `encryptBlob` — **ноль продовых вызывающих** (grep находит
   только само определение). `vault_put_blob` зарегистрирована в `lib.rs:42` и не зовётся из
   фронта ни разу.
3. Формы шлют плейнтекст в поля, которых нет в схемах: `pages/Servers.tsx:84`,
   `ServerDetail.tsx:98`, `Cloudflare.tsx:264,657`, `Settings.tsx:74,260` шлют `ssh_password`
   и т.п., а `backend/app/schemas/server.py` знает только `*_blob_id`.
4. Ни в одной схеме нет `extra="forbid"` → Pydantic по умолчанию `ignore`, а
   `model_dump(exclude_unset=True)` берёт только объявленные поля. Итог: **200 OK и ничего
   не сохранено.**

Сценарий: пользователь добавляет сервер с SSH-паролем → 200 → `has_ssh: false`, баннер
«SSH-доступ не настроен» никуда не делся. «Добавить SSH» → снова 200 → снова ничего.
«Install FastPanel» → `commands/provision.rs:975`, `"server has no ssh_password_blob_id"`.
То же у `provision_domain`, `registrar_set_nameservers` и всех `cf_*`.

**Сквозной сценарий приёмки из `sprint3.md:91-99` не проходится дальше шага 1.** Спринт этого
не создал и строго улучшил состояние, но заявленная бизнес-цель («юзабельно для себя
end-to-end») не достигнута и не будет достигнута никаким количеством дотянутых кнопок.
**Это задача №1 следующего спринта**, и она больше всего, что осталось в отложенном.

## Долг, обнажённый спринтом (в порядке важности)

1. **Путь записи блоба секрета** — см. выше. Блокирует бизнес-цель фазы A целиком.
2. **`extra="forbid"`** на `ServerCreate`/`ServerUpdate`/`CloudflareAccount*`/`RegistrarAccount*`
   + вычистить `ssh_password`/`fastpanel_password`/`api_token`/`api_key`/`api_secret` из
   TS-типов: плейнтекст перестанет уходить на провод, а молчаливая потеря станет громкой 422.
3. **`sdmp://bulk-provision`** — единственная ветка deep link, оставшаяся прямым
   `invokeSynced` мимо гейта и с выбросом результата. `site_only=false` ⇒ FTP-аккаунт
   создаётся на каждом домене, пароли N аккаунтов теряются безвозвратно. Гард
   `bulk_run_status` ключуется на **наборе** id и по отдельному домену не защищает.
   Парадокс: десктопная кнопка Provision в тулбаре бьёт в 404, а веб-ссылка работает
   по-настоящему — веб функциональнее десктопа и он же опасен.
4. **Продюсер `last_provision_error`** — колонка есть, тестов два, пишущего кода ноль:
   единственное присваивание в Rust это `Some(None)`, то есть сброс. На провале provision
   `stepped?` возвращается **до** блока write-back, поэтому упавший прогон не пишет ничего.
   Следствие: `failedAtSslCount` не может стать ненулевым, «Last error» всегда «—» —
   упавший provision не виден сегодня ни в одной точке UI.
5. **Проверки существования БД и FTP-аккаунта.** Имя базы детерминированное (`{slug}_db`),
   проверки нет; на повторе срабатывает mysql-fallback с `CREATE USER IF NOT EXISTS`, который
   существующему пользователю пароль **не меняет**. Команда возвращает 0 и свежий пароль,
   модалка показывает его как «copy them now» — и он не аутентифицирует. Чекбокс `withDb`
   этого спринта сделал путь досягаемым.
6. **ZK-тест `test_provision_writeback.py:172` частично холостой:** `secret not in r.text`
   проходит потому, что у `DomainResponse` нет поля под пароль, — он прошёл бы и в мире, где
   плейнтекст-колонка существует и в неё только что записали. Проверять надо по БД.
   Там же: кросс-юзерные 404 не имеют позитивного контроля URL (опечатка в пути даст тот же 404).
7. **Свести к одной форме** гейт двойного запуска (сейчас три) и формулировку «только
   десктоп» (сейчас три: `desktopOnly()`, `requireDesktop()`, литерал `DESKTOP_ONLY_NOTE`).
   Гейт Set NS перевести на `MutationCache` — сейчас ошибка живёт в кэше, а гейт локальный.
8. **Гард полноты `PROVISION_STEP_LABEL`** (14 шагов) по образцу двух существующих гардов
   для `fastpanel:progress` и `audit:progress` — забытый шаг здесь молча невидим.
9. **`SECRET_KEY_MARKERS` += `secret`, `token`** (`api_secret` в кодовой базе уже есть);
   в доккоммент `audit_redact.rs` — строчку про обход гарда через `api_request`/`request_raw`.
10. **Валидация `fastpanel_url`/`fastpanel_user`** — распарсенный вывод инсталлятора уезжает
    на сервер и в аудит без проверки; `url_regex` матчит `https://admin:s3cr3t@ip:8888/`,
    а гард по именам поле `url` пропустит.
11. **`GET /api/domains/failed-export.csv` затенён** `GET /api/domains/{domain_id}` (объявлен
    выше по файлу) — всегда 422/401.
12. **Мёртвые схемы `DomainDbCredentials`/`DomainFtpCredentials`** с полями `*_password: str`
    — удалить вместе с остальными, чтобы не воскресли.
