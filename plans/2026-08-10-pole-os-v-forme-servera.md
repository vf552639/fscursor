# План: поле OS в форме сервера — чистые имена ОС

## Context (зачем)

В форме **Add Server** поле «OS» сейчас предлагает три подробных варианта с версией и
архитектурой: `Ubuntu 22.04 LTS (x86_64)`, `Ubuntu 20.04 LTS (x86_64)`, `Debian 12 (x86_64)`.
Пользователю версия здесь не нужна — важно только семейство ОС, потому что от него зависит
установка FastPanel: десктоп по имени ОС выбирает пакетный менеджер (`apt` для Debian/Ubuntu,
`yum` для RHEL-семейства). Нужно оставить в списке только сами названия ОС и покрыть пять
поддерживаемых: **Debian, Ubuntu, CentOS, AlmaLinux, Rocky Linux**. Значение уже сохраняется
и используется установщиком — менять цепочку хранения не требуется.

Решения пользователя:
- OS выбирается **только при создании** сервера (как сейчас); отдельного редактирования на
  странице сервера не добавляем.
- Поле — **закрытый список** из пяти имён (строгий `<select>`), без произвольного ввода.

## Что уже работает (не трогаем)

Цепочка сохранения `os` полностью готова:
- Backend: колонка `servers.os` (`String(64)`) — [backend/app/models/server.py:30](backend/app/models/server.py) —
  проходит через `ServerCreate.os` и `server_service` без изменения формата.
- Desktop: `install_fastpanel` читает `os` из кэша и передаёт в
  `update_command(os)` — [desktop/src-tauri/src/provision/fastpanel_install.rs:17](desktop/src-tauri/src/provision/fastpanel_install.rs) —
  которая по подстроке `cent|rhel|rocky|alma|fedora` (lowercase) выбирает `yum`, иначе `apt`.

Проверка соответствия пяти новых значений этой логике:

| Значение `os` | lowercase     | Ветка `update_command` |
| ------------- | ------------- | ---------------------- |
| `Debian`      | `debian`      | apt (default) ✓        |
| `Ubuntu`      | `ubuntu`      | apt  ✓                 |
| `CentOS`      | `centos`      | yum (`cent`) ✓         |
| `AlmaLinux`   | `almalinux`   | yum (`alma`) ✓         |
| `Rocky Linux` | `rocky linux` | yum (`rocky`) ✓        |

Все пять значений уже корректно разруливаются существующей логикой — **изменения нужны только
во фронтенде**. Старые серверы с прежними строками (`Ubuntu 22.04 LTS (x86_64)` и т. п.)
остаются валидными (ветка apt), миграция данных не требуется.

## Изменения

### [x] Фаза 1. Пять чистых имён в форме

Единственный файл: [frontend/src/pages/Servers.tsx](frontend/src/pages/Servers.tsx),
компонент `AddServerModal`.

1. **Список опций.** Заменить три захардкоженных `<option>` в `<Sel>` (строка 115) на пять
   чистых имён. Для читаемости вынести их в локальную константу рядом с компонентом:

   ```tsx
   const OS_OPTIONS = ["Debian", "Ubuntu", "CentOS", "AlmaLinux", "Rocky Linux"] as const;
   ```

   и рендерить `OS_OPTIONS.map(o => <option key={o} value={o}>{o}</option>)`. Явный `value`
   делает сохраняемое значение независимым от текста лейбла (сейчас `value` нет и уходит сам
   лейбл — оставляем поведение «value = имя ОС», но уже осознанно).

2. **Дефолт state.** Строка 37: `useState("Ubuntu 22.04 LTS (x86_64)")` → `useState("Ubuntu")`
   (Ubuntu — самый частый выбор; поле обязательно не даёт уйти пустым, что важно: пустой `os`
   блокирует установку FastPanel).

Ничего в `handleAdd`, API-клиенте, бэкенде и десктопе менять не нужно — `os: os` уже уходит в
`create.mutateAsync` (строка 84).

### [x] Фаза 2. Закрепить контракт «список во фронте ↔ матчер в Rust»

Пункт 4 раздела «Проверка» ниже был помечен как опциональный — сделан. Существующие тесты
`update_command` покрывали строки **с версиями** (`Ubuntu 22.04`, `CentOS 7`, `AlmaLinux 9`),
то есть ровно тех пяти значений, которые теперь шлёт форма, среди кейсов не было.
Добавлен тест `update_command_covers_every_ui_os_option` в
[desktop/src-tauri/src/provision/fastpanel_install.rs](desktop/src-tauri/src/provision/fastpanel_install.rs).

Важное ограничение, зафиксированное в комментарии к тесту: он **не** сверяет список с фронтом
(литералы захардкожены в Rust) — он фиксирует поведение матчера на Rust-стороне. При правке
`OS_OPTIONS` тест нужно править руками.

## Проверка

1. `cd frontend && npm run build` (или `tsc --noEmit`) — тип `os: string` не меняется, сборка
   должна пройти.
2. Запустить фронт/десктоп, открыть **Add Server**: в поле OS ровно пять вариантов —
   Debian, Ubuntu, CentOS, AlmaLinux, Rocky Linux; по умолчанию выбран Ubuntu.
3. Создать сервер с `CentOS` (или Rocky/Alma) и с `Ubuntu`. Убедиться в БД/через API, что в
   `servers.os` лежит именно выбранное чистое имя (`CentOS`, `Ubuntu`).
4. Логическая проверка установщика (без реальной установки): для `os = "CentOS"`
   `update_command` даёт `yum -y update`, для `os = "Ubuntu"` — `apt-get update && ... upgrade`.
   Покрыто существующими юнит-тестами в `fastpanel_install.rs` (строки 285–306) — при желании
   добавить в них кейсы `"CentOS"`, `"AlmaLinux"`, `"Rocky Linux"`, `"Debian"`, `"Ubuntu"`.

### Осталось (долг, за рамками этого плана)

1. **Массовый импорт заводит серверы без `os`, и починить это потом негде.** CSV в
   [frontend/src/components/ServerBulkImportDialog.tsx](frontend/src/components/ServerBulkImportDialog.tsx)
   — `name,ip,ssh_user,ssh_password,ssh_port,provider`, колонки `os` нет;
   `bulk_import_service.py` собирает `ServerCreate` без неё. Итог: `os = NULL`, установка
   FastPanel отказывает («server has no OS recorded — set it before installing»), а «set it»
   сделать нечем — OS выбирается только при создании, редактора OS на странице сервера нет
   (осознанное решение этого плана). Тупик преэкзистующий, но именно этот план делает форму
   создания единственным входом для `os`. Лечение: либо колонка `os` в импорте, либо
   редактирование OS в `ServerDetail`.
2. **`update_command` — `else`-fallback, а не whitelist.** Нераспознанная ОС молча получает
   `apt`; на RHEL-подобной машине это провал установки с невнятным кодом возврата. Поведение
   легаси, теперь задокументировано в двух местах; настоящее лечение — явная ошибка на
   нераспознанном имени (отдельное продуктовое решение).
3. **Синхронность `OS_OPTIONS` с Rust-матчером ничем не проверяется** — только комментариями
   с обеих сторон. Автосверка потребовала бы генерации списка или общего источника.
