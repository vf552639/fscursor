# План: Hostiq на реальном API (DI-API v3) + чтение NS из реестра через RDAP

**Дата:** 2026-08-17
**Связь с бизнесом:** прямое закрытие обещания продукта — «поштучно или пачками разворачивать
сайты, выпускать SSL, **прописывать NS**» (`.business/products/`). До этой работы смена NS не
работала ни у одного домена Hostiq, а бейдж делегирования у них был серым всегда.
Источник: `task13.md` (исполнен, удалён из корня по правилу `plans/README.md` — живёт в истории git).

## Отчего это не «доработка», а починка неработавшего

Живая проверка боевым токеном (127 доменов, 120 активных) установила три факта, каждый из
которых снимает предыдущее объяснение симптома:

1. **Клиент Hostiq в десктопе был ВЫДУМАН.** Он бил в `https://hostiq.ua/api` с
   `Authorization: Bearer`. Такого хоста нет: `/api/domains` отдаёт 404 HTML. Эндпоинта
   `PUT /domains/{d}/nameservers` не существует. При этом `registrarCaps.ts` рисовал у Hostiq
   живую кнопку «Прописать NS» — то есть кнопка гарантированно падала.
2. **Чтения NS у API Hostiq нет и быть не может.** В `domain/list` нет ни одного поля с
   nameservers — проверено на всех 127 доменах. `get_nameservers` у Hostiq не «сломан», он
   невозможен.
3. **Способа прочитать NS извне регистратора в проекте не было вообще** — ни DNS-резолвера, ни
   WHOIS/RDAP. `dnspython` в `backend/requirements.txt` стоял и не использовался ни строчкой,
   а `docs/TECH_STACK.md` описывал несуществующий «NS resolver fallback».

## Acceptance criteria (что значит «готово»)

- [x] Клиент Hostiq говорит с настоящим DI-API v3 и умеет менять NS.
- [x] Форма аккаунта Hostiq просит один токен, а не пару email + ключ.
- [x] NS домена читаются **из реестра** (RDAP) для ВСЕХ провайдеров, включая ручные.
- [x] Бейдж делегирования у домена Hostiq и у домена ручного провайдера перестал быть серым по
      построению.
- [x] Чтение NS через API регистратора удалено целиком, а не оставлено вторым путём.
- [x] Контракт DI-API v3 и его молчаливые ловушки задокументированы (`docs/HOSTIQ_API.md`).
- [ ] **Живая приёмка человеком** в собранном приложении — см. раздел ниже. Ни один агент к
      боевым Hostiq/Cloudflare доступа для мутаций не имел.

## Edge cases (продуманы, каждый закрыт кодом и тестом)

- **Аккаунт больше 1000 доменов.** `limit` выше 1000 API молча откатывает к 100 — значит «весь
  список одним запросом» невозможен. Пагинация; признак конца — пустая страница, `total` только
  верхняя граница (исчезни поле `total` — листинг иначе молча обрезался бы первой страницей и
  отдавался как полный). `MAX_PAGES = 50` от API, игнорирующего `offset`: там ошибка, а не
  усечённый список.
- **Ответ не от Hostiq** (страница прокси, капча, WAF) с кодом 200. Нераспознанное тело — не
  данные: иначе `set_nameservers` вернул бы `Ok(true)`, а `ns_outcome_plan` записал бы
  `ns_status = "ok"` и строку `registrar.ns_set` в audit log про смену, которой не было.
- **Тело говорит «записей N», распознали ноль** (переименовался ключ конверта). Это «ответ не
  распознан», а не пустой аккаунт: иначе клиент обвинял бы аккаунт пользователя в отсутствии
  домена, который тот же экран показывает.
- **Zero-knowledge.** RDAP получает только имя домена — не секрет. Токен Hostiq уезжает
  ЗАГОЛОВКОМ, поэтому транспортную ошибку можно печатать как есть (у соседнего Namecheap
  наоборот: credential в query-строке, и адрес из текста ошибки вычищается — разница между
  клиентами есть следствие разных способов авторизации, а не недосмотр).
- **Двойной клик по массовому прогону.** Не менялось: гейт «один прогон за раз» на клиенте.

### Фаза 1 — Переписать клиент Hostiq `[x]`

**Что нашло ревью и чего в спеке не было:**
- **Успех выводился из одного HTTP-статуса.** Нераспознанное 2xx-тело проезжало как данные →

- **Пропавший `total` тихо усекал листинг** до первой страницы (см. edge cases).
- **`total` против нуля распознанных записей** — ложное «домена нет в аккаунте» (см. edge cases).
- **Токен от человека мог уронить приложение паникой**: `format!().parse().unwrap()` падал на
  вставке с переводом строки из личного кабинета.

25 тестов, все гейты проверены **мутацией** — снятие каждого роняет адресный тест. Именно
мутационная проверка нашла, что фолбэк на `count` не держался ничем.

### Фаза 2 — Форма Hostiq: токен вместо email + ключа `[x]`

Коммиты `fe3a29b` → `19e2fac` → `e06c31d` → `64db0d8`. Каталог получил `needsApiUser` и
`apiKeyLabel`; поле `API User` показывается по новому признаку, а не по «есть ли вообще API»;
`REGISTRAR_SECRETS` стала вычисляемой (`useMultiSecretSave` переделывать не потребовалось —
подписи лежат в ref).

**Решение оркестратора против первого варианта реализации:** у Hostiq `api_user` вычищается и
при ПРАВКЕ аккаунта, а не только при создании. Правило «чего не показываем, того не меняем»
верно в общем случае, но здесь поле не «не показано», а мертво по контракту: DI-API v3 не
использует его ни в одном запросе, а унаследованный email продолжал светиться подписью
`Hostiq · admin@…` на карточке, то есть врал про то, чем аккаунт настроен. Момент чистки —
тот самый, когда владелец и так обязан зайти за новым токеном.

**Регрессия, которую породила эта же правка, и её починка:** признак `needsApiUser` ложен не
только у Hostiq, но и у любого провайдера ВНЕ каталога. Первая версия стирала `api_user` у
аккаунта `provider: " namecheap "` (строка с пробелами из чужого импорта) при переименовании —
невидимо, потому что поля на экране нет. Граница переехала на «опознан ли провайдер»
(`apiUserDeadByContract` в каталоге): у опознанного API-провайдера без `needsApiUser` колонка
мертва по контракту, у неопознанного мы про его контракт не знаем ничего.

Попутно убран `apiUserSuffix`: он стал пустым у обоих провайдеров, но имел ДВА потребителя с
разным поведением (создание рисовало суффикс, правка нет) — задел, который при использовании
ломается, хуже отсутствующего.

### Фаза 3 — Чтение NS из реестра (RDAP) `[x]`

Новый `desktop/src-tauri/src/rdap.rs`, команда `domain_registry_nameservers`, фронтовая
`api/rdap.ts` с `useRegistryNameservers` (staleTime 5 мин) и `foldRegistryNameservers`.
Коммиты `7b2f949` → `14bca33`.

Три состояния описывает тегированный enum `RegistryNameservers::{Registered{nameservers},
NotRegistered, Unavailable{reason}}`, а не `Result<Vec<String>, _>`: в `Result` «не найден» и
«не смогли спросить» неотличимы, а `Registered{[]}` («зарегистрирован, но не делегирован» —
родная форма RDAP, ключа `nameservers` в ответе просто нет) неотличим от «не смогли».

**Самая дорогая находка сессии.** Ревью обнаружило, что модуль **не работал ни на одном
домене**: `reqwest` не ставит `User-Agent` по умолчанию, а Cloudflare перед `rdap.org` режет
безUA-трафик — 403 на каждый запрос. Все 11 тестов при этом были зелёными, потому что
`wiremock` — не Cloudflare, он отвечает на что угодно. А живые проверки в докстринге снимались
`curl`'ом, который ставит `User-Agent` сам: **обоснование кода было получено другим
инструментом, чем описываемый код.** Это ровно тот класс ошибки, ради которого весь `task13` и
затевался. Лечение: `.user_agent(concat!("sdmp/", env!("CARGO_PKG_VERSION")))` плюс
`#[ignore]`-проба `live_probe_confirms_what_this_module_claims`, ходящая в настоящий `rdap.org`,
чтобы этот класс нельзя было повторить.

Там же закрыты: любой JSON-объект зачитывался как «реестр ответил» (RDAP-ошибка в теле при 2xx,
`nameservers` не массивом, элемент без `ldhName` — последнее давало **усечённый** список, то
есть «расходится» на верном делегировании); имя домена уходило в путь URL без экранирования
(`"%2e%2e/ip/8.8.8.8"` уводил запрос на другой RDAP-эндпоинт, чей 200-ответ читался как
«зарегистрирован, не делегирован»); `expect("reqwest")` панике́й обходил все три состояния,
оставляя карточку в «загружаю» навсегда.

**Осознанный компромисс:** `rdap.org` — сторонний редиректор, то есть имена доменов уходят
третьей стороне. Прямой путь через IANA bootstrap (`data.iana.org/rdap/dns.json`) убирает
посредника, но не покрывает часть TLD, включая `.ua`, который `rdap.org` отдаёт.

Живая проверка **этим клиентом** (не curl): `betify2.com` → `ada/bob.ns.cloudflare.com` через
`rdap.verisign.com`; `hostiq.ua` → `algin/dora.ns.cloudflare.com` через `rdap.hostmaster.ua`;
`nosuchdomain-zzz9988.com` → 404 ПОСЛЕ редиректа → `NotRegistered`; `example.invalidtldxyz` →
404 БЕЗ редиректа → `Unavailable`. Два сорта 404 различаются по адресу ответа — без этого
непокрытый редиректором TLD стал бы приговором нашему домену.

### Фаза 4 — Бейдж делегирования переведён на RDAP `[x]`

Коммит `b107c9a`, 22 файла. Удалены: `RegistrarService::get_nameservers` из трейта и обеих
реализаций, команда `registrar_get_nameservers` и её регистрация, парсер `parse_dns_get_list`,
хук `useRegistrarNameservers`, ключ `registrarsKeys.nameservers`, проп `registrarNsError`.
Живых ссылок на удалённое не осталось ни одной.

Новая лестница `nsDelegation` — причина → действие:

| Причина | Что случилось | Что делать |
|---|---|---|
| `no-zone` | домен не привязан к живой зоне Cloudflare | привязать зону |
| `zone-name-mismatch` | привязка указывает на зону с ДРУГИМ именем | перепривязать |
| `zone-nameservers-unknown` | зоны не прочитаны или зона не назвала NS | дождаться |
| `registry-nameservers-unknown` | ответа реестра ещё нет | дождаться |
| `not-in-registry` | утверждение реестра: домена там нет | разобраться с доменом |
| `registry-unavailable` | спросить не удалось | повторить позже |

`not-in-registry` специально НЕ `mismatch`: кнопка «Прописать NS» такому домену не поможет.
Слова реестра доезжают обязательным полем `detail: string | null` («нечего добавить» — явный
`null`, а не забытое поле).

**`Registered { nameservers: [] }` → `mismatch` с `actual: []`.** Пустота от реестра — это
утверждение «домен есть, делегирования нет», а не промах разбора (как было у API регистратора),
и чинится тем же действием — прописать NS зоны. Серый бейдж прятал бы за «мы не выяснили» домен,
который не работает вообще.

**`no-registrar` убрана целиком**, `registrarAccountId`/`registrarProvider` ушли из входа
правила: реестру всё равно, чей домен и есть ли у него аккаунт в нашей БД. Именно поэтому ручной
провайдер (Dynadot) впервые получает настоящий бейдж — это заявленный бонус фазы, и он закрыт
тестом. `registrarSupportsNsApi` и `registrarProviderKnown` сохранены как гейты **ЗАПИСИ**,
JSDoc переписан (иначе он описывал бы снятую роль).

## Итог

**Реализован целиком: да** — все шесть фаз закрыты, каждая прошла двухступенчатое ревью
(соответствие спеке → качество кода) с циклами доработки до одобрения.

**Сюита:** 1015 фронт-тестов / 95 файлов, `tsc --noEmit` чист; 294 rust-теста + 1 `#[ignore]`
(живая проба в сеть), `cargo clippy` без новых предупреждений. Rust-тестов стало меньше 300 —
удалено 6 тестов удалённого кода.

**Метод, который себя оправдал:** мутационная проверка гейтов. Три реальные дыры (фолбэк на
`count`, ветка таймаута в RDAP, возможность вернуть `path_segments_mut` к `format!`) были
зелёными на всех тестах и нашлись только снятием гейта. Отдельно — правило «поведение клиента
можно проверять только этим клиентом»: `User-Agent` стоил бы фиче полной неработоспособности при
зелёной сюите.

### Что осталось

1. **Живая приёмка человеком — обязательна.** Ни один агент не имел доступа к боевым Hostiq и
   Cloudflare для мутаций. Порядок: (1) Settings → добавить аккаунт Hostiq: поля email нет, есть
   `API token`; (2) кнопка `Test` зелёная; (3) список доменов приходит целиком — ожидается **127,
   из них 120 `Active`**, это же проверяет пагинацию; (4) карточка домена с зоной в Cloudflare —
   бейдж читается из RDAP и не серый; (5) прописать NS на тестовом домене → через ~20 секунд
   бейдж `delegated`, сверка снаружи:
   `curl -sL https://rdap.org/domain/<домен> | python3 -c "import sys,json;print([n['ldhName'] for n in json.load(sys.stdin)['nameservers']])"`;
   (6) домен у ручного провайдера («Dynadot») — бейдж живой, а тумблер «Прописать NS» выключен с
   подсказкой про отсутствие API.
2. **Существующие аккаунты Hostiq хранят старый нерабочий ключ.** Миграции нет и быть не может —
   блоб зашифрован на клиенте. После выката токен надо ввести заново. В UI это никак не
   подсвечено: аккаунт выглядит настроенным, а `Test` вернёт «✕ Failed». Кандидат на отдельную
   задачу: помечать аккаунт, чей ключ не проходил `Test` после смены контракта.
3. **Кэш «имя → id» живёт только внутри одного вызова команды.** `commands::registrars::reg_service`
   собирает новый `HostiqService` на каждую tauri-команду, а `full_setup::push_nameservers` зовёт
   смену NS по домену за раз — значит массовый прогон листает аккаунт заново на каждый домен.
   Рычаг вне файла клиента: переиспользование сервиса на уровне команд.
4. **Троттлинга RDAP нет.** Бейдж на списке доменов даст веер параллельных запросов в один
   публичный сервис, лимитирующий по IP; 429 приедет как `Unavailable` на всём списке.
   Клиент уже один на процесс (`OnceLock`), ограничение параллелизма — за потребителем.
5. **IANA bootstrap вместо `rdap.org`** — убрал бы посредника, видящего имена наших доменов.
   Не покрывает часть TLD, включая `.ua`: понадобится гибрид (bootstrap, где есть, редиректор
   как фолбэк).
6. **Не сверено живьём:** поведение Hostiq при `200` с отказом в теле без поля-сообщения (ветку
   `{"result":"error"}` сознательно не выдумывали, положительное распознавание `result ==
   "success"` её закрывает, но сам ответ не наблюдался); IDN/punycode в именах зон `.ua` — если
   листинг отдаёт punycode, а `domains.domain` хранит юникод, сопоставление по имени не найдёт
   домен и ответит «домена нет в аккаунте».
7. **Порядок лестницы: Cloudflare раньше реестра.** У домена без привязанной зоны И
   отсутствующего в реестре бейдж скажет «нет зоны», и про «домена не существует» пользователь
   узнает только после привязки — то есть худшая новость сообщается второй. Обратный порядок —
   одна перестановка. НЕ сделано намеренно: спека прямо требовала не двигать первую половину
   лестницы, и переигрывать это решение молча было бы неправильно.
8. **Многостраничный обход пагинации живьём не проверен** — на боевом аккаунте 127 записей, то
   есть одна страница. Обход держат только `wiremock`-тесты.
