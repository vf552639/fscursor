# План: Мониторинг доступности серверов раз в 6 часов

**Дата:** 2026-08-06
**Связь с бизнесом:** продукт — «пульт управления инфраструктурой» для power-user'а,
ведущего десятки–сотни серверов (`.business/audience/`). Без фонового мониторинга статус
связи — это снимок на момент ручного клика «SSH Test», и упавший сервер обнаруживается
случайно. Автопинг раз в 6ч превращает «жив/упал» в живой сигнал: пользователь узнаёт о
падении, даже когда не смотрит на страницу.

## Что решили на этапе brainstorming

Развилки закрыты явно (см. рефлексию сессии):

1. **Что мониторим:** только **доступность** (TCP-порт 22), без пароля. Это обходит
   zero-knowledge стороной — пароль расшифровывается лишь в разблокированном десктопе, а
   TCP-проверка ключа не требует и потому может крутиться на бэкенде 24/7. Полный SSH-вход
   (проверка, что наши креды ещё работают) сознательно **не** делаем — он потребовал бы
   открытого десктопа.
2. **Механизм проверки:** `asyncio.open_connection(ip, ssh_port)` с таймаутом. НЕ ICMP-ping
   (режется файрволами → ложные «упал»). Открытый порт 22 = «по серверу реально можно
   работать».
3. **Где крутится:** существующий **Celery-beat** (`app/core/celery_app.py` уже настроен,
   воркер уже есть). НЕ заводим второй планировщик.
4. **Порог падения:** статус `down` только после **2 неудач подряд** + короткий ретрай
   внутри одной проверки. Гасит ложные тревоги от мгновенной сетевой икоты.
5. **Как доходит до пользователя:** запись в существующую систему **уведомлений** (колокольчик
   в UI + внешний диспатч) на **переходах** состояния (up→down, down→up) ПЛЮС цвет статуса на
   карточке сервера (фронт уже это рисует).
6. **Интервал:** ровно 6 часов.

## Acceptance criteria (что значит «готово»)

- [ ] Раз в 6 часов Celery-beat запускает задачу проверки всех серверов с `user_id IS NOT NULL`.
- [ ] Проверка = TCP-connect на `ip_address:ssh_port` с таймаутом 5с и одним ретраем через ~2с.
- [ ] Успех: `last_check_ok=True`, `consecutive_failures=0`, `last_check_at=now`,
      `last_check_error=NULL`.
- [ ] Неудача: `consecutive_failures += 1`, `last_check_at=now`, `last_check_error`=текст.
      Статус `last_check_ok` роняется в `False` **только** при достижении 2 промахов подряд.
- [ ] Уведомление `server_down` создаётся ровно один раз на эпизод падения (переход
      «был жив → подтверждённо упал»), `server_up` — на переход «был упавшим → снова жив».
      Повторные прогоны в том же состоянии новых уведомлений НЕ плодят (дедуп).
- [ ] Проверки серверов идут параллельно с ограничением одновременности (не последовательно).
- [ ] Прогон пишет строку в `TaskLog` (`task_type="server_monitor"`): проверено / упало / поднялось.
- [ ] На карточке сервера видно «проверено N назад» из `last_check_at`.
- [ ] Юнит-тесты на логику переходов зелёные; настоящие TCP-соединения в тестах не открываются.

## Edge cases (продумать заранее)

- **Ноль серверов / только веб-серверы без user_id:** задача отрабатывает вхолостую, пишет
  `TaskLog` «checked 0», не падает.
- **Сотни серверов:** последовательные 5-секундные таймауты = минуты и риск `task_time_limit`
  (60 мин). Отсюда параллельность с semaphore (≈20 одновременно).
- **Мгновенная сетевая икота на воркере:** гасится ретраем + порогом 2 промаха. Одиночный
  промах не роняет статус и не шлёт уведомление.
- **Флаппинг (сервер то жив, то нет):** уведомления только на переходах + `dedup_key`,
  привязанный к эпизоду, — не даёт спамить каждые 6ч.
- **Идемпотентность/гонки:** beat не запускает вторую копию, пока первая идёт (обычная
  практика; при желании — `singleton`-lock, но для 6ч-интервала перекрытие маловероятно).
  Запись полей — простой `UPDATE` по `id`, без гонок между серверами.
- **Zero-knowledge:** проверка НЕ трогает пароль/блоб/keychain — только TCP-порт. Плейнтексту
  утекать неоткуда: его в этом пути просто нет. `last_check_error` содержит текст сетевой
  ошибки (`timeout`, `connection refused`), не секреты.
- **Смена IP/порта сервера:** проверка всегда читает актуальные `ip_address`/`ssh_port` из БД.
- **`consecutive_failures` на старых строках:** миграция ставит `DEFAULT 0 NOT NULL`, backfill
  нулём — существующие серверы стартуют как «промахов нет».

## Модель состояния (семантика полей)

| Ситуация | `consecutive_failures` | `last_check_ok` | Уведомление |
|---|---|---|---|
| Порт ответил | → 0 | → True | если было `False` → `server_up` |
| 1-й промах подряд | → 1 | без изменений | нет (статус не роняем) |
| 2-й промах подряд | → 2 | → False | если было не-`False` → `server_down` |
| 3-й+ промах | → 3,4… | остаётся False | нет (дедуп) |

`last_check_ok === False` = «подтверждённо упал» — ровно то, что фронт уже красит красным.
Первый транзиентный промах в это состояние не протекает.

### Фаза 2 — Проверка доступности (чистая функция)  `[x]`
- `backend/app/services/server_monitor.py`: `async def probe(host, port, timeout=5.0) -> tuple[bool, str|None]`
  на `asyncio.open_connection` + `asyncio.wait_for`; при неудаче — один ретрай через ~2с;
  корректно закрывает соединение; возвращает `(ok, error_text|None)`.
- Коннектор вынесен параметром/подменяемой функцией, чтобы тесты не открывали реальный сокет.
- Файлы: `backend/app/services/server_monitor.py`.
- Сделано 2026-08-06. Сигнатура:
  `probe(host, port, timeout=5.0, *, connect=asyncio.open_connection, retry_delay=2.0)`.
  Пауза ретрая тоже параметр — тесты гоняют её нулём, иначе прогон стоил бы 2 секунды на случай.
- `probe` **не бросает вообще**: любой отказ — это `(False, текст)`. Ревью нашло два пробоя, оба
  воспроизведены на живом коде и закрыты:
  - `UnicodeError` из IDNA-кодека резолвера (адрес `10.0.0..5`) — не наследник `OSError` и летел
    мимо перехвата. Схема `ServerBase.ip_address` не валидируется, так что такая строка ложится
    в БД штатно, а цикл фазы 4 из-за неё молча перестал бы проверять все остальные серверы.
  - Пустой `ip_address`: `getaddrinfo("", 22)` разрешается в localhost воркера. Сегодня порт 22
    на воркере закрыт, но `ssh_port` конфигурируем — сервер с пустым адресом и занятым на
    воркере портом отчитался бы `up`, ни разу не будучи опрошенным. Теперь ранний отказ
    `no address configured`, резолвер не зовём.
  - Валидацию `ip_address` в схемах намеренно не трогали — отдельная задача.

## Часть II — метрики «жизни сервера» (добавлено 2026-08-06)

Исполнение плана вскрыло вторую половину той же дыры. Пользователь видит на карточках
`No metrics yet` и прочерки в Uptime/SSD/CPU, а у старых серверов — окаменелости от
30.04.2026. Причина найдена в истории:

- Сбор метрик по SSH жил в `backend/app/services/server_metrics_service.py` и
  `backend/app/tasks/server_health_task.py` (коммит `b148a79`) и был **удалён** переездом на
  zero-knowledge (`5192372`): у бэкенда больше нет SSH-пароля — он лежит блобом под
  мастер-ключом. Собирать метрики с бэкенда теперь **невозможно в принципе**.
- Колонки (`uptime_seconds`, `cpu_usage_pct`, `ram_*`, `disk_*`, `os_pretty`, `kernel`,
  `metrics_collected_at`) остались в модели и в `ServerResponse`, фронт их рисует — но
  писать в них некому.
- `useRefreshMetrics` (`frontend/src/api/servers.ts:266`) до сих пор зовёт
  `POST /servers/{id}/refresh-metrics` — **такого роута на бэкенде нет** (один из «мёртвых
  роутов» из долга Спринта 3).

Отсюда единственная архитектурно допустимая схема (принцип №3 «desktop выполняет, web
смотрит»): **метрики собирает десктоп по SSH и пишет их обратно в бэкенд**. TCP-мониторинг
из части I остаётся независимым — он отвечает на «жив/упал» 24/7 без открытого десктопа,
а метрики появляются, когда пользователь в десктопе нажал «Refresh metrics».

Разделение ответственности, которое фронт обязан показывать раздельно:

| Сигнал | Кто пишет | Когда свеж | Поле |
|---|---|---|---|
| жив/упал | Celery-beat, TCP:22 | всегда, раз в 6ч | `last_check_ok`, `last_check_at` |
| метрики (uptime/CPU/RAM/SSD) | десктоп по SSH | когда открывали десктоп | `metrics_collected_at` |

### Что оказалось шире плана

План лечил «нет источника данных». Настоящая болезнь была общее: **интерфейс показывал то,
чего не измерял**, и жалоба пользователя описывала два её симптома из пяти.

1. **Экранов, врущих о состоянии сервера, было четыре, а не один.** Кроме карточек серверов —
   дашборд (`status === "active" ? "healthy"`: подтверждённо упавший сервер считался в плитке
   «Healthy: N»), список доменов (`Domains.tsx` — зелёная точка у каждого домена мёртвого
   сервера) и деталь сервера. Каждый экран считал лестницу состояний заново и по-своему.
   Сведено в `frontend/src/lib/serverStatus.ts` — один источник на все четыре.
2. **Спарклайны рисовали историю, которой не существует.** `genBars` генерировал 15 случайных
   столбиков вокруг одного текущего значения; истории метрик мы не храним (в колонках только
   последний снимок). На дашборде ряд был просто зашит константой. Удалены вместе с
   `MiniChart` и пропом `chartData`.
3. **Полосу заполнения диска красила загрузка CPU** (`cpuColor` → `pctColor`).
4. **Протухшая проверка не была помечена нигде.** Введён порог 18ч (три пропущенных прогона
   при шаге 6ч) — умерший beat больше не выглядит как здоровье.
5. **`formatUptime` существовал в двух реализациях** с разным текстом, причём плотная —
   та, что стояла на двух экранах, — не была покрыта тестами вообще.

### Решения, принятые по ходу и зафиксированные в коде

- **Семантика записи метрик:** явный `null` затирает колонку, отсутствующий ключ — нет,
  тело без единого поля → 422. Снимок атомарен: протухшая цифра под свежей отметкой хуже
  прочерка. Канонический текст — в `server_service.apply_metrics`.
- **Асимметрия лестницы:** протухшая проверка перестаёт удерживать `active` (незнание нельзя
  рисовать как здоровье), но подтверждённое падение на старой отметке остаётся `error`
  (старая проблема не усыпляет). Свежий положительный ответ монитора перебивает легаси-колонку
  `status === "error"`.
- **Сбор метрик — только по кнопке.** Аудит-запись на роут метрик оправдана ровно тем, что
  действие инициирует человек: `GET /api/audit/log` отдаёт последние 100 записей без фильтра и
  прунинга, и периодический сбор по сотне серверов вытеснил бы оттуда все человеческие действия.
  Появится расписание — пересматривать аудит вместе с ним.
- **Архитектура прогона:** опрос веером (`Semaphore(20)`, чистая сеть), запись —
  последовательно в одной сессии. Причины: `touch_entity_sync` берёт `FOR UPDATE` на строку
  `sync_state` пользователя, а `apply_check_result` коммитит внутри себя и делает исходящий HTTP.

### Дефекты, найденные ревью (каждый воспроизведён, не предположен)

- `UnicodeError` из DNS-резолвера пробивал `probe` наружу и **молча выключал мониторинг для
  всех остальных серверов**; достижим опечаткой в поле IP (`10.0.0..5`).
- Сервер с пустым `ip_address` резолвился в `127.0.0.1` — мониторинг мог доложить `up` о
  машине, которую не трогал.
- Трафик считался разностью **сумм** по интерфейсам: въехавший в окно `head` контейнер давал
  8 Гбит/с там, где шло 8 кбит/с. Считается по пересечению имён, дельтами.
- Обрыв SSH-вывода после первого маркера давал снимок из одних `null` и **стирал все
  накопленные показания**. Закрыто финальным маркером `#sdmp:end`.
- Суррогат в текстовой метрике давал 500 **дважды**: из драйвера и, после починки первого, из
  самого обработчика 422 (`JSONResponse.render` падал на эхе `input`). Гард повторял рендер
  неточно — потерянный `allow_nan=False` пропускал живой 500 на `{"cpu_usage_pct": NaN}`.
- Упавшая доставка уведомления писала в журнал `checked 0`, хотя проверка была записана, —
  и промах приходился с повышенной вероятностью на **инцидентный** прогон (вебхук часто живёт
  на той же инфраструктуре, что и упавший сервер).
- Устаревший результат опроса применялся к строке, у которой сменился адрес: правка IP во
  время фазы опроса давала ложное «упал» с чужим адресом в письме.

### Фаза 11 — Два немедленных триггера поверх той же задачи  `[x]`

Ритм 6 часов не тронут, новой задачи не заведено — оба триггера зовут ту же
`check_server_reachability`, у которой появился необязательный параметр `user_ids`.

- **Старт воркера** (`celeryd_after_setup` в `core/celery_app.py`) — `send_task` **без сужения**:
  после деплоя переопросить надо весь парк, в этом весь смысл триггера. Сигнал воркерный, beat
  его не поднимает; несколько воркеров дадут несколько прогонов, но повторный прогон в том же
  состоянии идемпотентен и уведомлений не плодит (дедуп по эпизоду).
- **Заведение сервера** (`server_service.create`, строго после коммита) — `apply_async`
  **с сужением до владельца новой строки**. Прогон по всему парку всех пользователей на чужое
  добавление — сотни лишних сокетов и драка за `sync_state` всех разом; в общей с dev базе это
  ещё и та самая мина, что однажды записала «упал» трём настоящим машинам.
- **Пакетный импорт** — `create(..., check_now=False)` в цикле и одна проверка на всю пачку
  после него: иначе N прогонов по одному и тому же парку из N серверов.
- `user_ids` едут **строками**: брокер настроен на `task_serializer="json"`, `uuid.UUID` в него
  не сериализуется, и задача с таким аргументом не уехала бы в очередь вовсе. Разбор в `UUID` —
  на входе задачи.
- **Провал публикации не входит в контракт.** `retry=False` (штатный `task_publish_retry` дал бы
  три таймаута подключения вместо одного), исключение не выпускается наружу, публикация уходит
  в `asyncio.to_thread` — kombu пишет синхронно, и прямой вызов из корутины подвесил бы весь
  event loop, то есть все запросы процесса, а не один. С мёртвым Redis `POST /api/servers`
  отдаёт 201, сервер в БД есть, в логах — warning с адресатом.

### Фаза 13 — Настоящая граница ожидания брокера (по итогам ревью)  `[x]`

Ревью замерило то, что фаза 11 считала решённым, и оказалось, что **верхней границы ожидания
не было вовсе**, а докстринг утверждал обратное («граница остаётся за
`broker_connection_timeout`») — то есть врал следующему читателю. Замер на самом вызове
(`enqueue_reachability_check`, брокер и result backend подменены):

| сценарий | было | стало (ждёт вызывающий) |
|---|---|---|
| хост недостижим (блэкхол) | **> 100 с** (в одном прогоне > 25 мин) | **3.0 с** |
| порт закрыт (refused) | 19.8 с | **3.0 с** |
| имя не резолвится | 19.8 с | **3.0 с** |
| брокер жив | 0.0 с | **0.0 с** |

Почему было так плохо и что сделано:

- `retry=False` снимает повторы **публикации**, но таймаута соединению не задаёт: kombu не
  передаёт redis-py ничего, и connect уходит в системный TCP.
- Половину времени съедал **result backend**, а не брокер: `send_task` перед публикацией зовёт
  `backend.on_task_call`, подписывая веб-процесс на результат, которого он никогда не спросит.
  Закрыто `ignore_result=True` в обоих триггерах — результат никем не читается (человек видит
  итог строкой в `task_logs`, оператор — в логе воркера).
- `broker_transport_options={"socket_connect_timeout": 1}` — ограничивает попытку подключения.
  Парного `socket_timeout` намеренно нет: настройка общая с воркером, а тот держит на брокере
  долгие блокирующие чтения очереди.
- `PUBLISH_TIMEOUT_SECONDS = 3` вокруг `to_thread` — **единственная настоящая граница**: таймаут
  сокета ограничивает попытку, но не их число, и на закрытом порту/неразрешимом имени время
  уходит в паузы между повторами (поток заканчивается сам за 4–6 с).

**Открытая транзакция на время сетевого ожидания** (тоже находка ревью) закрыта не лишним
коммитом, а порядком строк: публикация встала **между `commit()` и `refresh()`**, где соединение
уже возвращено в пул. Первый вариант — `commit()` после `refresh()` — был замерен и отвергнут:
на пулере включён `NullPool`, освобождённое соединение закрывается, и лишний коммит стоил
**+3 с к каждому** `POST /api/servers` в обмен на устранение задержки, которая бывает только при
больном брокере. В пакетном импорте коммит перед публикацией оставлен: там он один на всю пачку.

Тесты: граница проверяется на `enqueue_reachability_check` (заглушка спит дольше границы,
граница подменена крошечной — быстро и без сокетов), а не на `POST /api/servers` — на уровне
запроса её не видно за латентностью БД, которая здесь сама по себе ~2.5 с на `NullPool` через
пулер Supabase. Тест сигнала старта переведён с прямого вызова обработчика на **отправку самого
сигнала** (`celeryd_after_setup.send(...)` теми же аргументами, что шлёт celery), так что теперь
ловится и снятие декоратора. Обе правки проверены мутацией: убираешь `wait_for` — падает тест
границы; снимаешь `@celeryd_after_setup.connect` — падает тест сигнала.

Замечено по ходу и отнесено к уже записанному долгу «тесты ходят в общую dev-БД»: в одном из
полных прогонов упал `test_a_result_for_a_changed_address_is_thrown_away`, в повторном полном
прогоне и в одиночном запуске — зелёный. К правкам фазы 13 отношения не имеет (тест не создаёт
серверов через API и ничего не публикует), это то самое плавающее падение на общей базе.

### Фаза 14 — Полный реестр моделей в любом процессе  `[x]`

`BlobStorage` объявлен в `app/blobs/models.py` и импортировался только модулями роутов
(`auth/routes.py`, `blobs/routes.py`, `sync/routes.py`). Веб грузит роуты — реестр полон, API
работает. Воркер роуты не грузит никогда: его цепочка `app/tasks/__init__.py` →
`server_monitor_task` → `app.models.server`. На `blob_storage.id` ссылаются шесть колонок в
четырёх моделях (`server` ×2, `domain` ×2, `cloudflare_account`, `registrar_account`),
SQLAlchemy разрешает FK лениво — на flush, при сортировке таблиц по зависимостям, — и запись
результата падала всегда. Выборка и опрос при этом проходили, поэтому в логах всё выглядело
как работающий мониторинг с невезучими серверами.

Починено в `app/models/__init__.py`: туда внесены все модели, включая живущие в `auth`, `blobs`
и `audit`. Место выбрано из-за того, что Python импортирует пакет раньше подмодуля — значит
`from app.models.server import Server` (ровно то, что делает задача) сам тянет полный реестр.
Ни воркеру, ни beat, ни alembic, ни будущему скрипту не нужно ничего помнить. Вариант
«импортировать в точке входа воркера» отвергнут: он чинит один процесс и оставляет мину под
всеми остальными, а FK на `blob_storage` есть ещё в `domain`, `cloudflare_account` и
`registrar_account`.

Реестр воркера не содержал двух таблиц — `blob_storage` и `audit_log`; теперь совпадает с вебом.

Тест — `tests/test_model_registry.py`, в **отдельном интерпретаторе**: внутри общего прогона
роуты давно импортированы соседями, и проверка зеленела бы всегда. `configure_mappers()`, вопреки
ожиданию, эту поломку **не ловит** (`relationship()` на `BlobStorage` ни у кого нет, только сырые
FK-колонки) — форсировать разрешение FK приходится через `metadata.sorted_tables`, тот самый путь,
которым ходит flush. Проверено мутацией: снимаешь фикс — тест краснеет ровно продовой ошибкой.

### Фаза 15 — Провал перестал маскироваться успехом  `[x]`

Именно зелёная задача при `failed 6` дала поломке прожить незамеченной: ошибки лежали в логах
воркера, а наверх шёл `succeeded`. Изоляция сбоев («один сервер не уносит остальных»)
спроектирована верно, но в вырожденном случае, когда падают все, превращается в отчёт ни о чём.
Это то же «не рисуй незнание здоровьем», только на уровне задачи.

Прогон, не проверивший **ни одной** цели из непустого списка **при наличии настоящей ошибки**,
поднимает `ServerMonitorRunFailed`. Условие узкое намеренно: пустой прогон (аккаунт без серверов)
— штатное «нечего делать»; частичный провал уже виден человеку статусом `partial`; а `failed` от
безобидных гонок (строку удалили или ей сменили адрес во время опроса) ошибок не порождает и
тревоги не поднимает. Журнал пишется до падения — человек получает объяснение независимо от
судьбы задачи.

### Живая проверка (пункт 3 плана закрыт по существу)

```
до:    server_monitor: прогон по 2 владельцам — checked 0, down 0, up 0, undelivered 0, failed 6
после: server_monitor: прогон по 2 владельцам — checked 6, down 0, up 0, undelivered 0, failed 0
```

Кто из парка отвечает на TCP:22 — теперь видно по факту: **все три настоящих сервера живы**
(id 2 `45.83.193.106`, id 3 `45.83.194.107`, id 421 `193.111.63.5` — `last_check_ok = true`).
Жалоба «у одного сервера проверка не работает» была иллюзией: не работал мониторинг целиком.

Остальные три из шести (id 2383–2385, хосты `*.probe.invalid`) — **мусор от тестов**, утёкший в
общую dev-БД 2026-08-07: они не резолвятся, за два прогона набрали порог и создали три
`server_down`. Владелец у них тестовый (`srvmon-…@example.com`), настоящего пользователя это не
коснулось. Не удалял — это чужие данные и отдельное решение; см. долг ниже.

### Долг, дописанный по итогам части IV

- **В общей dev-БД 2563 пользователя**, почти все — мусор от тестовых прогонов, и часть из них с
  серверами, которые мониторинг честно опрашивает каждые 6 часов. Это то же «тесты ходят в общую
  dev-БД», но теперь с ценником: фантомные серверы в парке и фантомные уведомления. Чистка +
  эфемерная БД под тесты — отдельная задача.
- **`renewal_task` и любая будущая фоновая задача** жили с тем же неполным реестром; сейчас
  закрыто разом, но регрессию стережёт только `tests/test_model_registry.py` — не удаляйте его,
  не заменив равноценным.
- **Несужённый триггер на старте воркера гоняет полный обход этого мусора.** В разработке
  `docker compose restart worker` случается заметно чаще четырёх раз в сутки, и каждый рестарт —
  обход парка всех 2563 пользователей. В продакшене это ровно то поведение, которое задумано
  (после деплоя переопросить всех), а в dev — умножитель к предыдущему пункту: чинится той же
  эфемерной БД, а не сужением триггера.
- **Порог `FAILURE_THRESHOLD = 2` ослаб по смыслу.** Проектировался, когда между прогонами были
  гарантированные 6 часов, — «два промаха подряд» означало «не отвечает уже полдня». С
  событийными прогонами два промаха могут лечь в минуту (два рестарта воркера подряд). Это
  по-прежнему четыре TCP-попытки, так что менять порог не потребовалось, но формулировку в
  `docs/ARCHITECTURE.md` пришлось ослабить до правды. Если событийных триггеров станет больше —
  пересматривать порог вместе с ними.
