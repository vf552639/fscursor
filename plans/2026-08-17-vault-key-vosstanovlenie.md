**Связь с бизнесом:** восстановление доступа — обязательное условие доверия к
zero-knowledge-хранилищу. Пользователь ведёт десятки серверов и не может позволить себе
потерять все SSH-пароли из-за забытого мастер-пароля; сейчас восстановление ровно это и
делает, то есть закрывает продукт для всех, кто читал, что бывает при потере пароля.

## Контекст: почему это делается

Восстановление пароля **гарантированно** уничтожает доступ ко всем секретам аккаунта.

Мастер-ключ выводится напрямую из пароля и соли — `derive_master_key(password, salt)`
(`desktop/src-tauri/src/crypto/kdf.rs:35`) — и именно им шифруются блобы
(`desktop/src-tauri/src/commands/vault.rs:44`) и открывается локальный sqlcipher-кэш
(`desktop/src-tauri/src/sync/cache.rs:23`). При восстановлении сервер поворачивает и
соль, и пароль (`backend/app/auth/routes.py:299`), а перешифровки блобов нет ни на
клиенте, ни на сервере: у `/password/change` поле `re_encrypted_blobs` есть, у
`/recovery/finish` — нет. Значит выведенный после восстановления ключ математически не
равен тому, которым зашифрованы блобы.

Три следствия, каждое подтверждено кодом:

1. Запись старого ключа в связку (`commands/auth.rs:231`) бесполезна: `recovery/finish`
   удаляет все сессии (`routes.py:304`), новой не выдаёт, а UI сразу уходит на `/login`
   (`frontend/src/pages/RecoveryRestore.tsx:39`). Ключ затирается на первом же входе
   (`auth.rs:139`) — и `let _ = new_master` лишь маскирует это как осознанное решение.
2. Recovery-блоб переоборачивает старый мастер-ключ (`auth.rs:214`), поэтому повторное
   восстановление вернёт тот же нерабочий ключ. Дыра не самозалечивается.
3. Ломается и веб: `UnlockModal` выводит ключ из пароля тем же способом
   (`frontend/src/components/UnlockModal.tsx:22`).

**Решение** — модель 1Password: случайный **ключ хранилища (vault key, VK)**, которым
шифруется всё; пароль лишь оборачивает VK. Тогда смена пароля и восстановление
перезаписывают 72 байта одним атомарным запросом. Для существующих аккаунтов
`VK := текущий мастер-ключ`, поэтому **ни один блоб не переписывается**, а старые
recovery-блобы (они оборачивают ровно этот ключ) остаются корректными как есть.

Заодно доводится до рабочего состояния смена пароля: эндпоинт `/auth/password/change`
существует, но его не вызывает ни один клиент.

## Термины

| Термин        | Что это                                                                                                |
| ------------- | ------------------------------------------------------------------------------------------------------ |
| **KEK**       | `derive_master_key(password, salt)` — то, что сейчас зовётся master key. Только оборачивает VK.        |
| **VK**        | Случайные 32 байта. Шифрует блобы и sqlcipher-кэш. Живёт в связке ключей. Не меняется при смене пароля. |
| `wrapped_vk`  | `aead::encrypt(VK, KEK)` — лежит на сервере в `users.wrapped_vault_key`.                               |
| recovery-блоб | `wrap_master_key(VK, phrase)` — теперь оборачивает VK (а для старых аккаунтов уже оборачивает его же). |

## Acceptance criteria (что значит «готово»)

- [ ] Блоб, записанный до восстановления пароля, читается после него — и после второго
      восстановления подряд тоже.
- [ ] Смена пароля не трогает ни блобы, ни локальный кэш (`blob_storage.version` не растёт).
- [ ] Старый аккаунт (`wrapped_vault_key IS NULL`) мигрирует лениво на первом входе,
      не теряя ни одного секрета и не переписывая блобы.
- [ ] Старый билд десктопа, не приславший обёртку в `recovery/finish`, получает 422,
      а не тихо добивает аккаунт.
- [ ] Веб читает те же секреты, что и десктоп, после каждой из операций.

## Edge cases (продумать заранее)

- **Аккаунт до перехода** (`wrapped_vault_key IS NULL`) — ленивая миграция на входе;
  повторный `vault-key/init` обязан отвечать 409, а не затирать обёртку.
- **Гонка двух устройств** на ленивой миграции: оба выведут один и тот же KEK и один и
  тот же VK (`VK := KEK`), поэтому 409 у проигравшего безопасен — обёртки эквивалентны.
- **Рассинхрон пароля и обёртки** (`aead::decrypt(wrapped_vk, kek)` падает) — отдельное
  внятное сообщение, а не «aead: decrypt».
- **Zero-knowledge:** `recovery_start` анонимный и обёртку **не** отдаёт — иначе это
  оффлайн-оракул для перебора пароля. VK и так достаётся из recovery-блоба.
- Имя записи в связке ключей не меняется — иначе установленные копии потеряют ключ.

### [ ] 2. Desktop: VK вместо выведенного ключа

Правка сосредоточена в `desktop/src-tauri/src/commands/auth.rs` плюс `sync/http.rs`.

- `keychain::store_master_key` / `load_master_key` → `store_vault_key` / `load_vault_key`
  (~12 мест: `provision.rs`, `full_setup.rs`, `registrars.rs`, `cloudflare.rs`,
  `domain_facts.rs`, `sync_cmd.rs`, `creds.rs`, `sync/client.rs`, `vault.rs`).
  Переименование обязательно: после этой правки «master key» и «vault key» — разные
  ключи. **Имя записи в связке ключей не менять.**
- `auth_register`: `vk = random 32` → `wrapped_vk = aead::encrypt(&vk, &kek)` →
  recovery-блоб оборачивает **VK** → `wrapped_vk` уходит в `register` → в связку VK.
- `auth_login`: обёртка есть → `vk = aead::decrypt(wrapped_vk, kek)`; нет → ленивая
  миграция `vk = kek` + `vault_key_init(aead::encrypt(&vk, &kek))`. Recovery-блоб не трогаем.
- `auth_recovery` — суть починки:
  ```
  vk       = unwrap_master_key(recovery_blob, phrase)   // это VK, не пароль
  new_kek  = derive_master_key(new_password, new_salt)
  new_wrap = aead::encrypt(&vk, &new_kek)
  new_blob = wrap_master_key(&vk, phrase)               // фраза та же → блоб по смыслу прежний
  recovery_finish(..., new_wrap)
  keychain::store_vault_key(&uid, &vk)                  // тот же VK, что и до восстановления
  ```
  `let _ = new_master` исчезает.
- `auth_recovery_setup`: оборачивать фразой **VK из связки**, а не выведенный из пароля ключ.
- Новая команда `auth_change_password(old_password, new_password)`. Блобы и локальный
  кэш не трогаются вовсе — в этом весь смысл VK.
- Тестируемость по образцу `put_blob_encrypted` (`vault.rs:37`): чистая функция
  `recovery_payload(recovery_blob, phrase, new_password, new_salt) -> (vk, new_wrapped_vk,
  new_recovery_blob)`. Тест формулирует инвариант, которого не было: *блоб, зашифрованный
  до восстановления, расшифровывается ключом из связки после него.*
- Тесты в `sync/http.rs` (wiremock): обёртка реально уходит в теле; `login_finish` без
  `wrapped_vault_key_b64` разбирается в `None`.
