# Cloudflare ↔ Domains: живой матч, синхрон и связка новых доменов

## Context (зачем)

В строке вкладки **Domains** колонка «Cloudflare» показывает аккаунт только из
персистентного `cloudflare_account_id` (`DomainRow.tsx:108` читает `d.cf_id`). Вкладка
**Cloudflare** знает раскладку шире — из живого `cf_list_zones` (`useCloudflareZones`), —
поэтому в строках стоит «—» там, где аккаунт по факту известен. Пользователь подтвердил
скриншотами: зоны на вкладке Cloudflare живые (настоящие zone-id, статус `Active`), а
колонка в строках пустая → у доменов в БД нет `cloudflare_account_id`.

Разбили на **два кейса** (решение пользователя, подтверждено на макете):

1. **Домен уже в Cloudflare** (зона существует) — нужен живой показ + синхронизация.
2. **Новый домен** — связать домен + Cloudflare + хостинг(+регистратор) одним потоком;
   требует доработки бэкенда.

Макет согласован интерактивно (инлайн visual-companion). Решения пользователя:
- Подсказка в строке визуально **отличается** от сохранённой привязки; неоднозначность
  **не угадывается**.
- Кейс 2 — **единый full-setup эндпоинт**.
- Синхрон Кейса 1 — **только привязка** (`account_id`+`zone_id`); NS пушится отдельно
  (вкладка NS), как сейчас.

Zero-knowledge (жёсткое ограничение архитектуры): токен Cloudflare и ключи регистраторов
живут только в десктопе; **бэкенд не ходит в Cloudflare и не пушит NS**. Любое выполнение
(список зон, создание зоны, смена NS) — Tauri-команды десктопа. Это определяет границу
full-setup ниже.

> Реализовывать **по частям**: сначала Кейс 1 (фронт, быстрая ценность), затем Кейс 2
> (бэкенд + десктоп). При старте скопировать в `plans/` двумя файлами
> (`2026-08-13-domains-cloudflare-zhivoy-match.md`, `2026-08-13-domains-full-setup.md`).

## Кейс 1 — домен уже в Cloudflare (фронт целиком)

### Фаза 1 — Живой матч как подсказка в строке `[ ]`

**Новый хук** `frontend/src/hooks/useDomainZoneMatches.ts`:
- `useCloudflareAccounts` + живые зоны каждого активного аккаунта через `useQueries`
  поверх существующего `zonesQuery(accountId)` (`api/cloudflare.ts`). Desktop-only
  (`enabled: isTauri()`); в вебе карта пустая → «—» как сейчас.
- Один мемоизированный прогон **`matchDomainsToZones(domains, zonesByAccount)`**
  (`lib/cfZoneMatch.ts`, переиспользуем как есть: даёт `matched`/`ambiguous`/`none`/
  `skipped`).
- Возврат — **стабильная** `Map<number, RowCfHint>`, где hint уже резолвит объект
  аккаунта: `{ outcome:"matched", account } | { outcome:"ambiguous", accountIds }`.

**`DomainRow.tsx`** (ячейка Cloudflare, строка 108) — проп `cfHint?: RowCfHint`:
- есть `cf` (сохранённый) → `{cf.name}` как сейчас;
- `matched` → имя аккаунта **курсивом и слегка приглушённо, БЕЗ метки-чипа** + `title`
  «Совпало с зоной Cloudflare — в базе не сохранено. Нажми Синхронизировать» (отличие от
  сохранённой привязки — только начертанием: та обычным текстом с зелёной точкой);
- `ambiguous` / `none` / нет данных → «—» (БЕЗ метки «неоднозначно» — решение
  пользователя: не угадываем и не шумим; совпадение в 2 аккаунтах просто не показываем).
- Колонку NS в таблицу **не добавляем** — её в таблице нет; NS живёт в Overview.
- Легенды-расшифровки под таблицей **нет** (решение пользователя).

**`DomainTable.tsx`** — проп `zoneHints`, проброс `zoneHints.get(d.id)` в строку.
**`Domains.tsx`** — вычислить hints поверх `domainsData`, передать в таблицу.

**Непрочитанные аккаунты (решение пользователя).** Хук матчей смотрит ошибки per-account
запросов зон (`useQueries`); если у аккаунта зоны не прочитались (сломан токен — как
`Invalid API Token` на скрине), над таблицей тихий баннер «N аккаунтов не прочитаны —
совпадения по ним не показаны», чтобы «—» не читалось как «Cloudflare нет».

**Гард мемоизации:** одна мемо-карта, ссылка стабильна — тест на число рендеров
`DomainRow` (`DomainTable.tsx:12`, `DomainRow.tsx:56`) должен продолжать проходить.

### Фаза 2 — Кнопка «Синхронизировать с Cloudflare» `[ ]`

Переиспользуем `useCloudflareBind` → `autoBindDomainsToCloudflare` (уже пишет
`account_id`+`zone_id`, идемпотентно, репорт через `CloudflareBindBanner`, гейт «один
прогон за раз»). Сегодня зовётся только по выделенным (`Domains.tsx:292`).
- `DomainsHeader.tsx` — заметная кнопка «Синхронизировать с Cloudflare».
- `Domains.tsx` — `onClick={() => void cfBind.run(domainsData, "manual")}` (весь список),
  `disabled={cfBind.pending}`, прятать/дизейблить под `!isTauri()`.
- Результат — существующий баннер. **NS не трогаем** (решение пользователя): после
  привязки NS пушится отдельно вкладкой NS.

### Фаза 3 — Overview: аккаунт + NS в одном месте `[ ]`

`DomainDetailModal.tsx`. **Слить NS в Overview** (решение пользователя): отдельной вкладки
`ns` больше нет — её содержимое переезжает в Overview (сам таб-свитчер убрать).
- **Пикер аккаунта.** Заменить `<Field k="Cloudflare" v={cloudflare_account_id} />` (225)
  на селект (`useCloudflareAccounts`, по имени — закрывает долг «сырой id», коммент 206–208).
  На выбор — `useUpdateDomain` (`PUT /domains/{id}`, `{ cloudflare_account_id }`).
- **Дорезолв зоны (решение пользователя).** При выборе аккаунта И для домена, у которого
  аккаунт уже есть, а `cloudflare_zone_id` пуст, резолвить зону точным совпадением имени
  (`useCloudflareZones` + `normalizeZoneName`); однозначно нашли → сохранить `zone_id`.
  Чинит `skipped`-домены, которым иначе NS прописать нечем.
- **NS-запись + делегирование (решение пользователя).** Показать nameservers зоны
  (`useZoneNameservers` по `account_id`+`zone_id`) и **сверить** с реальными NS у
  регистратора (`useRegistrarDomains` → `nameservers` домена): бейдж «делегировано /
  pending / расходится». Кнопка «Прописать NS у регистратора» (существующий
  `useSetNameservers`), дизейбл если регистратор без API (`registrarSupportsNsApi`, общий
  с Кейсом 2) или зона не резолвится.

**Файлы Кейса 1:** `hooks/useDomainZoneMatches.ts` (новый), `lib/registrarCaps.ts` (новый,
`registrarSupportsNsApi`), `components/domains/DomainRow.tsx`, `DomainTable.tsx`,
`pages/Domains.tsx`, `components/domains/DomainsHeader.tsx`, `components/DomainDetailModal.tsx`
(NS сливается сюда), возможно `components/domains/types.ts` (`RowCfHint`).

## Кейс 2 — новый домен: full-setup (бэкенд + десктоп + фронт)

Цель: из мастера завести домен и одним потоком связать хостинг + Cloudflare (+регистратор),
завести зону и (по тумблеру) прописать NS. Схемы `BulkFullSetupRequest/Response` в
`schemas/domain.py:155` есть, но **эндпоинт и десктоп-команда не реализованы**.

### Граница из-за zero-knowledge (важно)
- **Бэкенд** атомарно делает то, что не требует токена: создаёт строку домена и
  проставляет `server_id` + `cloudflare_account_id` + `registrar_id`; возвращает домен
  и `task_log_id`. Идемпотентность — через idempotency key (как у provision).
- **Десктоп** выполняет то, что требует токена: `cf_create_zone` → write-back
  `cloudflare_zone_id`; по тумблеру `registrar_set_nameservers` (write-back `ns_status`).
  Всё пишет audit best-effort, как остальные команды.

### Фаза 1 — Бэкенд: эндпоинт `[ ]`
Поддержать **оба входа** (решение пользователя):
- **Новый домен (одиночный).** Мастер сперва создаёт домен существующим `POST ""`
  (реюз `create_domain`), получая `id`, затем идёт в full-setup по этому id.
- **Массовый по существующим.** `POST /domains/full-setup` на базе готовой
  `BulkFullSetupRequest` (`domain_ids`, `server_id`, `cloudflare_account_id`,
  `registrar_id?`) — реализовать роут (сейчас только схема). Сервис `domain_service.py`:
  транзакция «проставить связки пачке» (реюз `bulk_assign_server`/`bulk_assign_cloudflare`),
  вернуть `BulkFullSetupResponse` (id для последующего write-back зоны из десктопа).

Бэкенд только персистит связки; зону/NS он не трогает (zero-knowledge).

### Фаза 2 — Десктоп: команда исполнения `[ ]`
Новый `commands/full_setup.rs` — Tauri-команда `domain_full_setup` (на ОДИН домен): по
`domain_id`+`cloudflare_account_id` зовёт `cf_create_zone` (если зоны нет), пишет
`cloudflare_zone_id` обратно (`domain_write_back`), по флагу `push_ns` —
`registrar_set_nameservers`. Реюз `cloudflare::client::create_zone` (+ `get_zone_by_name`)
и трейта регистратора; наружу — структура со статусами шагов (зона / NS / что не удалось).
Массовость — на фронте: пачка гоняет ту же команду с конкуренцией (паттерн `mapWithLimit`
из `cfAutoBind.ts` / гейт как у `provision_bulk`). Зарегистрировать в `lib.rs`.

### Фаза 3 — Фронт: мастер + массовое действие `[ ]`
**Одиночный** (мастер из «Add Domain»): расширить `AddDomainModal.tsx` (или новый
`FullSetupModal.tsx`): поля Домен, Регистратор, Хостинг(сервер), Cloudflare-аккаунт +
тумблеры «Создать зону в Cloudflare», «Прописать NS у регистратора». Поток: `POST ""`
(создать домен) → (desktop) `domain_full_setup` → отчёт по шагам (зона создана / NS
прописаны / что не удалось), тон как у привязки.

**Массовый** (по выделенным): кнопка «Full setup» в `BulkActionToolbar.tsx` → диалог
(сервер + CF-аккаунт + регистратор + те же тумблеры) → `POST /domains/full-setup` →
(desktop) прогон `domain_full_setup` по пачке с конкуренцией → сводный отчёт (как
`CloudflareBindBanner`). Гейт «один прогон за раз», как у привязки/provision.

Desktop-only для шагов выполнения (зона/NS).

Уточнения UX (решения пользователя):
- **Счётчик доменов в выпадашках.** Сервер и CF-аккаунт показывать как «имя — N доменов»,
  наименее загруженные сверху (сортировка по возрастанию N), чтобы сразу видеть, куда
  добавлять. N — из локального списка `useDomains()` группировкой по `server_id` /
  `cloudflare_account_id` (решение: считаем домены в SDMP, не живые зоны — быстро, работает
  и в вебе).
- **«Создать зону».** = `cf_create_zone` (POST /zones) — завести домен как зону в выбранном
  аккаунте, получить `zone_id` + NS; если зона уже есть, не дублировать (fallback
  `get_zone_by_name`). Инлайн-пояснение под тумблером.
- **Регистратор без API.** NS-API умеют только `hostiq` и `namecheap` (десктоп
  `make_service`, `registrars/mod.rs:39`). Новый чистый хелпер
  `registrarSupportsNsApi(provider)` (единственный источник правды, зеркалит десктоп):
  если провайдер не из этих двух или регистратор не выбран → **дизейблить только тумблер**
  «Прописать NS» + подсказка «нет API — пропишите NS вручную». Кнопка «Создать и настроить»
  остаётся активной: домен и зона создаются, NS-шаг просто пропускается (решение).

## Переиспользуем (не плодим нового)
- `matchDomainsToZones`, `normalizeZoneName` — `lib/cfZoneMatch.ts`
- `zonesQuery`, `useCloudflareZones`, `useCloudflareAccounts`, `useCreateZone` — `api/cloudflare.ts`
- `useCloudflareBind`, `autoBindDomainsToCloudflare`, `CloudflareBindBanner` — привязка + баннер
- `useUpdateDomain`, `useCreateDomain`, `useSetNameservers` — `api/domains.ts`
- `useZoneNameservers` — `api/cloudflare.ts`; `useRegistrarDomains` — `api/registrars.ts`
- Бэкенд: `create_domain`, `bulk_assign_cloudflare` — `domain_service.py`
- Десктоп: `cloudflare::client::create_zone`, `registrar_set_nameservers`, `domain_write_back`

## Гарды корректности
- Подсказка ≠ факт: отдельный стиль + `title`; сохранённая привязка как раньше.
- Неоднозначность не угадываем (зеркалит `cfZoneMatch`).
- Мемо-строки не ломать (есть тест на число рендеров).
- Zero-knowledge: бэкенд не ходит в Cloudflare/регистратор; зоны/NS — только десктоп.
- Full-setup идемпотентен (idempotency key); частичный успех — строки отчёта, не краш.
- `Invalid API Token` на скрине: аккаунт с непрочитанными зонами не даёт подсказок
  (корректно). Токен проверить отдельно — фичу не блокирует (листинг зон работает).

## Верификация (end-to-end, десктоп)
1. **Кейс 1 показ:** аккаунт CF с валидным токеном, домены = именам зон → колонка сама
   показывает аккаунт подсказкой «по зоне», без кликов. Веб → «—».
2. **Кейс 1 синхрон:** «Синхронизировать с Cloudflare» → баннер «N of M linked»,
   подсказки становятся сохранёнными; NS пушится из Overview отдельно.
3. **Неоднозначность:** одноимённая зона в 2 аккаунтах → строка «—» (без метки), sync
   пропускает — не угадываем и не шумим.
4. **Overview:** выбрать аккаунт → сохранилось, зона дорезолвилась; NS-запись видна, бейдж
   делегирования (делегировано/pending/расходится) верный; кнопка «Прописать NS» дизейблится
   для регистратора без API.
4a. **Непрочитанный аккаунт:** сломан токен → баннер «N аккаунтов не прочитаны»; домены
   этого аккаунта показаны «—», а не ложным совпадением.
5. **Кейс 2:** мастер нового домена → `full-setup` создаёт домен+связки → десктоп заводит
   зону, (по тумблеру) NS → отчёт по шагам; повтор идемпотентен.
6. Тесты точечно (`npm test` во фронте флакует таймаутами, долг Д12): новый хук матчей,
   рендер подсказки в `DomainRow`, тест мемо-рендеров; бэкенд-тест эндпоинта full-setup.
