# SDMP — навигация по проекту

Этот документ — карта проекта. Читай его в начале каждой сессии, чтобы понимать,
где что лежит и как с этим работать.

> ⚠️ Держи этот файл ≤ 200 строк. Иначе сжигаешь токены каждый запрос.

## Что это за проект

**SDMP (Secure Domain Management Platform)** — десктоп-приложение (Tauri 2) + read-only
веб-панель для массового управления доменами и серверами. Один пользователь ведёт
десятки–сотни доменов: подключает регистраторов (Hostiq, Namecheap), аккаунты Cloudflare
и серверы (FastPanel по SSH), а затем поштучно или пачками разворачивает сайты, выпускает
SSL, прописывает NS, ставит панели.

Продукт переезжает на **zero-knowledge** модель по образцу 1Password: секреты (SSH-пароли,
API-токены) шифруются на клиенте и хранятся на сервере как непрозрачные блобы; выполнение
операций (SSH, Cloudflare, registrar API) уходит в десктоп. Веб становится read-only.

Подробности «зачем» — в `.business/INDEX.md`. Переход исполнен: его спека (`plan.md`,
стадии 0–4) и корневые копии спринтов удалены как отработавшие — ищи их в истории git,
а не на диске. В корне остался только `stage5.md` — launch prep, единственная
невыполненная стадия. Спринты 1–4 живут в `plans/` (там же их итоги и долг).

## Ключевые принципы проекта

1. **Zero-knowledge.** Секреты шифруются на клиенте (Argon2id + libsodium
   `crypto_secretbox_easy`, то есть XSalsa20-Poly1305 — не XChaCha20, как говорилось
   раньше: `dryoc` в десктопе и `libsodium-wrappers` во фронте зовут именно secretbox);
   сервер хранит только непрозрачные ciphertext-блобы и метаданные.
2. **Плотность без тесноты.** Продукт — «пульт управления инфраструктурой» для
   power-user'а: много данных на экране, но иерархия ведёт глаз (см. `design-brief.md`).
3. **Desktop выполняет, web только смотрит.** Любая мутация/выполнение — только в десктопе;
   веб показывает те же метаданные и CTA «Открыть в десктопе» (`sdmp://`).
4. **Идемпотентность.** Массовые операции защищены от двойного выполнения (idempotency keys).
5. **Аудит без секретов.** Действия пишутся в серверный audit log без плейнтекст-секретов.
6. **Не рисуй незнание здоровьем.** Отсутствие или протухание измерения — это отдельное
   состояние (`unchecked`), а не зелёный бейдж. Лестница состояний сервера живёт в одном
   месте на все экраны — `frontend/src/lib/serverStatus.ts`; переписанная заново на каждом
   экране, она уже разъезжалась. У сервера **два независимых сигнала** с разными источниками
   и порогами протухания: доступность (TCP-проверка бэкенда, 6ч) и метрики (десктоп по SSH,
   по кнопке) — сливать их в один нельзя (`docs/ARCHITECTURE.md` § Server signals).

## Стек

Backend: Python 3.12, FastAPI, SQLAlchemy async + asyncpg (Supabase pooler), Alembic,
Celery 5 + Redis. Frontend: React 18 + TypeScript + Vite + TanStack Query. Desktop:
Tauri 2 + Rust (russh, dryoc/sodiumoxide, rusqlite+sqlcipher, keyring). Инфра: Docker
Compose, Nginx. Интеграции: Cloudflare API, Hostiq/Namecheap, FastPanel по SSH.

Детали — в `docs/TECH_STACK.md`.

проект. Читай только нужный файл (по таблице в `INDEX.md`), не загружай всё сразу.

## Папка `plans/`

Технические планы реализации новых функций. Здесь живёт информация **как**. Один план =
одна функция. Здесь же исторические планы миграции — спринты 1–4. В корне из них
остался только `stage5.md` (launch prep, не выполнен); индекс планов и их статусы —
в `plans/README.md`.

## Как работать с проектом

- Перед любой задачей — прочитай этот файл, затем нужные документы из `.business/` и `plans/`.
- Если меняется бизнес-логика — обнови `.business/INDEX.md` и нужные файлы.
- Если меняется технический план — обнови соответствующий план в `plans/`.
- Если появляется новая важная папка или документ — обнови этот `CLAUDE.md`.

## ВАЖНО: план для каждой новой функции

Любая функция, которую мы создаём в любом чате, всегда оформляется планом в папке `plans/`.

Правила:

1. Один план = одна функция. Если план уже есть — работаем с ним.
2. Имя файла: `YYYY-MM-DD-название-функции.md`.
3. План делится на фазы. У каждой фазы статус `[ ]` или `[x]`.
4. В конце плана — итоговый блок: реализован целиком или нет, что осталось.
5. Любой агент обязан актуализировать план после каждой сессии.

## ВАЖНО: завершение каждого чата

В конце каждой сессии записывай рефлексию в файл
`.business/история/YYYY-MM-DD-краткое-название.md` (создавай папку при необходимости).

Формат:

1. Какая задача была поставлена.
2. Как я её решал.
3. Решил ли — да / нет / частично.
4. Эффективно ли решение, что можно было лучше.
5. Как было и как стало.
