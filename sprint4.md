# SDMP — Спринт 4: путь записи блоба секрета (разблокировка фазы A)

## Context

**Зачем этот план.** Спринт 3 дотянул кнопки до готовых Tauri-команд и завёл write-back
результатов. Но его финальное сквозное ревью вскрыло блокирующий дефект: **пути записи
блоба секрета не существует нигде** — а значит ни одна из 26 команд не может отработать,
и цель фазы A («юзабельно для себя end-to-end») не достигнута.

**Дефект подтверждён по коду (4 независимые точки):**
1. `encryptBlob` ([crypto.ts:115](frontend/src/lib/crypto.ts)) — определение без единого вызова.
2. `vault_put_blob`/`vault_delete_blob` — только регистрация в `lib.rs:42-43`, вызовов нет.
3. `ServerCreate` принимает лишь `ssh_password_blob_id: UUID`, не `ssh_password`; при
   `model_config = ConfigDict(from_attributes=True)` действует дефолтный `extra="ignore"` →
   плейнтекст-пароль из формы молча выброшен → `ssh_password_blob_id = NULL`, 200 OK.
4. Миграция 011 дропнула плейнтекст-колонки без конвертации (данных мало, конвертация не нужна —
   но и forward-путь никто не построил).

Итог: пользователь заводит сервер/регистратора/CF-аккаунт и получает пустой credential;
команды падают на «server has no ssh_password_blob_id». **Это задача №1.**

**Подход (урок Спринта 3): приёмка — первой.** Спринт открывается сквозным тестом
(ввести SSH-пароль → blob лёг в БД зашифрованным → `provision`/`ssh_exec` его расшифровал →
SSH подключился). Сегодня он падает на шаге 1; строим до прохождения. Проверять эффект **по
БД и реальному подключению**, не по «secret not in response» (пункт 6 долга: такой тест
холостой). Каждый фикс — с мутационной проверкой (тоже урок Спринта 3: зелёный тест
переживал вырезанный механизм).

Долг Спринта 3 — 12 пунктов в `plans/2026-08-03-sprint3-ui-reachability-writeback.md`
(итоговый блок) и предупреждение в `plans/README.md`. Этот план их разбирает по фазам.

## Фаза 1 — Путь записи блоба (критично, разблокирует всё) · долг №1

**Нарезка: тонкий вертикальный срез сначала** (выбор пользователя). Сперва доказать путь на
ОДНОЙ сущности сквозняком, потом развернуть — чтобы не тиражировать непроверенный паттерн на
все формы (урок Спринта 3: паттерн расходился с реальностью, пока не сверен на живом коде).

**Фаза 1a — тонкий срез (SSH-пароль сервера), до зелёной сквозной приёмки.**
Единый поток «ввёл секрет → зашифровал → загрузил → привязал» на одной форме:
на submit сгенерировать `blob_id` (uuid) → `encryptBlob(plaintext, masterKey)` →
`vault_put_blob(blob_id, ciphertext, blob_kind, device_id)` → `blob_id` в
`server.ssh_password_blob_id` → create/update.
- **Инвариант ZK:** на сервер уходит только ciphertext-blob и `blob_id`, не плейнтекст.
- Приёмка (сегодня падает на шаге 1): завести сервер с SSH-паролем в десктопе → в БД есть
  строка `blobs` и `ssh_password_blob_id` заполнен → `ssh_exec`/`provision` расшифровал и
  **реально подключился по SSH**. Проверка по БД и по факту подключения, не по тексту ответа.
  Тест — с мутационной проверкой.

**Фаза 1b — развернуть паттерн** на остальные секрет-несущие формы: `fastpanel_password`,
регистратор (`api_key`/`api_secret`), Cloudflare (`api_token`). Правка/замена секрета —
перезапись того же `blob_id` (версионирование в `blobs` уже есть); удаление сущности →
`vault_delete_blob`.

Критические файлы: `frontend/src/lib/crypto.ts`, `frontend/src/components/` (формы
сервера/регистратора/CF), `desktop/src-tauri/src/commands/vault.rs`,
`frontend/src/api/{servers,registrars,cloudflare}.ts`.

## Фаза 2 — Громкий провал вместо тихой потери · долг №2

- `extra="forbid"` на `ServerCreate/Update`, `CloudflareAccount*`, `RegistrarAccount*`.
- Вычистить плейнтекст-поля (`ssh_password`, `fastpanel_password`, `api_token`, `api_key`,

## Фаза 3 — Опасные пути, ставшие достижимыми · долг №3, №5

Чекбокс `withDb` и работающая запись делают эти дефекты активно вредными:
- **`sdmp://bulk-provision`** (№3) — единственная ветка deep link мимо гейта подтверждения и
  с выбросом результата: `site_only=false` ⇒ на каждом домене создаётся FTP-аккаунт, пароли N
  аккаунтов теряются. Гард `bulk_run_status` ключуется на наборе id и по одному домену не
  защищает. Провести через тот же гейт и вернуть/показать результаты (или явно запретить FTP в
  bulk). Парадокс сейчас: веб-ссылка исполняет по-настоящему, а десктопная кнопка Provision
  бьёт в 404 — веб функциональнее и опаснее десктопа.
- **Проверки существования БД/FTP** (№5) — имя базы детерминированное (`{slug}_db`), проверки
  нет; повтор идёт в mysql-fallback с `CREATE USER IF NOT EXISTS`, который существующему юзеру
  пароль **не меняет** → команда возвращает 0 и свежий пароль, модалка показывает «copy now»,
  а он не аутентифицирует. Добавить проверку существования до создания.

Критические файлы: `frontend/src/lib/deepLink.ts`,
`desktop/src-tauri/src/commands/provision.rs`, `desktop/src-tauri/src/ssh/fastpanel.rs`.

## Фаза 4 — Видимость упавшего provision · долг №4

Колонка `last_provision_error` есть, тестов два, пишущего кода ноль (единственное
присваивание — сброс `Some(None)`). На провале `stepped?` возвращается **до** блока
write-back, поэтому упавший прогон не пишет ничего → «Last error» всегда «—»,
`failedAtSslCount` не станет ненулевым. Писать ошибку до раннего возврата; показать в UI.

Критические файлы: `desktop/src-tauri/src/commands/provision.rs`,
`backend/app/schemas/domain.py`, `frontend/src/pages/Domains.tsx`.

## Проверка (сквозной сценарий приёмки — тот, что падал в Спринте 3)

Полный путь в десктопе: завести сервер с SSH-паролем → Install FastPanel → завести домен →
CF DNS-редактор (A-запись) → Set NS → Provision c `withDb` → повтор (срабатывают гарды
`site_exists`/`ssl_exists`/«уже установлено») → упавший provision виден как «Last error».
В БД: секретов в плейнтексте нет, но `*_blob_id` заполнены и blob'ы расшифровываются.
Тесты `pytest`/`cargo test`/`vitest` зелёные; новые тесты проверяют эффект по БД и прошли
мутационную проверку.

Оформить как `plans/2026-08-04-sprint4-secret-write-path.md` (фазы `[ ]/[x]`, итоговый блок).
