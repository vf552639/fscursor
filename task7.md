## Context (зачем это)

Пользователь попросил изучить вкладку Domains, предложить улучшения и обратить
внимание на техдолг. Аудит вскрыл, что вкладка страдает не косметикой, а
**структурной ложью**: значительная часть кнопок исполнения бьёт в бэкенд-роуты,
которых не существует (404), потому что после миграции на zero-knowledge
(«desktop исполняет, web смотрит») исполнение переехало в Tauri-команды, а старый
HTTP-слой исполнения во фронте не убрали и местами оставили подключённым к UI.
Параллельно модель домена хранит данные (сроки истечения, SSL), которых нет в
списке, а сам файл разросся до God-компонента.

Пользователь выбрал в работу **все четыре направления**; по долгу №1 выбран путь
«сейчас убрать фикцию, гранулярные операции — в будущий план».

Итог этого документа — **роадмап из 4 планов**. При старте реализации каждый
оформляется отдельным файлом в `plans/YYYY-MM-DD-*.md` (правило CLAUDE.md
«один план = одна функция»). Ниже план №1 детализирован до исполнения, планы
2–4 — очерчены.

### Долг №1 — мёртвый слой исполнения (404)
- ~~`apiPost` (`frontend/src/api/client.ts:135`) — чистый HTTP (axios), **не**
  Tauri-aware. Значит все хуки на `apiPost` в вебе и десктопе идут по HTTP.~~
  **Посылка неверна, исправлено по факту кода (2026-08-11).** `apiPost`
  Tauri-aware ровно как соседи: `frontend/src/api/client.ts:136` —
  `if (isTauri()) return tauriRequest<T>("POST", …)`, то есть в десктопе вызов
  уходит Tauri-командой `api_request`. Вывод долга №1 от этого не меняется:
  `api_request` — прокси в тот же REST API, где перечисленных ниже роутов нет,
  так что хуки дают 404 на ОБОИХ транспортах, а не только в вебе. Механика
  другая, диагноз тот же.
- В `backend/app/api/routes/domains.py` объявлены только: list, `failed-export.csv`,
  get/{id}, create, `bulk`, `bulk-structured`, put/{id}, delete/{id},
  `bulk-assign-server`, `bulk-assign-cloudflare`, `bulk-import`,
  `bulk-import-errors/{token}`. **Больше ничего.**
- Значит эти хуки всегда дают 404 (нет ни роута, ни Tauri-команды):
  `useBulkProvisionDomains`, `useBulkFullSetup`, `useRefreshSsl`, `useCreateSite`,
  `useCreateDb`, `useDbCredentials`, `useRequestSsl`, `useCancelSsl`,
  `useSetNginxOverride`, `useGetNginxOverride` (все в `api/domains.ts`).
- Рабочая Tauri-реализация массового provision **есть** —
  `runBulkProvisionDomains` (`api/domains.ts:761`) → команда `provision_bulk`, но
  вызывается **только** из deep-link `sdmp://bulk-provision` (`lib/deepLink.ts:192`),
  а **не** из кнопки тулбара. Кнопка «Provision» тулбара зовёт 404-хук
  `useBulkProvisionDomains` (`Domains.tsx:312,480`).
- `DomainDetailModal` — 5 вкладок; **4 из 5 — фикция**: `overview`/Create Site,
  `db`/Create DB, `ssl`/Request+Refresh SSL, `nginx`/override — все на 404-хуках.
  Работает только вкладка `ns` (`useSetNameservers` → Tauri
  `registrar_set_nameservers`, `api/domains.ts:318`).
- Реально существующий путь исполнения ровно один: всё-в-одном
  `provision_domain` / `provision_bulk` (SSH: сайт + FTP + сертификат за прогон).
  Одиночный provision на странице сделан правильно (Tauri, гейт от двойного
  клика) — его не трогаем.

## План №1 — Чистка слоя исполнения (детально)

**Цель:** убрать всё, что зовёт несуществующие роуты, починить единственный
дёшево-чинибельный путь (bulk-provision через готовый `provision_bulk`), и не
задеть работающее (одиночный provision, вкладка NS).

### Что чиним (подключаем к рабочему Tauri)
- **Bulk «Provision» тулбара.** Переключить `handleBulkProvision`
  (`Domains.tsx:480`) с `useBulkProvisionDomains` на путь
  `runBulkProvisionDomains(userId, ids)` (Tauri `provision_bulk`) — тот же вызов,
  что уже отработан в `lib/deepLink.ts:192` (взять его как образец: userId из
  `useAuthStore`, гейт, показ результата через ту же очередь показов, что у
  одиночного provision). Кнопку показывать только под `isTauri()`.

### Что удаляем (фикция без Tauri-подложки)
- Хуки из `api/domains.ts`: `useBulkProvisionDomains`, `useBulkFullSetup`,
  `useRefreshSsl`, `useCreateSite`, `useCreateDb`, `useDbCredentials`,
  `useRequestSsl`, `useCancelSsl`, `useSetNginxOverride`, `useGetNginxOverride`
  и связанные типы/константы, если больше не используются.
- В `Domains.tsx`: `useRefreshSsl`/`handleBulkRefreshSsl`,
  `useBulkFullSetup`/`showFullSetup`/`BulkSetupWizard`-ветку — убрать кнопки
  «Refresh SSL» и «Run Full Setup» из тулбара (у обеих нет Tauri-подложки).
- В `DomainDetailModal.tsx`: удалить вкладки `db`, `ssl`, `nginx` и кнопку
  «Create Site» на `overview`. Оставить `overview` как read-only-инфо и рабочую
  вкладку `ns`. Модалка ужимается с 5 вкладок до 2.
- Мёртвый **`EditDomainModal`** (`Domains.tsx:100–247`) и его состояние
  `editingDomain`/`setEditingDomain` — удалить целиком (долг №2 закрывается здесь
  же попутно).
- Компоненты, оставшиеся без вызывающих (`BulkSetupWizard`,
  `MultiTaskProgressModal`/`TaskProgressModal`, если после удаления Full Setup они
  больше нигде не нужны) — проверить grep’ом и удалить.

### Что НЕ трогаем
- Одиночный `useProvisionDomain` / диалог provision (`Domains.tsx:829+`) — работает.
- Вкладка `ns` в `DomainDetailModal`, `useSetNameservers` — работает через Tauri.
- Bulk-assign server/CF, bulk-import, create/bulk-create — реальные роуты.

### Явно откладываем (в отдельный будущий план «Гранулярные операции домена»)
Возврат Create Site / Create DB / Request SSL / Refresh SSL / nginx-override —
через **новые Tauri-команды + SSH-логику** (повтор certbot, шаблон nginx,
mysql-create). Это фича, а не чистка; в объём плана №1 не входит по решению
пользователя.

### Критерий готовности
Ни одна кнопка вкладки Domains и её модалок не даёт 404. Массовый provision
работает через `provision_bulk`. Мёртвого исполнительного кода в
`api/domains.ts`/`Domains.tsx`/`DomainDetailModal.tsx` не осталось. Тесты
(`Domains.provision.test.tsx`, `Domains.provisionerror.test.tsx`,
`domains.bulkprovision.test.ts` и др.) зелёные / актуализированы.

## Кросс-каттинг: токены и тёмная тема

`design-brief.md` описывает **общеприложенческий** редизайн: единый слой
CSS-переменных (токены) + тёмная тема как основная, для всех экранов сразу.
Сделать тёмную тему **только** для Domains — значит создать визуальный остров,
несовместимый с остальным (светлым) приложением. Поэтому:
- В плане №4 берём только безопасную структурную часть (разбивка компонента).
- Полную токенизацию/тему НЕ делаем точечно на Domains. Это отдельная
  общеприложенческая инициатива (или Domains становится её пилотом — но это
  осознанное продуктовое решение уровня всего фронта, не задача вкладки).

## Верификация (для плана №1)

1. `cd frontend && npm test` — гоняем существующие тесты Domains/provision; чиним
   те, что ссылались на удалённые хуки.
2. Grep-проверка отсутствия мёртвых вызовов:
   `grep -rn "bulk-provision\|bulk-full-setup\|create-site\|refresh-ssl\|ssl-request\|ssl-cancel\|create-db\|nginx-override\|/set-ns" frontend/src`
   — должны остаться только комментарии/тесты, не живые `apiPost`.
3. Grep-проверка, что удалённые хуки нигде не импортируются.
4. Ручной прогон в десктопе (Tauri): выделить 2–3 домена → «Provision» тулбара →
   убедиться, что идёт `provision_bulk`, а не сетевой 404; открыть
   `DomainDetailModal` → видны только `overview` (read-only) и `ns`; вкладка NS
   пушит nameservers как раньше.
5. Веб (read-only): кнопок исполнения без Tauri не осталось; 404 в консоли сети
   при обычной работе с вкладкой нет.
