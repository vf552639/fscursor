# ТЗ на редизайн SDMP — Secure Domain Management Platform

**Тип продукта:** десктоп-приложение (Tauri) + веб-панель (read-only) на React
**Кому:** UI/UX-дизайнеру
**Статус:** редизайн существующего интерфейса (визуальный + системный, без изменения продуктовой логики)
**Дата:** 2026-08-02

---

## 1. Что это за продукт и кто им пользуется

SDMP («SDMP Infrastructure») — рабочий инструмент для **массового управления доменами и серверами**. Один пользователь ведёт десятки–сотни доменов: подключает аккаунты регистраторов (Hostiq, Namecheap), аккаунты Cloudflare и серверы (панель FastPanel, ставится по SSH), а затем — поштучно или пачками — назначает домену сервер + регистратора + зону Cloudflare, прописывает NS, разворачивает сайт, выпускает SSL и ставит панель.

**Портрет пользователя:** технический power-user (агентство / хостинг-реселлер / оператор большой сетки сайтов). Работает быстро, пачками, много времени проводит в таблицах, ценит плотность информации, горячие клавиши и предсказуемость. Не турист — не нужно «объяснять на пальцах», нужно **не мешать и не тормозить**.

**Ключевая ценность и настроение бренда:** это **пульт управления инфраструктурой**, работающий с секретами (SSH-пароли, API-ключи, токены хранятся в клиентски-зашифрованных блобах, AES-256-GCM / Argon2id + libsodium). Отсюда две несущие эмоции, которые должен передавать интерфейс:
1. **Контроль и точность** — плотно, инженерно, ничего лишнего, всё под рукой.
2. **Доверие и безопасность** — состояние «заперто / открыто», работа с секретами и шифрованием должны читаться как надёжные, а не как случайные элементы формы.

Тон — спокойный профессионализм, «cockpit», а не маркетинговый лендинг. Референсы по духу (для калибровки, не для копирования): Linear, Vercel Dashboard, Tailscale admin, 1Password, Raycast.

## 2. Зачем редизайн — что не так сейчас

Текущий интерфейс — типовая светлая «админка», собранная функционально, но без визуальной системы. Конкретные проблемы, которые редизайн обязан решить:

| # | Проблема сейчас | Что нужно |
|---|---|---|
| 1 | **Нет дизайн-системы.** Цвета, отступы, размеры шрифта захардкожены инлайн-стилями (`style={{}}`) в каждом файле, дублируются десятками копий. | Единая система токенов (цвет / типографика / отступы / радиусы / тени), из которой собираются все экраны. |
| 2 | **Только светлая тема.** В хедере есть иконки ☀/🌙, но они показывают тост «Dark mode coming soon». | Полноценные **тёмная и светлая** темы. Тёмная — основная (см. §4). |
| 3 | **Тема акцента переключается в рантайме** (Blue / Purple / Green / Red / Amber) через скрытую «Tweaks»-панель. | Дизайн должен поддерживать **сменный акцентный цвет** как ось темы, не ломаясь ни на одном из вариантов. |
| 4 | **Иконки — эмодзи и юникод-глифы** (⊞ ▤ ☁ 🔔 ⚙ 🖥 ⚡). Выглядит несогласованно, разъезжается по платформам. | Единый векторный icon-set (line-стиль), один вес, одна сетка. |
| 5 | **Графики — фейковые.** `MiniChart`/`genBars` рисуют случайные бары. | Спроектировать **честную** дата-визуализацию под реальные метрики (CPU/RAM/SSD, аптайм, счётчики). |
| 6 | **Плоская иерархия, мелкий тесный текст** (11–14px, всё серо-белое), слабые пустые/ошибочные состояния. | Осмысленная типографическая иерархия, дышащая плотность, проработанные состояния. |
| 7 | Шрифт Inter объявлен, но **не подключён вебфонтом** — рендерится системным фолбэком. | Явно выбрать и подключить шрифтовые пары (см. §5). |

**Важно для дизайнера:** технически «слоя токенов» сейчас нет вообще. Первый практический шаг редизайна на стороне разработки — вынести всё в CSS-переменные. Поэтому **макет нужно сдавать в токенах** (см. §11 «Формат сдачи»), а не как набор отдельных экранов с произвольными значениями.

## 3. Цели редизайна (по чему меряем успех)

1. Интерфейс читается как **цельная система** — один экран нельзя спутать с «другим приложением».
2. **Плотность без тесноты** — на экране много данных, но глаз не устаёт, иерархия ведёт.
3. **Тёмная тема — первого класса**, не инверсия задним числом.
4. Явный **визуальный язык безопасности** (заперто/открыто, секрет скрыт/раскрыт, шифрование).
5. Явное **различие desktop vs web** (см. §8) — пользователь всегда понимает, где действие выполнится, а где только откроется в десктопе.
6. **Массовые операции** (выбор пачкой, bulk-тулбар, прогресс задач) — понятны и не пугают.
7. Всё переиспользуемо: из компонентов §7 собираются все 11 экранов §6.

**Вне скоупа:** менять продуктовую логику, роутинг, названия сущностей, набор функций. Это редизайн внешнего вида и системы, а не переработка продукта.

## 4. Цвет и темы

**Две темы, тёмная — основная.** Обе строятся на нейтральной шкале + семантике + сменном акценте. Ниже — не финальная палитра, а **требования и опорные значения**; дизайнер подбирает точные оттенки и проверяет контраст.

**Нейтральная шкала (surface/border/text)** — нужна полноценная лесенка (напр. 9–11 ступеней) для: фон приложения → фон карточки → приподнятая поверхность (модалка/поповер) → бордеры → разделители строк → приглушённый текст → основной текст. Сейчас всё держится на 3–4 значениях (`#fff` / `#e5e7eb` / `#6b7280` / `#111` в светлой; фон `#f4f6f9`) — этого мало.

**Семантические цвета** (должны работать в обеих темах, с фоновой заливкой и бордером для «плашек»):
- success / online — сейчас `#16a34a` (bg `#f0fdf4`, border `#bbf7d0`)
- warning / pending — `#d97706` (bg `#fffbeb`, border `#fde68a`)
- danger / offline — `#dc2626` / `#b91c1c` (bg `#fef2f2`, border `#fecaca`)
- info / idle — нейтральный серый `#6b7280`
- CPU-рампа (для метрик): ≥80% → danger, ≥60% → warning, иначе → accent

**Акцент (сменный).** Пользователь может выбрать Blue / Purple / Green / Red / Amber. Дизайн должен:
- иметь **дефолт** (рекомендую сине-стальной, ближе к текущему `#2563eb`, но подобрать «свой», не бутстраповский);
- задавать акцент как **одну токен-переменную** с производными (hover, активный фон-тинт ~12% альфы, фокус-ринг), чтобы 5 вариантов получались подстановкой;
- гарантировать читаемость акцентного текста/иконок на поверхностях в обеих темах для **всех пяти** цветов (красный акцент не должен путаться с danger — предусмотреть, как их развести).

**Контраст:** весь текст и интерактив — минимум WCAG AA (4.5:1 для основного текста, 3:1 для крупного/иконок и границ контролов). Проверить в обеих темах и на всех акцентах.

## 5. Типографика

Сейчас: `Inter` (системный фолбэк) + моноширинный для IP/ID/значений конфигов. Требуется осознанная пара, подключённая вебфонтом (или бандлом в приложение), с чётной шкалой.

- **Основной / UI-текст:** гротеск с хорошей читаемостью в мелких кеглях и плотных таблицах. Inter допустим, но рассмотреть более характерную альтернативу (напр. Geist, IBM Plex Sans, Söhne-подобные). Нужна поддержка **табличных цифр** (`tabular-nums`) — в таблицах доменов/серверов цифры должны стоять в колонку.
- **Моноширинный:** обязателен и важен — это язык продукта (IP, ID задач, ключи конфигов, NS-записи, фрагменты токенов). Выбрать качественный моно (напр. Geist Mono, JetBrains Mono, IBM Plex Mono) и сделать его **осознанной частью айдентики**, а не просто `monospace`.
- **Шкала:** задать явную типо-шкалу (напр. 11 / 12 / 13 / 14 / 16 / 20 / 24 / 32) с ролями (caption / label / body / body-strong / h3 / h2 / h1) и весами. Uppercase-лейблы таблиц (сейчас 11.5px, letter-spacing) — сохранить как приём, но систематизировать.
- Дать правила для **числовых/статусных** данных: где моно, где tabular-nums, как выравниваются метрики.

## 6. Экраны (полный инвентарь)

Приложение — это **один шелл** (`DesktopWorkspace`): фикс. левый сайдбар + верхний хедер + область контента, между «страницами» переключается локальным состоянием (не роутингом). Плюс отдельные экраны аутентификации по роутам.

### 6.1. Шелл / навигация (каркас — центральный экран редизайна)
- **Левый сайдбар** (fixed, ширина настраивается 160–260, дефолт 200): лого-плитка «SD» + вордмарк «SDMP / INFRASTRUCTURE»; пункты **Dashboard / Servers / Domains / Cloudflare / Notifications / Activity / Settings** (иконка + подпись, активный — тинт акцентом); внизу закреплён индикатор **System Status** (зелёная пилюля).
- **Верхний хедер** (высота ~57): справа — колокол уведомлений со счётчиком непрочитанных, переключатель темы (сделать **рабочим**), меню аккаунта (аватар-инициал + email → Lock / Logout).
- **Контент:** отступ под сайдбар/хедер, анимация появления при смене страницы.
- Нужен **compact-режим** (уменьшенная плотность) — уже существует как настройка, заложить в систему.

### 6.3. Экраны аутентификации / доступа (отдельные роуты, «за пределами» шелла)
- **Login** — email + мастер-пароль + опц. TOTP. У **web** отдельная ветка с плашкой «Read-only web dashboard». Это **лицо продукта** — проработать особенно (см. §10 signature).

## 7. Компоненты для дизайна (дизайн-система)

Собрать библиотеку компонентов — из них строятся все экраны. Существующий набор (файл `Primitives.tsx`), который нужно пересобрать по-новому:

- **Поверхности:** Card (+ header/title/body), Modal, поповер/дропдаун, приподнятые поверхности.
- **Управление:** Button (варианты primary / secondary / danger / ghost; размеры sm/md/lg; состояния hover/active/disabled/loading), Input, Select, чекбокс (важен для bulk-выбора), тумблер, табы, поиск.
- **Индикация:** Badge (gray/blue/green/yellow/red/purple), StatusDot, StatusBadge (жизненный цикл домена — см. ниже), пилюля System Status.
- **Данные:** таблица (заголовки, строки, hover, выбранное состояние, сортировка, зебра/разделители, tabular-nums), StatCard, дата-виз (шкалы CPU/RAM/SSD, спарклайн/мини-график, шкала лимита SSL-пула), InfoRow, копи-кнопка для моно-значений.
- **Bulk & прогресс:** BulkActionToolbar (появляется при выборе строк — спроектировать появление/закрепление и счётчик выбранного), BulkSetupWizard (пошаговый мастер), TaskProgressModal / MultiTaskProgressModal (прогресс одной и нескольких задач).
- **Состояния:** EmptyState, ErrorState, loading/skeleton, toast (успех/ошибка/инфо).
- **Секреты:** RevealSecret / UnlockModal — паттерн «раскрыть секрет» (см. §9).

**Жизненный цикл домена** (реальная последовательность статусов — годится как основа для «пайплайн»-визуализации, см. §10):
`new → ns_pending → provisioning → site_created → ssl_pending → active` (+ ветка `failed`). Это настоящая последовательность — нумерация/этапность здесь оправданы и несут смысл.

## 8. Desktop vs Web — обязательная ось UX

Это **не косметика, а несущая механика продукта**, её нужно выразить визуально.

- **Web-панель — read-only для изменений.** Любое действие, меняющее инфраструктуру, на вебе не выполняется, а **открывается в десктопе** через диплинк `sdmp://…` (provision, bulk-provision, install-fastpanel, add-server, test-cloudflare). Компонент `OpenInDesktop`: в Tauri — обычная кнопка действия; на web — ссылка «Открыть в приложении ↗».
- **Задача дизайна:** единый узнаваемый визуальный маркер «это действие уйдёт в десктоп-приложение» — чтобы на вебе пользователь не тыкал в глухие кнопки. Продумать состояние кнопки/иконку/подсказку.
- **Замок / хранилище:** на desktop — постоянно разблокированный vault и экран **Lock**; на web — эфемерный ключ в памяти, самоочистка через 5 минут простоя, существует только чтобы «раскрывать секреты». Показать это состояние в UI (индикатор «vault unlocked / auto-lock через N мин»).
- **Login** прямо разделяет ветки: web показывает плашку *«Read-only web dashboard. Actions that change infrastructure open in the SDMP desktop app.»* — оформить как осознанный элемент, а не серую сноску.

## 9. Безопасность и секреты — отдельный визуальный язык

Продукт хранит и раскрывает чувствительные данные. Нужен согласованный паттерн:
- **Скрытый секрет** (токен/пароль замаскирован, напр. `sk_live_••••••••`) → действие **Reveal** → раскрытый секрет + **копирование** → **авто-скрытие/очистка** (на вебе plaintext сам стирается через 30 сек). Показать таймер/состояние «скоро скроется».
- **Состояние хранилища:** заперто / открыто (Lock / Unlock vault) — сильный, «физический» визуальный образ, это точка доверия.
- **Панель Encryption** (Settings) — read-only, объясняет AES-256-GCM. Сделать её убедительной и спокойной (не пугающей), она — знак качества.
- Общий принцип: безопасность = **уверенность, а не тревога**. Замки/щиты — минималистично и по делу, без «кибер-панк» клише.

## 10. Визуальная идея и signature-элемент

Дизайнер свободен в творческом решении, но ТЗ задаёт рамку и ожидает **один запоминающийся фирменный элемент**, а не просто аккуратную админку.

**Рекомендуемое направление (можно оспорить с обоснованием):** «инфраструктурный пульт» — тёмная основная тема, инженерная плотность, стальной/сине-серый акцент по умолчанию, честная моно-типографика для технических значений, спокойные состояния.

**Кандидаты на signature-элемент** (выбрать один и довести до идеала, остальное держать тихим):
1. **Пайплайн провижининга домена** — визуализация жизненного цикла `new → … → active` (§7). Это ядро продукта; сделать его выразительным (в таблице компактно, в DomainDetailModal — развёрнуто, с прогрессом bulk-операций).
2. **Состояние хранилища / замок** на экранах Lock и Login — «физика безопасности» как лицо бренда.
3. **Health-виз серверов** — живая, честная визуализация нагрузки (CPU/RAM/SSD/аптайм) как «приборная панель».

Рекомендация: signature = **пайплайн провижининга** (он уникален именно для этого продукта и встречается на главном экране Domains), а замок/health — сильные поддерживающие мотивы. Всё остальное — дисциплинированно и тихо.

**Чего избегать:** дефолтная бутстрап-синева; перегруз анимацией; «энтерпрайз-серость» без характера; декоративные иконки-эмодзи; графики ради графиков (только честные данные).

## 11. Обязательные требования к качеству

- **Токены прежде экранов.** Сдать систему переменных (color / type / space / radius / shadow / z-index / motion), из которой выводится всё остальное. Это напрямую ляжет в CSS-переменные на разработке.
- **Обе темы** проработаны, не автоинверсия. Тёмная — дефолт.
- **5 акцентов** проверены на обоих фонах.
- **Адаптив:** десктоп — приоритет (это desktop-app), но веб-панель должна деградировать корректно вплоть до планшета/узкого окна; таблицы — со скроллом внутри своего контейнера, страница по горизонтали не едет.
- **Доступность:** контраст AA, видимый фокус на всех интерактивных элементах, состояние клавиатурной навигации (продукт для power-users — заложить hover/focus/selected явно), уважение `prefers-reduced-motion`.
- **Состояния для каждого компонента:** default / hover / active / focus / disabled / loading / error / empty / selected.
- **Иконки:** единый line-набор, один вес и сетка; заменить все эмодзи.
- **Копирайт в UI** — по-человечески, от лица пользователя, активным залогом, sentence case, действие названо тем, что произойдёт («Provision», а не «Submit»), одно имя действия через весь флоу. Ошибки — что случилось и как починить, без извинений. Пустые экраны — приглашение к действию.

## 13. Технические ограничения (справочно, для дизайнера)

Чтобы макет лёг на код без потерь:
- Стек: **React 18 + Vite + TypeScript**, стили — переедут на **CSS-переменные + Tailwind** (сейчас инлайн). Проектируйте в токенах — это прямое соответствие переменным.
- Иконки будут вставлены как SVG-компоненты (нужен единый набор).
- Тема акцента переключается **в рантайме** пользователем (§4) — акцент должен быть одной переменной с производными.
- Дата-виз рисуется в вебе (SVG/CSS), тяжёлых чарт-библиотек нет — держите визуализации реалистично-простыми (шкалы, спарклайны, компактные бары), но **на честных данных**.
- Это desktop-first приложение (Tauri) с дополнительной web-сборкой — приоритет плотных десктопных разрешений.

**Резюме одной фразой:** превратить функциональную светлую админку в цельный, тёмный-по-умолчанию «пульт управления инфраструктурой» с настоящей дизайн-системой, честной дата-визуализацией, внятным языком безопасности и явным различием desktop/web — с одним запоминающимся signature-элементом (пайплайн провижининга домена).
