# Hostiq DI-API v3 — справочник по реальному API

Как SDMP-десктоп разговаривает с регистратором Hostiq: какой адрес у API, чем он
авторизует, какую форму ответа отдаёт, где молча делает не то, о чём его просили, и чего
у него нет вовсе. Контракт установлен **живой проверкой боевым токеном** на реальном
аккаунте — **127 доменов, из них 120 `Active`** — дата проверки **2026-08-17**.
Реализация — `desktop/src-tauri/src/registrars/hostiq.rs`.

> ⚠️ **Зачем этот документ.** Предыдущий клиент Hostiq в десктопе был **ВЫДУМАН**: он бил
> в `https://hostiq.ua/api` с заголовком `Authorization: Bearer`. Такого API не
> существует — `/api/domains` отдаёт **404 HTML**, эндпоинта `PUT
> /domains/{domain}/nameservers` нет. То есть смена NS у Hostiq не «сломалась», она не
> работала никогда. Настоящий API нашли и разобрали с нуля живой проверкой. Без этого
> документа следующий агент повторит весь путь заново — **ровно это однажды и произошло**.

> ⚠️ **Данные в примерах обезличены.** Форма ответа (структура JSON, имена полей, коды
> HTTP, текст сообщений об ошибках) сохранена точь-в-точь; боевые домены и id заменены
> плейсхолдерами (`example.com`, `10000001`). **Исключение — `betify2.com` и его
> `domainid` 245736**: это тестовый домен стенда, уже названный в плане и в истории
> коммитов, он оставлен как якорь для перепроверки. **Токен и любые его фрагменты в
> документе отсутствуют** и попадать сюда не должны ни под каким видом; в примерах он
> всегда `<token>`.

> **Каждый факт помечен:** «сверено вживую (2026-08-17)» — подтверждено запросом боевым
> токеном; «не сверено» — знаем из кода/рассуждения, но живьём не снимали (сводка — §6).

## 0. Ключевые факты (прочитай первым)

1. **База — `https://hostiq.ua/clients/di-api/v3`.** Не `hostiq.ua/api` (не существует),
   не поддомен `api.`. Константа `HOSTIQ_API` в `hostiq.rs`.
2. **Авторизация — один заголовок `X-Authorization-Token: <token>`.** Не `Authorization:
   Bearer`, не query-параметр. **Email для авторизации не нужен вовсе**: у DI-API v3 нет
   второго credential'а, «hash» из личного кабинета **и есть** токен. Поле «API User
   (email)» в форме Hostiq было лишним и снято.
3. **Тело запроса — только JSON.** Form-encoded API отбивает `400 Syntax error` (§4.1).
4. **Чтения nameservers у API НЕТ вовсе** — ни поля, ни эндпоинта (§5). Источник «как
   есть» в этом проекте — реестр через RDAP (`desktop/src-tauri/src/rdap.rs`). Не ищи
   эндпоинт, которого нет.
5. **`domainid` добывается ТОЛЬКО полным листингом аккаунта** и сопоставлением по имени
   на клиенте: фильтр по имени домена API молча игнорирует (§4.3). Цена одной смены NS —
   выкачка всех доменов аккаунта.
6. **Пять ловушек этого API — молчаливые.** Он не отвечает ошибкой, а тихо делает не то,
   о чём его просили: откатывает `limit`, игнорирует `filter`, отдаёт `400` со словом
   `"error"` вместо причины. Все пять — §4; каждая помечена комментарием в коде там, где
   на неё поставлен гейт.
7. **Запись NS работает** — сверено вживую на `betify2.com`: ответ `{"result":"success"}`,
   реестр обновился примерно за **20 секунд**.

## 1. Контракт (сверено вживую 2026-08-17)

| Что | Значение |
|---|---|
| База | `https://hostiq.ua/clients/di-api/v3` |
| Авторизация | заголовок `X-Authorization-Token: <token>` |
| Формат тела | **JSON** (`Content-Type: application/json`); form-encoded → `400` |
| Конверт ошибки | вложенный: `{"error":{"code":400,"message":"…"}}` |
| Список доменов | `GET /domain/list?limit=<n>&offset=<n>` → `{domains:[…], count, total}` |
| Поля домена | `id, domainname, expirydate, status, regdate, nextduedate, donotrenew, dnsmanagement, …` — **nameservers среди них нет** |
| Смена NS | `POST /domain/changeNameServer`, тело JSON |
| `domainid` в теле | только **ЧИСЛО**; строкой `"245736"` → `400 Bad Request` |
| Число NS | `ns1` + `ns2` обязательны, дальше до `ns5` |
| Чужой `domainid` | `403 Forbidden` |

### 1.1 Заголовки запроса

```
X-Authorization-Token: <token>
Content-Type: application/json
Accept: application/json
```

Токен приезжает вставкой из личного кабинета, а вставка охотно тащит перевод строки и
пробелы по краям — в HTTP-заголовок такое значение не кладётся вовсе. Поэтому в
`HostiqService::with_base_url` он `trim()`-ится, а невалидный символ становится **ошибкой
запроса**, а не паникой внутри tauri-команды (`headers()`).

⚠️ **Токен уходит ЗАГОЛОВКОМ — и на этом стоит вся политика текста ошибок.** Транспортную
ошибку `reqwest` в `hostiq.rs` печатают как есть, вместе с адресом, который `Display`
дописывает сам: в URL секретов нет. У соседнего клиента (`namecheap.rs`) ровно поэтому всё
иначе — там credential едет query-параметром, и адрес из текста ошибки вычищается. Разница
между двумя клиентами — следствие разных способов авторизации, **а не недосмотр**;
выравнивать их «под один стиль» нельзя. Если Hostiq однажды переедет на ключ в
query-строке, эти строки станут утечкой.

### 1.2 Форма ошибки — вложенный конверт

**Сверено вживую (2026-08-17).** Тело неуспешного ответа:

```json
{"error":{"code":400,"message":"Syntax error"}}
```

Читать надо **вложенный** `error.message`. Без этой ветки любой отказ API выглядел бы
«нераспознанным ответом», то есть выглядел бы поломкой прокси, а не отказом регистратора.
В `error_message` рядом оставлены ключи верхнего уровня (`message`, `error` строкой,
`detail`, список `errors`) — они встречались у Hostiq и стоят дешевле, чем ещё один способ
получить «нераспознанный ответ».

⚠️ **HTTP 2xx — ещё не успех.** Ответить `200` может не Hostiq: страница корпоративного
прокси, WAF, капча, портал публичного Wi-Fi. Поэтому `call()` считает ответ данными только
если тело — JSON **и** в нём не распознан конверт отказа. Цена ошибки в другую сторону
была бы велика: приняв HTML-заглушку за успех, `set_nameservers` вернул бы `Ok(true)`, а
`commands::registrars::ns_outcome_plan` записал бы `ns_status = "ok"` и строчку
`registrar.ns_set` в audit log — **аудит утверждал бы смену, которой не было**.

## 2. `GET /domain/list` — единственный источник фактов о доменах

### 2.1 Форма ответа — **сверено вживую (2026-08-17)**

**Запрос:** `GET /clients/di-api/v3/domain/list?limit=1000&offset=0` · **200**

Ответ — объект с массивом и двумя счётчиками (обезличено; в `domains[]` оставлены только
те поля, значения которых мы действительно снимали):

```json
{"domains":[{"id":245736,"domainname":"betify2.com","expirydate":"2027-01-15","status":"Active"},
            {"id":10000001,"domainname":"example.com","expirydate":"2026-12-01","status":"Active"}],
 "count":2,"total":127}
```

| Поле ответа | Смысл |
|---|---|
| `domains[]` | страница записей |
| `count` | сколько записей в **этой** странице |
| `total` | сколько записей всего под текущим фильтром (у пустого фильтра — 127) |

### 2.2 Поля записи домена

| Поле | Тип | Куда идёт в SDMP |
|---|---|---|
| `id` | число | **это и есть `domainid`** для `changeNameServer` (имя ключа разное!) |
| `domainname` | строка | `DomainInfo.domain` |
| `expirydate` | строка-дата | `DomainInfo.expiry_date` |
| `status` | строка (`"Active"`, `"Expired"`, …) | `DomainInfo.status` |
| `regdate`, `nextduedate` | присутствуют; тип не снимали | не используется |
| `donotrenew`, `dnsmanagement` | присутствуют; тип не снимали | не используется |
| **nameservers** | **отсутствует полностью** | см. §5 |

⚠️ **Имя ключа id меняется между эндпоинтами:** в листинге это `id`, а
`changeNameServer` требует `domainid`. Переименование поля — не выдуманный риск, поэтому
`domain_id()` различает «домена нет в аккаунте» и «записи есть, но id не добыт ни у
одной»: второе — про формат ответа, и сказать надо именно это (иначе при переименовании
поля клиент обвинял бы аккаунт пользователя в отсутствии домена, который в нём есть).

### 2.3 Пагинация — как её обходит SDMP

`PAGE_LIMIT = 1000` — это **потолок API**, а не выбор (§4.2). Правила обхода в
`all_domains()`, каждое стоит живого наблюдения:

- **`offset` двигается на число ПОЛУЧЕННЫХ записей, а не на запрошенный `limit`.**
  Запрошенный `limit` API соблюдать не обязан, и шаг «по запрошенному» перепрыгивал бы
  через хвост каждой страницы.
- **Короткая страница ≠ конец списка.** «Прислали меньше, чем просили» у этого API —
  штатное поведение, а не сигнал.
- **Признак конца — ПУСТАЯ страница.** `total` — только верхняя граница: он позволяет
  сэкономить последний запрос, но не решает, полон ли ответ. Обратный порядок («кончился,
  когда набрали `total`») экономнее и молча врёт: исчезни или переименуйся поле — и
  листинг обрезался бы первой страницей, а домены со второй перестали бы «существовать»
  (`get_domains` их не покажет, `domain_id` объявит, что домена нет в аккаунте).
- **`MAX_PAGES = 50`** — страховка от единственного исхода, при котором цикл не кончится
  сам: API, игнорирующий `offset`. Обрывать список молча нельзя (это опять «часть выдана
  за всё»), поэтому — ошибка. Без потолка вызов висел бы 50 запросов по 30 секунд таймаута.
- **`count` клиент не читает вовсе** — его роль полностью покрыта длиной массива.

### 2.4 `filter` — работает только по документированному ключу

**Сверено вживую (2026-08-17).** `{"status":"Active"}` в фильтре даёт `total: 120` из 127
— то есть фильтр как механизм существует. А по имени домена он **молча игнорируется** —
это ловушка §4.3. Клиент SDMP `filter` не использует ни в одном запросе.

### 2.5 Проверка соединения

`test_connection` шлёт самый дешёвый осмысленный запрос: `GET /domain/list?limit=10`.
Успех — «API ответил распознаваемым JSON без конверта отказа», то есть токен принят.

## 3. `POST /domain/changeNameServer` — запись NS · МУТАЦИЯ

**Сверено вживую (2026-08-17)**, включая успешную ветку на `betify2.com`.

**Запрос:**

```
POST /clients/di-api/v3/domain/changeNameServer
X-Authorization-Token: <token>
Content-Type: application/json

{"domainid":245736,"ns1":"ada.ns.cloudflare.com","ns2":"bob.ns.cloudflare.com"}
```

**Ответ при успехе · 200:**

```json
{"result":"success"}
```

Реестр после этого обновился **примерно за 20 секунд** (проверено запросом в RDAP: у
`betify2.com` появились `ADA.NS.CLOUDFLARE.COM` / `BOB.NS.CLOUDFLARE.COM`).

**Правила тела:**

| Правило | Что будет при нарушении |
|---|---|
| `domainid` — **число** | строкой `"245736"` → `400 Bad Request` (§4.1 по духу: значение то же, ответ — отказ) |
| `ns1`, `ns2` — обязательны | голый `{"code":400,"message":"error"}` без причины (§4.4) |
| до `ns5` включительно | то же самое |
| тело — JSON | `400 Syntax error` (§4.1) |
| хосты NS должны существовать | `400` без причины (§4.4) |
| домен должен быть ваш | `403 Forbidden` (§4.5) |

**Гейты в SDMP стоят ДО сети** (`set_nameservers`), и это не педантичность: на неверном
числе серверов API отвечает `{"code":400,"message":"error"}`, из чего пользователю нечего
понять. Поэтому клиент сам отвечает «нужно хотя бы 2» / «принимается не больше 5», а
перед подсчётом схлопывает повторы **после** нормализации (`normalize_ns`):
`ADA.ns.cloudflare.com.` и `ada.ns.cloudflare.com` — один сервер, и без схлопывания дубль
прошёл бы гейт как «два сервера» — или, хуже, был бы принят как делегирование на один.

**Пустое тело ответа — законный исход** и обрабатывается как успех (`call()` возвращает
`{}`).

## 4. Пять молчаливых ловушек DI-API v3

Все пять сверены вживую (2026-08-17). Общее у них одно: **API не жалуется**. Он отвечает
`200` или отвечает `400` без причины — и в обоих случаях код, написанный «по здравому
смыслу», получается тихо неверным.

### 4.1 Form-encoded тело → `400 Syntax error`

**Чем молчалива:** ошибка называет синтаксис, но **не говорит, что дело в кодировке
тела**. Отправив `domainid=245736&ns1=…` как обычную форму, получаешь `400 Syntax error`
и уходишь искать опечатку в значениях — которых там нет.

```json
{"error":{"code":400,"message":"Syntax error"}}
```

**Что ломается:** любая попытка звать API «как обычный веб-хук». **Только JSON** —
в `call()` тело уходит через `req.json(&j)`, `Content-Type: application/json` стоит в
`headers()`.

Сюда же по духу: **`domainid` строкой**. `{"domainid":"245736"}` — то же значение, тот же
формат тела, но ответ `400 Bad Request`. Ни намёка, что проблема в типе. Отсюда асимметрия
в коде, которая иначе выглядит небрежностью: наружу `domainid` уходит **жёстко числом**
(`Value::from(id)`), а внутрь (`as_i64`) принимается и строка — потому что цена промаха на
**чтении** молчаливая: запись просто выпадает из индекса доменов.

### 4.2 `limit=1001` тихо откатывается к 100

**Чем молчалива:** это не ошибка и даже не усечение до потолка. Попросив 1001, получаешь
**100** — то есть ответ, который по всем признакам выглядит нормальной страницей.

**Что ломается:** «возьму весь аккаунт одним запросом». Код, который просит `limit=100000`
и считает полученный массив полным списком, получит первые 100 доменов из 127 — и будет
уверен, что это всё. Дальше `domain_id()` для 27 доменов честно скажет «домена нет в
аккаунте», а `get_domains()` покажет усечённый список без единого признака проблемы.

**Что делать:** **только пагинация**, и `PAGE_LIMIT = 1000` понимать как потолок, а не как
настройку. Из того же наблюдения растёт правило §2.3: раз запрошенный `limit` API
соблюдать не обязан, шагать `offset` можно только по числу **полученных** записей.

### 4.3 `filter` по имени домена молча игнорируется

**Чем молчалива:** запрос отвечает `200` и отдаёт **все 127 записей** — то есть выглядит
успешным поиском, у которого «нашлось много». Проверено на двух написаниях ключа:

| `filter` | Ответ |
|---|---|
| `{"domainname":"betify2.com"}` | все 127 записей |
| `{"domain":"betify2.com"}` | все 127 записей |
| `{"status":"Active"}` | `total: 120` — **работает** |

Работает **только документированный ключ** (`status`), а по нему конкретный домен не
найти.

**Что ломается:** самый естественный код — «фильтрую по имени, беру `domains[0]`» — берёт
**первую попавшуюся запись аккаунта** и уверенно считает её нужным доменом. Дальше её
`domainid` уезжает в `changeNameServer`, и NS переписываются **не тому домену**. Из всех
пяти ловушек эта — самая дорогая: она не ломает операцию, она выполняет её над чужим
объектом.

**Следствие для архитектуры:** `domainid` добывается **ТОЛЬКО полным листингом** и
сопоставлением по имени на стороне клиента (`domain_id` → `all_domains` →
`domain_index`). Отсюда же кэш `domain_ids` в сервисе: цена одной смены NS — выкачка всего
аккаунта. ⚠️ **Границы кэша:** он живёт ровно столько, сколько сам `HostiqService`, а
`commands::registrars::reg_service` собирает новый сервис на **каждую** tauri-команду —
значит массовый прогон (`full_setup::push_nameservers` зовёт команду по домену за раз)
всё равно листает аккаунт заново на каждый домен. Убрать это можно только слоем выше,
переиспользованием сервиса между вызовами.

### 4.4 Реестр валидирует существование хостов NS — но причину не сообщает

**Чем молчалива:** отказ приезжает **без объяснения**. Сверено вживую:
`test1.cloudflare.com` (хост не существует) отбит `400`, а реальная пара
`ada/bob.ns.cloudflare.com` принята. Тело отказа:

```json
{"error":{"code":400,"message":"error"}}
```

Да, `message` — буквально слово `error`. То есть человекочитаемой причины нет вообще, и
после разбора конверта наружу уходит текст «`Hostiq error: error`».

**Что ломается:** отладка. Один и тот же голый `400` приходит и на несуществующий хост, и
на неверное число NS, и на пустую строку в списке — различить их по ответу **невозможно**.
Именно поэтому все проверки, которые можно сделать на клиенте (число серверов, пустые
строки, дубли), стоят **до** сети (§3): иначе пользователь получает `400 error` и никакой
зацепки. Опечатку в имени NS-хоста API при этом поймает — но скажет только «error».

### 4.5 Владение проверяется: чужой `domainid` → `403 Forbidden`

**Чем молчалива:** сама-то ошибка внятная — но она **обвиняет не то**. `403 Forbidden`
читается как «токену не хватает прав» и отправляет проверять права токена, перевыпускать
его, писать в поддержку. А настоящая причина обычно другая: `domainid` **не из этого
аккаунта** — например, взят из чужого листинга, перепутан, или подставлен по имени,
которого в аккаунте нет.

**Что ломается:** диагностика уходит в сторону прав доступа. Поэтому `domain_id()` **сам**
отвечает «`Hostiq: domain <d> is not in this account's domain list`» и запрос вообще не
отправляет — вместо того чтобы дать API ответить `403`. Тест
`an_unknown_domain_is_named_as_such_and_never_sent` держит именно это: в тексте ошибки
есть имя домена и **нет** слова `Forbidden`.

## 5. Чего у API нет: чтение nameservers

**Сверено вживую (2026-08-17) на всех 127 доменах боевого аккаунта: в `domain/list` НЕТ
ни одного поля с nameservers.** Отдельного эндпоинта под них у DI-API v3 тоже нет.

Это ключевой факт документа. Чтение NS у Hostiq — **не «сломано» и не «не реализовано»,
оно невозможно**. Не ищи эндпоинт: его не существует, как не существовало выдуманного
`PUT /domains/{d}/nameservers` у выдуманного хоста.

Поэтому метода чтения нет и в коде: `RegistrarService` (`registrars/mod.rs`) объявляет
только `test_connection`, `get_domains` и `set_nameservers` — заглушка-отказ, которая
стояла здесь до фазы 4, уехала вместе с самим методом трейта. Метод, отвечающий у одного
провайдера из двух, означал бы, что путь есть; его нет.

Поля `nameservers` нет и в `DomainInfo` (строке листинга): оно всегда было `vec![]` у
**обоих** клиентов — листинг NS не знает ни у Hostiq (нет поля), ни у Namecheap
(`domains.getList` их не отдаёт вовсе), — то есть было ловушкой ровно того сорта, от
которого построена лестница делегирования: пустой список неотличим от «у домена нет NS».
Отсутствующее поле такой подмены не допускает.

**Источник «как есть» в этом проекте — реестр через RDAP**:
`desktop/src-tauri/src/rdap.rs` (`GET https://rdap.org/domain/{domain}`,
`nameservers[].ldhName` через тот же `registrars::normalize_ns`). RDAP отвечает на вопрос
«куда домен делегирован», а не «отвечает ли зона» — именно это и нужно бейджу
делегирования. Живая проверка на `betify2.com`: реестр вернул `ADA.NS.CLOUDFLARE.COM` /
`BOB.NS.CLOUDFLARE.COM` при том, что зона не обслуживается и рекурсивный резолвер отвечает
SERVFAIL. Разбор компромисса `rdap.org` против IANA bootstrap — в докстринге `rdap.rs`.

Источник этот **единственный**, а не резервный: чтение NS через API регистратора снято
целиком — и у Hostiq, и у Namecheap, где оно работало (`namecheap.domains.dns.getList`
разбирался верно). Два источника, из которых один отвечает у одного провайдера из двух,
давали бы под одним и тем же бейджем делегирования разную по надёжности правду; побочный
выигрыш — домен у ручного провайдера (Dynadot) впервые получил настоящий бейдж вместо
серого «нет API». Регистратору осталась только ЗАПИСЬ (`set_nameservers`), которой реестр
не умеет.

## 6. Что НЕ сверено живьём (честный список)

Всё, чего в этом разделе нет, снято запросом боевым токеном. Здесь — то, что не снимали;
не выдумывай для него поведение, а проверь.

1. **Отказ под кодом `200`.** Живьём успех приходил только как `{"result":"success"}`, а
   отказы — с кодом ≥ 400. Ветку `{"result":"error"}` в коде **сознательно не
   выдумывали**: `call()` признаёт `200` отказом лишь тогда, когда узнаёт **конверт
   ошибки** в теле (`error.message`, `message`, `detail`, `errors`). Следствие, которое
   надо знать: тело вида `{"result":"error"}` **без** поля с сообщением было бы принято за
   успех. Если такое поведение однажды встретится — это ветка, которую надо добавить, а не
   баг разбора.
   Обратная сторона того же компромисса: успешный ответ с полем `message` на верхнем
   уровне (живьём не встречался) будет назван ошибкой. Сторону выбрали осознанно —
   объявить неуверенность дешевле, чем записать несостоявшуюся смену NS как состоявшуюся.
2. **IDN / punycode в именах зон `.ua`.** Проверяли только ASCII-имена. Как DI-API v3
   принимает и как отдаёт `domainname` для IDN (в punycode `xn--…` или в Unicode) —
   **не сверено**. Здесь есть риск для §4.3: сопоставление по имени на клиенте
   (`normalize_ns` = `trim` + снятие точки + нижний регистр) при разных представлениях
   одного имени домен просто «не найдёт».
3. **Тип значений `regdate`, `nextduedate`, `donotrenew`, `dnsmanagement`.** Поля в ответе
   есть, но клиент их не читает, и точную форму не снимали.
4. **Прочие методы DI-API v3.** Проверялись ровно два: `domain/list` и
   `domain/changeNameServer`. Что ещё умеет v3 (регистрация, продление, контакты,
   управление DNS-зоной через `dnsmanagement`) — **не исследовано**.
5. **Поведение на аккаунте больше 1000 доменов.** Пагинация проверена на 127 записях,
   то есть на одной странице; многостраничный обход держат только юнит-тесты на
   `wiremock`. Что API отдаёт на `offset` за пределами `total` — не снимали (клиент к
   этому готов: признак конца — пустая страница).

## 7. Правила общения с API (как SDMP шлёт запросы)

Живёт в `desktop/src-tauri/src/registrars/hostiq.rs`.

1. **Токен — только заголовком `X-Authorization-Token`.** На этом стоит разрешение
   печатать транспортные ошибки вместе с адресом (§1.1). Меняя способ авторизации, надо
   менять и политику текста ошибок.
2. **Тело — только JSON.** Никаких form-encoded (§4.1).
3. **`domainid` наружу — только числом**, внутрь (`as_i64`) — что читается. Асимметрия
   намеренная (§4.1).
4. **`base_url` — поле сервиса, а не константа.** Тем же приёмом и по той же нужде, что у
   `NamecheapService`: тесты обязаны проверять не разбор в отдельной функции, а то, что
   **живой путь ответа** зовёт именно её. Тесты — `wiremock` + `with_base_url`.
5. **Гейты до сети.** Всё, что можно проверить на клиенте (число NS, пустые строки, дубли,
   наличие домена в аккаунте), проверяется **до** запроса: API на это отвечает голым
   `400 error` (§4.4) или обвиняющим не то `403` (§4.5).
6. **Чужое тело не пересказывается наружу.** `failure_text` либо называет причину из
   распознанного конверта, либо говорит `Hostiq returned an unrecognised response (HTTP
   <code>)`. Текст ошибки едет **на экран** (бейдж делегирования в `DomainNsPanel`), а
   ответ мог прийти не от Hostiq: страница прокси или капча целиком в интерфейсе — это
   мусор, а не сообщение об ошибке.
7. **Незнание не рисуется фактом.** Пустой список доменов, пустой список NS, `Ok(true)` на
   неразобранном теле — все три формы одной и той же лжи. Ответ, который не распознан,
   становится ошибкой, а не данными (§1.2).
8. **Нормализатор один на весь десктоп** — `registrars::normalize_ns`. Второго не заводить:
   RDAP, гейты NS и сопоставление имён доменов должны нормализовать одинаково, иначе
   «домен не найден» и «NS не совпали» появятся там, где всё совпадает.

## Приложение. Состояние стенда и как перепроверить

**Тестовый домен стенда:** `betify2.com`, `domainid` **245736**. После разведки оставлен
делегированным на `ada.ns.cloudflare.com` / `bob.ns.cloudflare.com`; до проб на нём стояли
`pdns1.hostiq.ua` / `pdns2.hostiq.ua`.

Сверка делегирования снаружи, без десктопа:

```
curl -sL https://rdap.org/domain/betify2.com \
  | python3 -c "import sys,json;print([n['ldhName'] for n in json.load(sys.stdin)['nameservers']])"
```

Боевой токен в репозиторий не кладётся и в этот документ не попадает; при живой
перепроверке он берётся из локального `.env` (ключ `hostiq_hash`) и остаётся там.
Автотесты клиента живут в `hostiq.rs` (модуль `tests`, `wiremock`) и сети не требуют:
`cd desktop/src-tauri && cargo test`.
